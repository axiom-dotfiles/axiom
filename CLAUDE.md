# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A [Quickshell](https://quickshell.org) desktop shell config (QML) for Hyprland, named "axiom". It provides the bar, notifications, lockscreen, app launcher, power menu, OSD, workspace overlay, and rounded corners for the compositor. There is no build step — QML is interpreted at runtime by the `qs` binary.

## Running / reloading

- The shell runs as a detached background process; it is not started/stopped via a foreground terminal command in this session.
- **View logs**: `scripts/log.sh`. It prints warnings/errors since the last reload with colour stripped, so a clean reload is just `Reloading configuration...` + `Configuration Loaded`. Add `--debug` to include `console.log` output, `--all` for the whole history, `-f` to follow, and `-g PATTERN` to grep. It wraps `qs log -c axiom -r <rules>`. Don't rely on stdout or journalctl, since output is redirected to /dev/null. `console.log` is debug level and hidden by default, so use it freely for tracing, and keep `console.warn` for real problems. A normal reload should produce no warnings.
- Config reloads are automatic: `ConfigManager` watches `config/user/config.json` and the active theme file (`FileView` `watchChanges`, plus a 5s safety poll) and hot-reloads on change (see `services/ConfigManager.qml` `_checkForChanges`). An invalid or unreadable config.json never replaces the running config: the shell keeps the last good one (schema defaults at startup), and `savesBlocked` refuses every save until the file is fixed or a saved config is restored. Defaults are only written when the file is truly missing. `config/user/config.json` is owned by the settings UI (not meant for hand-editing), but editing it directly is still a valid way to test config changes without restarting.
- New singleton files (a new `pragma Singleton` QML file in `config/` or `services/`) are picked up by a hot reload with qs 0.3.1 (twelve renamed services were, 2026-09). Older qs only registered them at start; if a new singleton reads as `undefined`, ask the user to restart qs.
- Files loaded by URL (bar widgets, content, views) only see sibling types if some loaded file imports their directory by name: `BarWidgetHost` imports `qs.components.bar.widgets`, `BarPopouts` and `OverlaySlot` import `qs.components.content`, `OverlayPanel` imports `qs.components.views`. Without that, a new shared type there (e.g. `BarIconWidget`) reads as "is not a type" even though its file exists.
- File reads go through `FileManager.read` (a blocking `FileView`), so qs needs no `QML_XHR_ALLOW_FILE_READ`. `XMLHttpRequest` is only for HTTP (weather, chat).
- Lock through `qs -c axiom ipc call lockscreen lock` (what hypridle's `lock_cmd` should run; routes by `Lockscreen.mode`, see Lockscreen below). **Never lock the built-in locker yourself while testing**: only the user can type the password. Test the lock surface by instantiating `LockSurface` in a hidden window instead.
- Do not simulate cursor movement (e.g. `hyprctl dispatch movecursor`) to verify UI behavior — check logs/code instead.
- **Run `scripts/check_structure.py` after adding, renaming or moving QML files.** It statically checks the naming conventions the shell loads by: every schema type (`BarWidget`/`OverlayView`/`OverlayModule`) and `popoutName` has its file, URL-loaded directories are imported by name, every `import qs.…` resolves, and no singleton reference is a typo (`AudioManger.`). Exit 1 on errors.
- **Checks** (all run in CI, `.github/workflows/checks.yml`; `scripts/check_all.sh` runs every one locally):
  - `scripts/run_tests.sh [Name…]`: qmltestrunner unit tests in `tests/tst_<Name>.qml` for `components/methods/` (only Quickshell-free files, so not IconResolver), the real schema (every widget/module/view default is valid) and `ConfigMigration` (`tests/fixtures/configs/v1.json` migrates to a valid current config). Tests read repo files through `tests/RepoFiles.qml`; Lua they write to `tests/.out/` is checked with `luac -p`. Add a fixture or a case when changing a migration step or a methods helper. `SchemaValidation.validationErrors` returns the reasons instead of logging them.
  - `scripts/check_qmllint.py`: qmllint over the whole shell, failing only on warnings missing from `scripts/qmllint-baseline.json` (per file, `category: message` with a count). Fix a new warning, or, if it's a gap in Quickshell's type info, `--update-baseline`. An import only there for qs to scan a directory is marked `// qmllint disable unused-imports`. Both it and the tests lint/import a copy of the shell laid out as QML modules (`scripts/qml_modules.py`), since plain Qt tools can't resolve `qs.*`.
  - `scripts/check_qmlformat.sh [--fix]`, `shellcheck -x -S warning` (`.shellcheckrc`), and `tests/scripts/test_scripts.py` (every theme is complete; every `theme_*.sh` renders dark and light themes in a scratch `$HOME` with stubbed apps and no `Warning:`; `self_update.sh` on scratch clones; `generate_theme.py` on a generated image). `render_template` warns about a `${VAR}` nothing sets.
  - None of these run the shell: still verify QML changes with `scripts/log.sh` after a save (which triggers a reload), and by reasoning through property bindings.

## Formatting

- `.qmlformat.ini` pins `qmlformat` settings: spaces not tabs, 2-space indent, no max column width. Run `/usr/lib/qt6/bin/qmlformat -i` on changed `.qml` files before committing (`scripts/check_qmlformat.sh --fix` does every file). The `qmlformat` on PATH is Qt5's, which can't parse `pragma ComponentBehavior` and fails silently (exit 1, no output).
- The QML JS engine has no `Array.prototype.flatMap` (use `[].concat(...arr.map(...))`) and no `Object.fromEntries` (use `reduce`).

## Architecture

### Directory roles
```
shell.qml       entrypoint — instantiates one top-level Item per module (Bar, Lockscreen, Notifications, Overlay, OSD, AppLauncher, PowerMenu, WorkspaceOverlay, RoundedCorners)
shell/          top-level pieces instantiated by shell.qml (one per surface)
components/     UI building blocks
  methods/      pure singleton helpers (Utils, IconResolver, SchemaValidation, SchemaLayout, ConfigMigration, WorkspaceGeometry, KeyNames, HyprBinds, ChatProtocol, ChatMarkdown, HyprLua)
  reusable/     generic styled widgets (StyledRectButton, StyledTextEntry, BaseWidget, TabBar, DragArea, FieldGroup, ...) with no feature-specific logic
  forms/        the schema-driven form widgets (SchemaField, SchemaPropertiesForm, ...)
  content/      every loadable panel, loaded by name: overlay module types and bar popouts (see Content below)
    base/       content roots: Card (free-form card), Panel (column; popout or card), TitledCard, CardHeader
    parts/      helpers only content uses (ModuleHeader, StatFigure, AudioRow, TrayMenuItem, notifications/, chat/, ...)
  hosts/        where content appears: popout/ (bar + edge popouts: BarPopouts, PopoutAnchor, EdgePopout,
                AttachedSurface, ...) and overlay/ (OverlayPanel, OverlayPages, columns, cells, OverlaySlot)
  views/        overlay pages by view type (Custom, Keybinds, BarEditor, Settings, OverlayEditor) + their pieces
  bar/          the bar itself (BarPanel, BarContainer, WidgetGroup, BarWidgetHost); widgets/ = bar widget types
  surfaces/     standalone windows: launcher, lockscreen, notifications (toasts), powermenu, workspaces, border
services/       pragma Singleton QtObjects — global state and side-effecting logic (see below)
config/         static QML config singletons + JSON config/theme files
assets/         static assets (icons, images)
scripts/        Python/shell scripts invoked as external processes (theming, wallpaper, stats) from qs.services, plus the dev checks
tests/          qmltestrunner unit tests (tst_*.qml), fixtures, and tests/scripts/ for the scripts
```

### Layering

Dependencies point one way, so no layer needs to know about the ones above it:
- **`components/methods/`** are pure: no file access, processes, dispatches or `qs.*` imports (IconResolver only queries the icon theme and desktop entries).
- **Data owners** load and watch files: `ConfigManager` (config.json and the schema), `ThemeManager` (the active theme, `theme-defaults.json`, theme lists, generation, wallpaper, integrations) and `I18n` (dictionaries). ConfigManager reads no config reader.
- **`config/` readers** read only those owners (and each other).
- **Other services** may use readers and methods; they own side effects (`FileManager.read` for synchronous reads, `HyprlandManager` for window/workspace actions, `ShellManager.sessionAction` for power).
- **UI** may use everything below it.

### Import convention

QML files import project-internal singletons/components via the `qs.` namespace, mapped to this repo root, e.g. `import qs.services`, `import qs.config`, `import qs.components.bar`. There are no `qmldir` files — Quickshell resolves `qs.*` automatically from the shell root directory. Prefer this over relative imports.

Most files also start with `pragma ComponentBehavior: Bound` (for delegates/components using `required property`) or `pragma Singleton` (for services/config singletons).

### Services layer (`services/*.qml`)

Every file is `pragma Singleton QtObject` — one global instance per name, imported as `qs.services`. Key ones:
- **ConfigManager** — the source of truth for runtime config. Owns `_config` (parsed `config/user/config.json`) and `_configSchema`, loaded eagerly at creation (the active theme's data belongs to ThemeManager). Load pipeline: parse → `ConfigMigration.migrate` (upgrades old layouts by `version`, writes the result back once, moves API keys to `SecretsManager`) → `SchemaValidation.pruneUnknown` (drops unknown keys with a warning) → `SchemaValidation.applyDefaults` (fills every schema `default`) → validate. All config writes go through `setTheme()` / `setWallpaper()` / `saveConfig()` / `commit(object)` (draft services: runs prune/defaults/validate, returns false and changes nothing if rejected, so drafts stay dirty), which validate before writing, then `forceReload()`. Never mutate `ConfigManager.config` fields directly from UI code and expect persistence — call the setter functions (or `SettingsManager.setValue(path, value)` from settings UI). The editor services (SettingsManager, BarManager, OverlayManager) each hold a `ConfigDraft` (`services/ConfigDraft.qml`: working copy of one config path, `changed()` after in-place edits, `save()` merges onto the latest config via `commit`). `ConfigManager.previews` (`setPreview(section, value)` / `clearPreview(section)`) holds unsaved edits shown live without being part of `config`, so other saves and disk reloads don't touch them: BarManager previews `Bars` while dirty, and `Bar.bars` reads `previews.Bars ?? config.Bars`.
- **SecretsManager** — chat API keys, never in config.json: the provider's `keyEnv` env var, else the keyring (`secret-tool`, `service axiom provider <id>`; probed once, `keyringAvailable`), else `$XDG_STATE_HOME/axiom/secrets.json` (mode 600). `withKey(provider, cb)` is async (cached per session); `status(provider)` is `env` | `keyring` | `file` | `none` | `unneeded`; `setKey`/`clearKey` write through stdin, never argv. Keys are entered on `views/settings/ChatProvidersCard` (the Chat section's `x-card`, with Test and Fetch models), never through the settings draft.
- **ChatManager** — the chat: `conversation` (`{ id, title, preset, provider, model, messages }`), `conversations` (index, newest first), `send`/`stop`/`regenerate`, presets and models, attachments (clipboard, `slurp | grim` region with the overlay closed through `ShellManager.closeOverlay`, dropped files; base64 per send), saved to `$XDG_STATE_HOME/axiom/chats/` (`<id>.json`, `index.json`, `<id>/` attachments) up to `Chat.keepConversations`. Each reply is a `services/ChatRequest` (curl with its config, key included, on stdin via `-K -`; the body in a `$XDG_RUNTIME_DIR` file; a `SplitParser` feeding SSE lines to `components/methods/ChatProtocol`, which builds requests and parses streams for the `anthropic`, `openai` (any OpenAI-style server) and `gemini` kinds). Streamed text lives in `streamingText`/`streamingThinking`, flushed every 50 ms, and replaces the placeholder message only when the reply ends, so the message list doesn't rebuild per token. Anthropic thinking blocks (with signatures) are sent back only to the model that wrote them. `components/methods/ChatMarkdown` splits replies into prose and code blocks. `content/Chat.qml` is a `Panel` (ready to be a popout). IPC `chat`: `open`, `newChat`, `ask <text>`, `settings`; launcher `@` and `/chat`; `OverlayConfig.pageWithModule(type)` finds the page to open. Created from `shell.qml`'s `_services` (for the IPC target).
- **ThemeManager** — owns the active theme: `currentTheme` (loaded eagerly, watched, reloaded when `Appearance.theme` or the file changes) and `defaults` (`theme-defaults.json`); `Appearance.darkMode` is derived from the theme's `variant`. Also theme discovery: `themeFamilies`, one entry `{ label, dark, light, generated }` per theme, where a dark/light pair (each file's `paired` naming the other) is one theme labelled by the words their names share, and `currentFamily`; `applyFamily(family)` picks the variant for the current mode and `setLightMode(bool)` switches the current theme's variant (the only light/dark switch; `Appearance.darkMode` follows the applied theme). Then generation from a wallpaper (`scripts/generate_theme.py`, one run for every pywal backend: the backend only extracts candidate colors, the palette is built in OKLCH from targets measured off the hand-made themes, with the wallpaper's seed as `accent` in `base0F`; run through `scripts/venv_python.sh`, which keeps `.venv` in sync with `scripts/requirements.txt`), `setWallpaper` (runs `setWallpaper.sh`), and `themeIntegrations()` (one `scripts/theme_<key>.sh` per `ThemeIntegrations` switch, listed in `_integrations`; a failure, or a `Warning:` line on stderr, is logged), which run only when the active theme's name or contents change. The choice of theme is persisted through `ConfigManager.setTheme`.
- **ShellManager** — cross-cutting UI signals (power menu, launcher, overlays) that modules connect to rather than calling each other directly, and screen targeting. `General.monitors` is `"primary"` | `"focused"` | `"all"`; the OSD, overlay and launcher have their own `monitors` setting (`"general"` | `"primaryBar"` | `"focused"` | `"all"`, resolved by `modeFor(mode)`; the power menu uses General's). Surfaces are built on `General.screensFor(mode)` (`General.screens` for General's), and only the instance on `targetFor(mode)` (`isTarget(screen, mode)`: the focused monitor in "focused"/"all") answers a shortcut, IPC call or OSD event. In "all" (`everywhere(mode)`, `showsOn(screen, mode)`) the surface opens on every monitor at once: a `reusable/SurfaceGroup` per instance opens and closes the others with it (`ShellManager.surfaceShown`), and since only one `HyprlandFocusGrab` can be active, only the target's instance holds one, over every instance's window (`surfaceWindows`); the launcher's instances share `LauncherManager.text`. The workspace overlay is built on every screen and opens on the one under the cursor (`HyprlandManager.withHoveredScreen`, a `hyprctl cursorpos` lookup). Wallpapers are per monitor (`Appearance.wallpapers[monitor]`, set from the overlay's Themes page; the primary monitor's is also `Appearance.wallpaper`, the lockscreen's). IPC handlers are `enabled` on the target instance only, since a target name can have one handler.
- **SystemManager** — CPU/memory/temp/GPU/disk stats. Reference-counted through a `ConsumerRegistry` (shared with UpdatesManager; identical re-registrations are no-ops): consumers call `acquire(owner, {interval, metrics, diskPaths})` / `release(owner)`, and it polls only the union of requested metrics (sysfs/procfs `FileView` reads, no processes on the hot path), stopping entirely with no consumers.
- **UpdatesManager** — pending pacman/AUR updates shared by every Updates widget (same acquire/release pattern). Only one `checkupdates` may run at a time: concurrent runs share its temp db and fail.
- **Anything that polls goes through a service's `acquire(owner, request)` / `release(owner)`** (a `ConsumerRegistry` inside), so each thing is fetched once for all widgets, at the shortest interval asked for, and not at all when nothing shows it. Widgets never run their own polling Process or repeating Timer. Besides SystemManager and UpdatesManager: `WeatherManager`, `TailscaleManager` (`available`, `backendState`/`connected`, `tailnetName`, `ip`) and `CommandManager` (any shell command's output, `outputs[command]`, shared by identical commands; e.g. a Button's label). Acquire in `Component.onCompleted` (and again when the config-derived request changes: identical requests are no-ops), release in `onDestruction`.
- **NetworkingManager** — Wi-Fi over `Quickshell.Networking` (NetworkManager D-Bus, event-driven): radio (`wifiEnabled`, `setWifiEnabled`), `networks` (connected, saved, then by name; fixed order), connect/disconnect/forget, the password prompt (`passwordFor`, `connectWithPsk`, set again on a `NoSecrets` failure), and the primary connection (`primaryDevice`: wired before Wi-Fi; `netInfo` `{ kind, name, device, signal, ip }`, all bindings, except the IPv4 address, which Quickshell.Networking lacks: one `ip -4 -j addr` whenever the connection changes, or on `refreshIp()`). Nothing runs `nmcli`. The scanner runs only while something holds `acquireScan(owner)`. Not named `Networking` (Quickshell's singleton). Throughput stays in SystemManager.
- **BluetoothManager** — adapter power, scanning, sorted device lists and connect/pair/forget over `Quickshell.Bluetooth`. Not named `Bluetooth`, which would shadow Quickshell's singleton (and the `Bluetooth` bar widget file).
- **NotificationManager** — the DBus notification server plus a persistent history: `entries` (plain objects, newest first, capped at 100) stay until the user removes them (`dismiss(uid)`, `clearAll()`, or the `notifications` IPC target), even when the app withdraws one, and are saved to `$XDG_STATE_HOME/axiom/notifications.json`. `liveNotification(uid)` gives the still-open Notification (for actions), and restored entries open their app instead (`openApp`). `NotificationsConfig` sets the history's size and age (`maxEntries`, `maxAgeDays`) and which user actions remove an entry: `clearOnFocus` (an `activewindow` event whose class matches the entry's desktop entry or app name), `removeOnClick`, `closeRemoves`. Toasts take their entry's uid at creation (`uidOf`), because invoking an action can close the notification. `dnd` is saved in `config/state/notifications.json`. The toasts (`shell/Notifications`) stack once per screen of `NotificationsConfig.monitors` (`showsOn`); a toast the user closes closes on every screen. Images are cached as PNGs in `…/axiom/notifications/`, rendered through an `imageHost` item that `shell/Notifications` lends it (grabbing needs a window). `keepOnReload` keeps live notifications across QML reloads.
- **HyprlandConfigManager**: how axiom sets up Hyprland (`Hyprland` section, `HyprlandConfig` reader). It needs Hyprland's Lua config, 0.55+; axiom's own `hyprctl eval`/dispatch calls are all Lua (`hl.*`, stubs in `/usr/share/hypr/stubs/hl.meta.lua`). One Lua layer covers binds (`binds[]`: an IPC `action` or `exec`, `description` "Axiom: …"), required settings (`allow_session_lock_restore`, a `workspaces` animation), themed borders and blur. `mode` picks how it gets there:
  - `detached`: `hyprctl eval` at startup and on every `configreloaded`, skipping keys `hyprctl binds -j` shows taken (`components/methods/HyprBinds`: `keyId`, `runtimeBinds`, and `userKeyCounts` for KeybindManager). The keys it bound live in Hyprland's Lua state (`AXIOM_RUNTIME_KEYS`), which a Hyprland reload resets along with the binds and which survives a qs reload. They are unbound before the binds are read.
  - `included`: `moduleLua()` goes to `$XDG_STATE_HOME/axiom/hyprland.lua`, a module the user loads with `includeLines`.
  - `managed`: `managedLua()` becomes `~/.config/hypr/hyprland.lua` itself (plus the `managed` options; `matchAxiom` takes window rounding and border width from `Appearance.shape`, rewriting the file when they change), loading `user/*.lua` after it via `require("user.<name>")`. Hyprland watches required files, so user edits reload it; `user/lib/` is for shared modules. The user's own setup is this: `user/` is a symlink to `~/repos/dotfiles/hypr/user`. `scripts/claim_hyprland.sh` (`check` for `checkManaged()`, `claim` for the takeover) refuses a symlinked or git-tracked dir.
  - The `managed` options become one `hl.config({...})` through `components/methods/HyprLua` (pure), driven by schema annotations: `x-hypr` (the option's dotted path, or a list), `x-hyprScale` (integers shown scaled: 0.01 for a percent), `x-hyprValue` (`int`, `number` for numeric enums, `emptyIsDefault`, `color` for a theme color name, with `x-hyprAlpha`), `x-hyprIf` (a boolean sibling gates it) and `x-hyprAlways`. A field is written only when it differs from its default (Hyprland's own), so a new option is just a schema entry. `managed` stays flat (the settings page nests one level): its cards come from `x-group`/`x-order`. Not mapped: `animationPreset` (`hyprland` writes nothing; `axiom` follows `Appearance.animFast/Normal/Slow` and turns animations off with motion; `snappy`/`bouncy`; `custom` from `curves`/`customAnimations`), written after `axiom.setup()`, plus `env` and `autostart` (after axiom in the start hook) and the cursor.
  - Both file modes write only on change, then `hyprctl reload` (Hyprland doesn't watch `dofile`d files).
  - An `AXIOM_INCLUDED` global tells axiom the file is loaded. When it isn't, the runtime layer stands in and `problem` says why.
  - The settings page's Hyprland category starts with `HyprlandStatusCard`, built from `status` (`runtime` | `loaded` | `fallback` | `pending`) and `problem`. A mode picked there waits for Save (`x-applyOnSave`), and the card outlines what saving will do, predicting a managed takeover with `checkManaged()` (`managedCheck`: `ours` | `adopt` | `new` | `blocked`, a dry run of `claimManaged`).
  - `binds` are edited on the Keybinds page, not in settings (see KeybindManager). An action is an axiom IPC call (`_actions`, including the `audio`/`media` targets on AudioManager/MediaManager, so the OSD shows) or a Hyprland dispatcher bound directly (`_dispatchers`: focus/move/resize, close, fullscreen, floating, pin, special workspaces, mouse drag/resize on a `mouse:272` key, which Hyprland makes a mouse bind by itself). Binds carry `repeating`/`locked`/`release` flags, preset from `actionFlags` when the action is picked.
  - Created from `shell.qml`'s `_services`, since other services don't reference it. Never switch the user's real config to `managed` to test it: test `claim_hyprland.sh` on scratch dirs (`tests/scripts/test_scripts.py` does), and render the Lua with node and `luac -p`.
- **KeybindManager** — the Keybinds page: every bind Hyprland reports (`hyprctl binds -j`, grouped by "Section: Label" descriptions), and the editor for axiom's own `Hyprland.binds` (a `ConfigDraft`, saved with `save()`). Per-bind `issues` (no key, bad modifier, missing argument, duplicate, and a key the user's own config binds: Hyprland's binds minus the saved axiom binds it applied, since every Lua bind is an opaque `__lua` dispatcher), `presets` (built from the workspace layout; `applyPreset` skips keys already used) and recording: `startRecording(index)` puts Hyprland in an empty `axiom_record` submap (Hyprland only registers a submap with a bind, so it has an unreachable one, and a Lua timer leaves it after 30 s even if qs dies) so bound combos reach `keybinds/KeyRecorder`; `components/methods/KeyNames` turns the Qt key event into a Hyprland key name.
- **SelfUpdateManager**: axiom updating itself (not packages: that's UpdatesManager). Releases are `v*` tags on the clone's remote; `scripts/self_update.sh check|apply <tag>` does the git work and prints one JSON object (`current`, `commit`, `latest`, `state`: `uptodate` | `available` | `diverged`, `ahead`, `behind`, `blocked`: `dirty` | `diverged` | `branch` | `nogit`, `notes`, `error`). It only fast-forwards (`merge --ff-only`, or `checkout` when detached at a tag) and never stashes, resets or forces. `SelfUpdate.mode`: `auto` applies, notifies and `Quickshell.reload`s (git replaces files by inode, which the watcher misses); `notify` sends a notification whose `desktopEntry` (`axiom-update`) is a `NotificationManager.registerHandler` key, so clicking it runs `openSettings()` (Settings → Updates, the `SelfUpdateStatusCard`); `off` never checks. Checks run once per qs launch (a `PersistentProperties` flag, so hot reloads don't recheck) and daily. `config/state/selfupdate.json` keeps `lastChecked`, `notifiedTag` (each release is notified once) and the last result. IPC `selfUpdate`: `check`, `update`, `open`; launcher `/update`. Created from `shell.qml`'s `_services`. Test the script on scratch clones; never `apply` on the live repo.
- **IdleInhibitManager** — shared caffeine state (a `PersistentProperties`, so it survives QML reloads but not restarts) + `idleInhibit` IPC target; the Wayland inhibitor itself lives in `bar/widgets/IdleInhibitor.qml` (it needs a window).
- Other domain services (AudioManager, BatteryManager, MediaManager (MPRIS), NotificationManager, HyprlandManager, StateManager, BarManager, LauncherManager, SettingsManager, SavedConfigsManager, AuthManager, LockManager) follow the same singleton pattern. Services are named `*Manager` — one owns polling/IPC/process-spawning for its domain and exposes readonly properties + signals.

### Config layer (`config/*.qml`)

Also `pragma Singleton`, but these are typed config *readers*, not owners — one per config section, exposing `readonly property` values from `ConfigManager.config`. No `??` fallbacks: the schema defaults are already filled in. Readers: `General` (displayName, primaryMonitor, `monitors`/`screens`), `Appearance` (theme, font, shape, motion tokens), `Widget`, `Bar` (from `Bars`; the first bar is primary), `PopoutConfig` (open/dismiss delays, edge trigger size — shared by bar and edge popouts), `OSDConfig` (volume OSD: edge, position, orientation, timeout, tracked apps), `LauncherConfig` (launcher placement, size and providers), `NotificationsConfig` (the toasts' corner and gaps, measured inside the work area by an Overlay-layer anchor window with Normal exclusion, like `OverlayPanel`), `OverlayConfig` (views + card-grid constants), `EdgeMenusConfig` (edge menus), `IconConfig`, `ChatConfig`, `ThemeIntegrations`, plus `Paths` (derived filesystem paths from `$HOME` / `Quickshell.shellDir`, not configurable) and `Theme`. Readers whose section name collides with a type get a `Config` suffix (`Popouts`, `Overlay`, `Icons`, `OSD`, `Launcher`, `Notifications`). UI code should read colors/settings from these (`Theme.background`, `Widget.padding`, `Bar.extent`) rather than reaching into `ConfigManager.config` directly.

**Animation timing is uniform:** every `duration:` uses `Appearance.animFast` / `animNormal` / `animSlow` (derived from `Appearance.motion.speed`, and 0 when `motion.enabled` is off), never a literal. Looping animations also gate `running` on `Appearance.animations`. Only behaviour timings (cursor blink, notification timeout, polling) stay as literals.

`config/Theme.qml` exposes the base16 palette (`base00`-`base0F`) plus semantic aliases (`background`, `accent`, `error`, etc.) resolved through `_themeData.semantic`, and a `stringToColorMap` + `resolveColor(name)` for dynamic color lookup by string (used when a color name comes from JSON/config rather than a static binding).

`config/json/config.schema.json` is the single source of truth: shape, `default`s, and — via `title`/`description`/`minimum`/`maximum`/`enum`/`x-options` — the settings page, which is generated from it (`views/Settings.qml`; `x-settings: false` hides a key, `x-category` on a top-level section names its sidebar category, `x-links` lists page types it links to: `Themes`, `OverlayEditor`, or a view type). Adding a setting = add it to the schema (with a default) and a reader property. `x-options: "colors"` makes a string a color picker over `base00`–`base0F` (read it with `Theme.resolveColor`, which also accepts semantic names and hex); `x-hosts` on an overlay module lists where it may be placed (`overlay`, `edgeMenu`; both when left out); `x-showIf` hides a field unless a sibling has a given value (a key starting with `/` is a dotted path from the config root instead, e.g. `"/Workspaces.layout"`, read through `SettingsManager.configValueAt`; evaluated by `SchemaField` itself, so it works in every form; on a nested object it hides that object's settings cards); `x-applyOnSave` keeps a setting in the settings draft until Save instead of applying it live (Hyprland's `mode`, since it can take over files). `x-multiline: true` edits a string in a growing text area; integers render through `forms/SchemaNumberField` (a slider with a value box for 7–200 steps, otherwise a stepper beside the label with ±10 buttons past 20 steps; stepper clicks commit debounced, the slider on release), with `x-unit` (`px`, `%`, `ms`, `s`, `min`, `days`, …) shown after the value instead of in the title, and `x-control: "slider" | "stepper"` overriding the choice; `x-order` on an object schema lists the keys its form (or its settings cards, whose order is their first field's) shows first (a schema reaches QML as a map, whose keys come out sorted). On the settings page, `x-group` puts a field on a card of that name (so one section or object can make several cards) and a section's `x-card: "<Name>"` adds the hand-built `views/settings/<Name>Card.qml` as its first card (the Hyprland category's `HyprlandStatusCard`). Clicking a card's header folds it (`SettingsManager.collapsed`, keyed by the group's `key`, saved to `config/state/settings.json`; search results never fold). The masonry reads `layoutFolds`, a snapshot taken on category/search change and page unload, so a fold doesn't reshuffle the page. Flat objects (array items, widget/module options, the bar's own fields) render through `forms/SchemaPropertiesForm.qml`; only the settings page builds its own rows (`methods/SchemaLayout`: categories → groups → rows). An `array` whose `items` is an object schema renders as an add/remove/reorder list of those fields (`SchemaArrayItem`). There is no separate defaults file. The live file is `config/user/config.json` (gitignored, UI-owned); bump `version` and extend `ConfigMigration` when changing its layout. Theme JSON files live in `config/themes/*.json` (static) and `config/themes/generated/*.json` (pywal-style, generated from wallpaper). `config/json/theme-defaults.json` is the one fallback palette and semantic → base16 map (dark and light), read (through `ThemeManager.defaults`) by `Theme` for keys a theme omits and for a missing theme, and by `scripts/generate_theme.py`. The `scripts/theme_*.sh` integrations share `scripts/lib/theme_env.sh`: dependency checks; `load_theme`, one jq pass that fills what a theme leaves out from `theme-defaults.json`, as `Theme` does; `export_theme_colors` (every semantic color as `UPPER_SNAKE`, plus `ANSI_0`–`ANSI_15`); and `render_template`/`write_atomic`. Each writes only its own `axiom.*` file and never edits a user's config: its header and schema description give the line to add. A main config that's missing may be created with that line (cava's config, GTK's `gtk.css`); one that exists, or a symlink, is never touched. A new integration is a script, a schema boolean, a reader property and an entry in `ThemeManager._integrations`.

### Translation (`config/I18n.qml`)

`General.language` picks the language. English is the source language: user-visible text is written in English, inline, as `I18n.tr("Text")`.
- **Dynamic values** use placeholders, so the whole sentence stays one key: `I18n.tr("{0} updates", count)`. Don't build sentences with template strings.
- **Dates and times** go through `I18n.formatDate(date, format)`, never `Qt.formatDateTime`, so day and month names follow the language. Named formats come from `I18n.dateFormat("longDate" | "mediumDate" | "shortDate" | "monthYear" | "fullDate" | "time24" | "time12")`.
- **The schema form translates itself.** The generic `Schema*` form widgets translate their own `label`/`title`/`description` and dropdown option labels. Callers pass English, and schema titles and descriptions need no code.
- **Adding a language** means adding `config/i18n/<code>.json`: `{"_meta": {"name", "locale", "formats"}, "strings": {english: translation}}`. It then appears in the language dropdown (`x-options: "languages"`).
- **Missing entries fall back to English.** The active dictionary reloads live when edited.
- **Checking coverage.** Run `scripts/check_i18n.py` after changing text; it lists missing and unused entries (`--fill` adds the missing ones empty, `--untranslated` finds UI literals not wrapped in `tr()`).
  - Keys only chosen at runtime (e.g. `I18n.tr(form.shape)`) must be declared in a comment next to the call, as `I18n.tr("square") ...`, so the checker sees them.
- **Leave developer-facing strings in English:** logs, validation errors, migration notes.

### Bar / widget composition pattern

`shell/Bar.qml` renders one `BarPanel` per entry in `Bar.bars` (a `Variants`/model), so multi-monitor / multi-panel bars are data-driven from config, not hardcoded. Each module's options live under its `<Type>Widget.properties.properties` definition in the schema. `SchemaValidation` picks the `BarWidget` oneOf option by `type`, so widget properties get their defaults filled like the rest of the config and modules read `properties.<key>` directly. The bar editor (`views/BarEditor.qml`) has no preview of its own: edits show live on the running bars (see `ConfigManager.previews`) and Save writes them. Its `DragLayer` owns the one drag in progress (`begin`/`move`/`end`, hit-testing the registered `SectionLane`s) and the ghost chip, above both the `SectionsBoard` (five lanes of `WidgetChip`s, dragged within and between sections) and the `WidgetInspector` (the selected widget's options with the same `SchemaField` rows as the settings menu, plus `LayoutOverrideField`s; with nothing selected, the widget library to drag from). `WidgetGroup` models its widgets by count, so live option edits reach a widget in place instead of rebuilding the section. Bar contents are built from `components/bar/{BarContainer,BarWidgetHost,WidgetGroup,BarPanel}.qml` composing widgets from `components/bar/widgets/<type>.qml` (Time, Battery, Network, Workspaces, Media, SystemTray, Notifications, etc.). A widget opens a popout by dropping in a `PopoutAnchor` with a `popoutName`; the per-bar `BarPopouts` (in `hosts/popout/`) loads `content/<popoutName>.qml` by URL, so a new popout is a content file plus an anchor.

### Workspaces (`Workspaces` section, `WorkspacesConfig`)

One layout serves everything that shows or moves between workspaces: the `Workspaces` bar widget, its `WorkspaceGrid` popout, the workspace overview (`surfaces/workspaces/`), the `WorkspacesMap` module, the launcher's `/ws` and the `workspaces` IPC target.
- **Layouts.** `standard` is ids 1..`count`, shared by every monitor. `grid` gives each monitor `columns × rows` ids, numbered in Hyprland's monitor order (`WorkspacesConfig.baseFor(index)`). Nothing else holds a workspace count or grid size.
- **Ids.** `HyprlandManager.workspaceBase(monitor)` / `workspaceIds(monitor)` give a monitor's ids. The overview lays them out `boardColumns × boardRows`; in the standard layout it shows windows from every monitor, each placed against its own monitor's origin.
- **Navigation.** Everything goes through `HyprlandManager.goToWorkspace(id, mode, monitor)`, `stepWorkspace(direction, mode)` and `nthWorkspace(n, mode)`. `mode` is `go`, `move` or `moveSilent`. In a grid it only reaches the monitor's own ids, going by row, then column, with a slide along each axis (`animate`). The slide briefly overrides Hyprland's `workspaces` animation (read with `hyprctl animations` at startup and on config reload) and puts it back. Keybinds call `qs -c axiom ipc call workspaces …` instead of scripts of their own.
- **The bar widget.** `bar/widgets/Workspaces.qml` loads `workspaces/WorkspaceStrip` (standard) or `workspaces/WorkspaceGridStrip` (the active row, or column on a vertical bar) by layout. Their options share one schema definition: layout-only options hide themselves with `x-showIf: { "/Workspaces.layout": … }`. In a grid the widget hands its `properties` to the `WorkspaceGrid` popout, which uses the same colors, labels (grid position), app icons and click to switch as the strip.

### Content (loaded by name, shown by hosts)

`components/content/<Name>.qml` holds every loadable panel. The name is the overlay module `type` (`OverlayModule.oneOf`) and/or a bar `popoutName`; one file can be both (AudioMixer, BluetoothDevices, Notifications, NowPlaying, SystemGraphs, Updates, WifiNetworks). Hosts load it by URL and pass their context:
- **Roots.** `Card` (`content/base/`) is a free-form card (box, `properties`, slot context); card-only content uses it. `Panel` lays its children out in a column and works in either host: in a bar popout it sizes to its content with the popout box (`wrapper` set, `hovered` read for dismissal); in a card the host passes `embedded: true`, it fills the slot with the card box, and `compactContent` (e.g. a `StatFigure`) replaces the column in a quarter slot. A popout with a text field sets `wantsKeyboardFocus` (BarPopouts then takes a focus grab and the bar takes keyboard focus on demand; a click outside emits `focusLost`). Both expose `properties`, `slotRect`, `cols`/`rows`, `shape`, `compact`, `pad`.
- **Hosts.** `hosts/overlay/OverlaySlot` (card: `properties`, `slotRect`, `embedded: true`) and `hosts/popout/BarPopouts` (popout: `wrapper`, then the anchor's payload keys copied onto matching properties).
- Pairs that look different by design stay separate files: `Weather` (card) / `WeatherForecast` (popout), `ClockCalendar` / `Calendar`.

### Overlay composition (views → columns → cells → modules)

`Overlay.views` in the schema drives the overlay's pages, just as `Bars` drives the bar. Views are made of columns, columns of cells, and cells of modules. Everything loads by naming convention, so there are no lookup tables:
- **View** (`OverlayPages` → `OverlayView`): `components/views/<type>.qml`, which receives `screen` and `viewConfig`. `Custom` (`views/Custom.qml`) places its `columns` side by side. `Keybinds`, `BarEditor` and `Settings` are hand-built pages, with their pieces in `views/barEditor/`, `views/keybinds/` and `views/settings/`. `ShellManager.showOverlayPage(type)` switches the overlay to a page (`qs -c axiom ipc call overlay page <type>` opens it on one).
- **Column** (`OverlayColumn`): just `{ cells: [...] }`. The cells flow left to right and wrap at the column's widest cell, so Singles after a Wide sit side by side under it; an empty Single acts as a gap. `OverlayConfig.columnFlow(cells, unit, target)` computes the arrangement: `OverlayColumn` places its cells from it (no `Flow`), and the editor preview uses it for sizing. A cell with `fill: true` grows into `target` room (`{ width, height }`): the rest of its row, its row's height, and spare column height split evenly between rows holding a fill cell, so two fill cells around others centre them. `OverlayCell` sizes its slots from its real size, while modules keep the layout's `slotRect` (shape and fit checks don't change). `Custom` passes the tallest column's height (pages never grow); `EdgeMenuBody` passes the whole edge (`maxLength`) once any cell fills, spare width going to the columns holding one on top/bottom edges. The editor draws natural sizes with a fill badge (`ColumnsEditor.setCellFill`, the inspector's Fill space switch).
- **Cell** (`OverlayCell`): `layout` names an entry in `OverlayConfig.layouts`. Each entry is `{ cols, rows, slots: { name: [col, row, colSpan, rowSpan] } }` on a half-card grid, and `span(n)` converts half units to pixels. `Tall` (two cards high) and `Wide` (two cards wide) hold panel-sized modules; `HalfWide` (2×1) and `HalfTall` (1×2) are half-card cells. Adding a layout means one entry there plus the `OverlayCell.layout` enum in the schema.
- **Module** (`OverlaySlot`): `content/<type>.qml`, filling its slot. Its root is `Card` (box, `properties`, slot context; override only what differs, like `color`) or `Panel` (see Content). Titled scrolling panels (ThemeEditor, the bar editor panels, the settings page's content) use `TitledCard`, which has a `CardHeader` with `title`, `dirty`, `save()`/`reset()`, `headerExtras`, and children that go into the scrolling body. Adding a module means the file plus an `…OverlayModule` definition in `OverlayModule.oneOf`, with `x-shapes` listing the slot shapes it fits. Shapes are `square`, `horizontal` and `vertical`, taken from the slot's span (`OverlayConfig.slotShape`/`fits`); leaving `x-shapes` out means any shape. The editor only offers modules that fit and treats a misfit as a problem that blocks Save, and `OverlayCell` logs a warning for one. Helpers used only by content go in `content/parts/` (subfolders for groups, e.g. `parts/settings/`). `OverlaySlot` imports `qs.components.content` so that `qs` scans the URL-loaded content; without it, their own `qs.*` imports fail with "not installed".

Views and modules are `oneOf`s discriminated by `type`, like `BarWidget`.

**Sizing:** the card size is per screen, not a constant. Each `OverlayPanel` has an `OverlayGrid` (`hosts/overlay/`) whose `unit` is what fits the page area above the navigator (`min(height / fitCardsHigh, width / fitCardsWide)`, capped at the reference `OverlayConfig.cardUnit` 500, times `Overlay.size`%, never below `minCardUnit`). Views receive it as `grid` (`BaseView`) and size everything from `grid.unit` / `grid.span(n)` / `grid.columnFlow(cells)`, passing plain numbers down to content; `OverlayConfig.span`/`columnFlow` without a unit are the reference size (the editor preview uses them, scaling by hand). A page that still doesn't fit is shrunk as a whole by `OverlayPages.fitScale` (Item.scale, last resort). `cardSpacing`/`cardPadding` don't scale.

**Loading:** one overlay per screen in `General.screens` (`shell/Overlay.qml`): a transparent `OverlayPanel` inside the reserved area, over a `reusable/ScreenBackdrop` that dims the whole monitor under the bars and border (a Top-layer surface kept under them by a Hyprland `order` layer rule that `HyprlandManager` adds at startup and on config reload; the workspace overview and launcher use it too). Its `HyprlandFocusGrab` also whitelists `ShellManager.grabPartnersFor(screen)`: the bars, bar popouts and tray submenus register themselves there (`registerGrabPartner(window, screenName)`), so they keep working while it's open. Only the current page and its neighbours (navigation wraps) are instantiated, and only while the overlay is open (`OverlayPages.isLoaded` → `OverlayPage.loaded`), so modules must not assume they live forever: acquire in `Component.onCompleted`, release in `onDestruction`, and keep state that must survive in a service. Under the pages, `OverlayPageNavigator` shows a tab per page (`OverlayPages.pages`: icon and name from `OverlayConfig.viewIcon`/`viewLabel`, shared with the overlay editor) with a sliding accent pill; when all names don't fit, the other tabs drop to icons with tooltips.

**Writing overlay modules:**
- **Shape-aware.** `Card` and `Panel` expose the slot's `slotRect`, `cols`/`rows` (half units), `shape` and `compact` (a quarter slot), plus `pad`. Each module picks its internal layout from these: side by side when horizontal, stacked when vertical, the key figure only when compact.
- **Shared parts** live in `content/parts/`: `ModuleHeader`, `Sparkline`, `StatFigure`, `TileGrid` (lays out `reusable/ActionTile`s, the icon-well tiles the power menu also uses).
- **Content can be both.** A `Panel`-rooted file is a bar popout and a card at once; branch on `embedded` for card-only parts (a header, a mode switch, acquiring with the card's `properties`).
- **Data sources.**
  - `SystemManager` adds `history: true` (60-sample ring buffers), a `net` metric (`/proc/net/dev` rates; the connection itself is `NetworkingManager.netInfo`) and a `processes` metric (two-frame `top`, with `kill(pid)`).
  - Weather comes from `WeatherManager` (acquire with `{ latitude, longitude, location, units, intervalMinutes }`, read `sourceFor(request)`): one `WeatherSource` per distinct location and units, shared by the bar widget and the module.
- **Never derive a Repeater model, or anything passed to `acquire()`, from live values.** Build it from config (and tool availability) only. When the set of items is itself derived, model the Repeater by a joined string key or a count (`model: rows.length`, delegate reads `rows[index]`): an `int`/`string` only notifies when it actually changes, so the delegates survive each sample. A model that re-evaluates on every sample rebuilds its delegates (and Canvases) many times a second. That once pushed qs past 25 GB. `SystemManager.acquire()` now ignores identical re-registrations.
- **Testing a module safely.**
  - The running shell only picks up schema changes on a QML reload, and a reload only fires when a file it has *loaded* changes. A new module file doesn't count until something uses it.
  - A config checked against a stale schema fails validation, and the whole shell falls back to defaults until it's fixed.
  - So confirm the schema was reloaded after your edit before putting a new module into `config.json`. Add modules one at a time and watch `qs`'s RSS.

**Themes page:** `views/Themes.qml`, the `Themes` view type (in `Overlay.views` like any other, with nothing to configure). It's a `Custom` view that overrides `columns` with fixed ones: `WallpaperPicker` (in a Tall slot it adds a monitor picker and a preview, and sets the picked monitor's wallpaper), `ThemeEditor` (the theme list and light mode switch) and the 16 `ColorSwatch`es.

**Overlay editor:**
- `views/OverlayEditor.qml` with its pieces in `views/overlayEditor/`. It's not in config: `OverlayPages` adds it (`pinnedPages`) as a persistent page after the Repeater, so it's always last, can't be removed, and survives the page rebuild that every `Overlay.views` change causes (pages are keyed by the views' JSON, so other config edits don't rebuild them; `_onPinned` keeps the user on it across that rebuild).
- Layout, as in the bar editor: `PagesPanel` (pages, dragged to reorder; Save/Reset; the selected page's name; problems) on the left, and `PageCanvas` above `EditorInspector` on the right. `PageCanvas` draws the selected page at a scale it computes itself (not `Item.scale`): `CanvasColumn`s (header grip, cells placed from `OverlayConfig.columnFlow(...).rects`) with `ColumnGap`s between them, `CanvasCell`s (hover grip) and `SlotTile`s. The inspector shows a selected module's options plus its cell's layout thumbnails, or else the `ModuleLibrary` (modules and cell layouts to drag or click).
- `EditorDragLayer` covers the whole page. It owns the one drag in progress and its ghost, like the bar editor's `DragLayer`. Drop targets register themselves with a `targetKind` (`slot` > `gap` > `column` / `pages`, most specific first). Draggables use `reusable/DragArea` (press, a 6 px threshold, then begin/move/end) and pass `{ kind, icon, label, ... }` payloads: `module-add`/`module-move`, `cell-add`/`cell-move`, `column-move`, `page-move`.
- The canvas pieces are shared with the edge menu editor, so none of them names a service: they edit through `dragLayer.editor`, a `services/ColumnsEditor` (non-singleton: one set of columns, its selection, every column/cell/slot edit, `problemsFor(columns, name)`; the owner points `columnsOf` at the columns in its draft and saves on `edited`). `PageCanvas` takes `editColumns` (null: nothing to edit), `title`, `icon`, `emptyText`; `EditorInspector` takes `editable`; a `pages` drop is only reported (`pageMoved`).
- All edits go through `services/OverlayManager.qml`, a draft copy of `Overlay.views` like `BarManager`, whose `layout` is the selected page's `ColumnsEditor`. `problems` blocks Save, and Save merges onto the latest config. Drop places are `{ kind: "column", column, index }` or `{ kind: "gap", index }` (a new column), with indices counted as if the moved item were still in place. `_restructure` tracks cells by identity, so the selection follows what moved, and it removes any column a move empties. Dropping a module on an occupied slot swaps the two (`canMoveModule`: both must fit). Dropping one between cells gives it its own cell (`OverlayConfig.bestLayoutFor`).
- Module and view pickers read `OverlayConfig.availableModuleTypes` / `availableViewTypes`. These come from the schema's `oneOf`s, including `x-shapes` and `x-icon` (a Material Symbols name), so new types show up there automatically. The inspector generates property rows from each module's `properties` schema.
- `TypePickerPopup` (overlay root) is the shared "pick a type" popup used by both the bar editor and the overlay editor.

### Edge menus (`EdgeMenus` section, `EdgeMenusConfig`, `EdgeMenuManager`)

Menus that pop out of a screen edge, holding overlay modules. `EdgeMenus` is an array like `Bars` (`x-settings: false`, blocked from `/config`: the edge menu editor owns it). Each entry has `id`, `monitor`, `edge`, `mode`, `position`, `cardSize`, style (`padding`, `backgroundColor`/`borderColor` read through `EdgeMenusConfig.colorsOf`, floating `edgeDistance`, integrated `frame`/`margin`), hover (`openOnHover`, `openDelay`, `triggerSize`, `triggerLength`: 0 is the menu's length, `EdgeMenusConfig.lengthOf` from config until it's loaded; `closeOnLeave`, `closeDelay`), `closeOnOutsideClick` and `columns` (`[OverlayColumn]`, the overlay's column → cell → module chain as is). Escape closes a focused menu (`EdgeMenuBody`), and the `edgeMenu` bind action toggles one by id.
- **State.** `EdgeMenuManager` holds which menus are open and pinned (a `PersistentProperties`, so a reload doesn't reflow windows) and the `edgeMenu` IPC target. The menus follow it and report back when they close by themselves. A bar `Button` with `action: "edgeMenu"` and `menu: <id>` toggles one, passing itself as the anchor, so a floating menu stays open while the button is hovered.
- **Hosts** (`surfaces/edgemenu/`). `shell/EdgeMenus` builds one `EdgeMenu` per enabled entry (keyed by id), which `LazyLoader`s the host for its mode. Both put `EdgeMenuBody` inside: a row of `OverlayColumn`s on an `OverlayGrid` with `fixedUnit: cardSize`, scrolling along the edge when it's too long.
  - `floating`: `FloatingEdgeMenu`, an `EdgePopout` (`contentPadding`, `edgeOffset`, `fillColor`/`strokeColor`, defaulting to what the OSD uses). It's `detached` (a plain box) when `edgeDistance` > 0 or its edge has a pill or transparent bar, else attached to the border or solid bar.
  - `integrated`: `IntegratedEdgeMenu`, a `PopoutWrapperBase` with a Top-layer `axiom-edge-menu` window along the whole edge. Its layer rule's `order = 7` (above the bars' 5) arranges it first, so it sits outermost and the border, bars and every Normal-exclusion surface move inwards. The zone is set once while it's mapped (windows retile in one step) and the strip slides in. With `frame`, a rounded stroked box runs the strip's whole length `margin` in from its edges, holding the modules `padding` in from its stroke. It reports its zone (`EdgeMenuManager.setZone`), which `BarPopouts.borderInset` takes off the perpendicular bars' length.
- **Editor.** `views/EdgeMenuEditor.qml`, the `EdgeMenuEditor` view type: an ordinary page in `Overlay.views` (in the defaults; the user may remove it, and then `ipc call edgeMenu edit` / launcher `/menus` do nothing), with `edgeMenuEditor/MenusPanel` (the menus, "Show on screen", the selected menu's fields in groups from the `EdgeMenu` schema, problems) on the left and the overlay editor's `PageCanvas` / `EditorInspector` on the right. The draft (`ConfigDraft { path: ["EdgeMenus"] }`, `layout`: the selected menu's `ColumnsEditor` with host `edgeMenu`) lives in `EdgeMenuManager`, and shows live on the running menus through `previews.EdgeMenus` while dirty, as the bar editor's does. "Show on screen" sets `previewing` to the selected menu (following the selection and id renames) and opens it; `isHeld(id)` (pinned or previewing) makes a menu ignore `closeOnLeave` and outside clicks. The page's `onDestruction` (the overlay closing) stops it.
- **Pin.** `content/Pin` toggles `EdgeMenuManager.pinned[host.id]`. While pinned, a menu ignores `closeOnLeave` and outside clicks. Modules learn where they're shown from `host` (`{ kind: "overlay" }` or `{ kind: "edgeMenu", id }`, on `Card`/`Panel`, passed down `OverlayColumn` → `OverlayCell` → `OverlaySlot`). `x-hosts` on a module definition limits where it may go: `OverlayConfig.modulesFor(host)` feeds the pickers, and `OverlayManager.problems` flags a menu-only module on a page.

### Popouts (bar + screen edge)

Shared pieces live in `components/hosts/popout/`: `PopoutWrapperBase` (open/close/queue state, hover-loss dismiss timer), `SlideAnimation`, and `AttachedSurface` (the content box + connector + `CornerPiece` fillets that make a popout look like it grows out of a bar or the screen border; `edge` is a `Bar.Location`). Bar popouts (`BarPopouts.qml`) share one wrapper per bar. Screen-edge popouts (`EdgePopout.qml`, used by `OSD.qml`) are one independent instance per screen (`Variants` over `Quickshell.screens`). Each is an Overlay-layer `PanelWindow` with Normal exclusion and a `-borderWidth` margin, so it lands on the inner stroke of whatever reserves that edge: the border (`surfaces/border/`) or a bar.

**Bars and the screen border share an edge by layer-shell ordering.** `Appearance.screenBorder` turns the border (`shell/RoundedCorners`) off.
- **Solid bar** (`Bar.background: "solid"`): Top layer, at the screen edge. The border's strip on that edge is arranged after it and overlaps its inner part, so the strip's stroke is the bar's inner edge.
- **Floating bar** (`barConfig.floating`: transparent or pills, with the border on): Overlay layer, whose exclusive zones Hyprland arranges after the Top-layer border. It sits just inside the border with a `-borderWidth` margin, so its outer edge lies on the border's stroke. It hides while its workspace has a fullscreen window. Hyprland counts that margin into the reserved space, so it reserves `extent`. `RoundedBorders.cornerMargin` pulls the corner pieces back out to the border's corners on a floating bar's edge.
- **Pills** (`BarContainer.pillRects`): one per section, merged when they're at most `pillMerge` apart. Each is an `AttachedSurface` growing out of the bar's outer edge, covering the border stroke (`barConfig.overlap`); widgets sit `overlap + pillPad` in from that edge. A pill at an end of the bar joins the perpendicular edge (`joinStart`/`joinEnd`: flush on its stroke, whose far corner meets it with a fillet). The bar window is `borderRadius` thicker than `extent` in pill mode for that fillet, masked to the bar itself. Floating bars take `-borderWidth` margins on both ends too, so bar-window 0 along the bar is the perpendicular stroke's outer edge.
- **Bar popouts** join an end the same way when their alignment would push them back from it. On a pill bar, a popout not wholly within its pill (`BarPopouts.mergeWithPill`) grows from the outer edge instead, deeper by the pill, with the pill's interior showing through the surface's notch (also cut out of the input mask); each side wall lands on the frame, or on the pill's far stroke (`startFoot`/`endFoot`) where the pill carries on past it. On a transparent bar popouts are `detached`: plain rounded boxes, except one pushed to an end (`BarPopouts.cornerAttach`), which attaches to that perpendicular edge instead, joining it on both sides. They're a layer surface of their own (`underWindow`, not a popup, which would always draw over its bar) in the `axiom-popout-under` namespace, whose layer rule (`order = 6`) stacks it under the bars and border; it starts at the bar's outer edge and the box (`AttachedSurface.detachedOffset`) slides out from beneath the bar. Detached floating edge menus do the same (`EdgePopout.slideDistance`/`underLayer`).
- **Transparent bars** reserve `Hyprland gaps_out` less (`HyprlandManager.gapsOut`), so windows start at the bar's invisible inner edge and the widgets' gap to them matches their gap to the screen edge. Bar popouts use `adjustment: PopupAdjustment.None`: their placement is computed, and Hyprland otherwise nudges one flush on the screen edge a few pixels inwards.
- **Border off**: a solid bar draws its own inner stroke (`barConfig.innerStroke`, on its innermost `borderWidth` pixels, where its popouts attach). Surfaces on a bare screen edge (`Bar.screenEdgeOpen(screen, location)`: no border, no bar there) run straight off it, with no fillets and no `-borderWidth` margin: `AttachedSurface.straight` (attach edge) / `straightJoins` (joined ends) for pills, merged popouts and EdgePopout, and the overlay panel pushes its corners and stroke past the window on those sides.

**Icons are Material Symbols names** (`"wifi"`, `"battery_5_bar"`, from the `ttf-material-symbols-variable` font), drawn by `reusable/StyledIcon` in `Appearance.iconFamily`, never in the text font, so any text font works. Services, schema defaults (`x-icon`, icon fields) and launcher `glyph`s hold names. An icon never shares a Text with a label: put a `StyledIcon` next to a `StyledText`. `StyledIcon` draws anything that isn't a name (a glyph or text a user typed into an icon field) in the text font. `DependencyManager` warns and notifies once when the font is missing. Look names up at fonts.google.com/icons.

Icon + label bar widgets extend `bar/widgets/BarIconWidget.qml` (the BarWidgetHost inputs `barConfig`/`popouts`/`panel`/`screen`/`properties`, orientation, configured colors; override `backgroundColor` for states). `components/reusable/BaseWidget.qml` is the common sizing/background wrapper underneath (`crossSize`, `Widget.padding`, `Appearance.borderRadius`, vertical/horizontal orientation via `Bar.vertical`). **Bar widgets are sized by their bar:** the cross axis is `barConfig.widgetSize` (the bar's `extent` minus twice its `inset`, from `Bar.enrichBarConfig`), so a widget can never be thicker than its bar; bar modules set `crossSize: barConfig.widgetSize`. `Widget.height` ("Control height") is only for controls outside the bar (form fields, buttons, card headers).

### Launcher (`surfaces/launcher/`, `LauncherManager`)

`LauncherManager` turns the search text into rows, and the UI only draws them. `LauncherPanel` holds the field, list and hint, with no box of its own. `Launcher.qml` hosts it in a floating `LauncherWindow`, or in an `EdgePopout` when `Launcher.position` is `top`/`bottom` (`LauncherConfig.attached`). Only the host in use is created, through `LazyLoader`s. `reverse` puts the field at the bottom and lays the list out bottom to top. Every provider returns the same row shape: `{ kind, image, glyph, title, usage, subtitle, hint, complete, run(shift) }`. `run` returns true to close, false to stay open (then the rows are rebuilt, keeping the selection), or a string to search for instead. Tab puts `complete` into the field.
- **Routing.** The first character picks the provider: `/` commands, `=` calculator, `>` run, `?` web. Anything else searches apps (scored, plus frecency from `usage` `{id: {count, last}}` in `state/launcher.json`) and windows (`HyprlandManager.windowList`). A calculator row is added when the text is plain math, and a web row goes last. Each provider has a `Launcher` config toggle (`LauncherConfig`).
- **The calculator** runs `qalc` through one debounced Process, and the rows are rebuilt when it answers.
- **Commands** live in `services/LauncherCommands.qml`, a plain list of `{ name, aliases, glyph, description(), usage, needsArg, confirm, available(), status(), options(arg), run(arg, value) }`. A new shell feature gets a command by adding an entry that calls its service. `options` supplies argument completions. `confirm` (destructive session actions) asks for a second Enter.
- **`/config`** sets any setting by dotted path (`/config Appearance.font.size 14`), saving it at once through `SettingsManager.commitValue`, and holds `save` / `restore` for snapshots. It works inside the options contract: each option's title is the whole argument, so matching and Tab work unchanged. It offers `SettingsManager.settingPaths` only: the settings page's fields, minus `x-applyOnSave` ones and anything under `_blockedPrefixes` (`Bars`, `Overlay.views`), so it can never edit bars or overlays. Values are parsed and checked by `SettingsManager.parseValue`, and choices come from `SettingsManager.optionsFor` (shared with `SchemaField`).
- **IPC** is `appLauncher`: `open` / `close` / `toggle` / `search <text>`.
- **Opening a page.** `ShellManager.openOverlayPage(type)` opens the target overlay on a page, taking a view type or a view's name.

### Lockscreen (`Lockscreen.mode`)

`LockManager.lock()` is the one way to lock; lock buttons call it through `ShellManager.sessionAction("lock")`, and idle daemons through the `lockscreen` IPC target:
- **`quickshell`** (default): the built-in locker, `shell/Lockscreen.qml`. A `WlSessionLock` (Wayland `ext-session-lock-v1`, the protocol hyprlock uses) with one `WlSessionLockSurface` per screen showing `surfaces/lockscreen/LockSurface.qml`. While locked the compositor shows only the lock surfaces and sends them all input; if qs dies the session stays locked (Hyprland's fallback; `misc:allow_session_lock_restore` lets a restarted qs take it back). The locked state lives in a `PersistentProperties`, so a QML reload comes back locked. **Only `AuthManager.authenticationSucceeded` (PAM, `login` stack) unlocks**: there is no IPC unlock, and nothing on the surface may run commands.
- **`hyprlock`**: `ThemeManager.generateHyprlockConfig()` writes `$XDG_STATE_HOME/axiom/hyprlock.conf` from `scripts/templates/hyprlock_template.conf` (theme colors, font, wallpaper, blur, translated greeting) on theme/wallpaper/font/language changes and on switching to this mode; lock runs `hyprlock -c` with it. The user's own `hyprlock.conf` is never touched.
- **`none`**: axiom provides no locker and no IPC target (so an idle daemon pointed at axiom can't loop through `loginctl lock-session`); lock buttons run `Lockscreen.lockCommand`.
- **hypridle** for the first two: `lock_cmd = qs -c axiom ipc call lockscreen lock`, `before_sleep_cmd = loginctl lock-session`; for `none`, no axiom references.

### Naming

- **Services** are `*Manager` singletons; non-singleton helper types in `services/` (`ConfigDraft`, `ColumnsEditor`, `ConsumerRegistry`, `WeatherSource`, `ChatRequest`) are named for what they are.
- **Config readers** are named for their schema section, with a `Config` suffix only where the section name is a type (`OSDConfig`, `OverlayConfig`, …). `Paths` holds derived paths.
- **Hosts** say what they host: `BarWidgetHost` (one bar widget), `OverlaySlot` (content in a cell slot), `OverlayPages` / `OverlayView` (the overlay's pages / one view), `BarPopouts` (a bar's popouts).
- **Content** files are named by their overlay module `type` and/or bar `popoutName`; roots are `Card`, `Panel`, `TitledCard` (+ `CardHeader`).
- **Reusable widgets** that stand in for a Qt control are `Styled*` (`StyledText`, `StyledTabBar`, …), which avoids clashes with QtQuick.Controls names; composites are named for what they are (`SquareIconButton`, `IconTextWidget`).
- **Surface windows** get a `Window` suffix when their shell entry has the same concept's name (`shell/PowerMenu` → `PowerMenuWindow`).
- **Root ids** are `root` (the exceptions keep a different id only because the file already uses `root` for a child, or the id is also a keyword or property name).
- **Bar widget and content names can overlap** (`Weather`, `Media`, …: schema types, so config depends on them). No file may see both: `scripts/check_structure.py` errors if a file instantiates a type that two of its visible directories define.
