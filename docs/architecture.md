# Architecture notes

Detailed notes on how each service and surface works, moved out of CLAUDE.md so they are read on demand instead of loaded every session. CLAUDE.md holds the rules; this file holds the mechanics. Keep it current when changing a feature, and trust the code over it where they disagree.

## Services layer (`services/*.qml`)

Every file is `pragma Singleton QtObject` — one global instance per name, imported as `qs.services`. Key ones:
- **ConfigManager** — the source of truth for runtime config. Owns `_config` (parsed `config/user/config.json`) and `_configSchema`, loaded eagerly at creation (the active theme's data belongs to ThemeManager). Load pipeline: parse → `ConfigMigration.migrate` (upgrades old layouts by `version`, writes the result back once, moves API keys to `SecretsManager`) → `SchemaValidation.pruneUnknown` (drops unknown keys with a warning) → `SchemaValidation.applyDefaults` (fills every schema `default`) → validate. Editors create new entries at their definition's defaults with `withDefaults(value, "Bar" | "BarWidget" | "EdgeMenu" | "OverlayView" | "OverlayModule")`. All config writes go through `setTheme()` / `setWallpaper()` / `saveConfig()` / `commit(object)` (draft services: runs prune/defaults/validate, returns false and changes nothing if rejected, so drafts stay dirty), which validate before writing, then `forceReload()`. Never mutate `ConfigManager.config` fields directly from UI code and expect persistence — call the setter functions (or `SettingsManager.setValue(path, value)` from settings UI). The editor services (SettingsManager, BarManager, OverlayManager, EdgeMenuManager, KeybindManager, MonitorManager) each hold a `ConfigDraft` (`services/ConfigDraft.qml`: working copy of one config path, `changed()` after in-place edits, `save()` merges onto the latest config via `commit`). `ConfigManager.previews` (`setPreview(section, value)` / `clearPreview(section)`) holds unsaved edits shown live without being part of `config`, so other saves and disk reloads don't touch them: BarManager previews `Bars` while dirty, and `Bar.bars` reads `previews.Bars ?? config.Bars`.
- **SecretsManager** — chat API keys, never in config.json: the provider's `keyEnv` env var, else the keyring (`secret-tool`, `service axiom provider <id>`; probed once, `keyringAvailable`), else `$XDG_STATE_HOME/axiom/secrets.json` (mode 600). `withKey(provider, cb)` is async (cached per session); `status(provider)` is `env` | `keyring` | `file` | `none` | `unneeded`; `setKey`/`clearKey` write through stdin, never argv. Keys are entered on `views/settings/ChatProvidersCard` (the Chat section's `x-card`, with Test and Fetch models), never through the settings draft.
- **ChatManager** — the chat: `conversation` (`{ id, title, preset, provider, model, messages }`), `conversations` (index, newest first), `send`/`stop`/`regenerate`, presets and models, attachments (clipboard, a region from `ScreenshotManager.pick`, dropped files; base64 per send), saved to `$XDG_STATE_HOME/axiom/chats/` (`<id>.json`, `index.json`, `<id>/` attachments) up to `Chat.keepConversations`. Each reply is a `services/ChatRequest` (curl with its config, key included, on stdin via `-K -`; the body in a `$XDG_RUNTIME_DIR` file; a `SplitParser` feeding SSE lines to `components/methods/ChatProtocol`, which builds requests and parses streams for the `anthropic`, `openai` (any OpenAI-style server) and `gemini` kinds). Streamed text lives in `streamingText`/`streamingThinking`, flushed every 50 ms, and replaces the placeholder message only when the reply ends, so the message list doesn't rebuild per token. Anthropic thinking blocks (with signatures) are sent back only to the model that wrote them. `components/methods/ChatMarkdown` splits replies into prose and code blocks. `content/Chat.qml` is a `Panel` (ready to be a popout). IPC `chat`: `open`, `newChat`, `ask <text>`, `settings`; launcher `@` and `/chat`; `OverlayConfig.pageWithModule(type)` finds the page to open. Created from `shell.qml`'s `_services` (for the IPC target).
- **ThemeManager** — owns the active theme: `currentTheme` (loaded eagerly, watched, reloaded when `Appearance.theme` or the file changes) and `defaults` (`theme-defaults.json`); `Appearance.darkMode` is derived from the theme's `variant`. Also theme discovery: `themeFamilies`, one entry `{ label, dark, light, generated }` per theme, where a dark/light pair (each file's `paired` naming the other) is one theme labelled by the words their names share, and `currentFamily`; `applyFamily(family)` picks the variant for the current mode and `setLightMode(bool)` switches the current theme's variant (the only light/dark switch; `Appearance.darkMode` follows the applied theme). Then generation from a wallpaper (`scripts/generate_theme.py`, one run writing a `generated/wallpaper-<style>-dark|light` pair per `STYLES` entry (`tonal`, `vibrant`, `faithful`, `muted`, `alternate`: factors on the one build, like Material's scheme variants): k-means in OKLab picks candidate colors, the palette is built in OKLCH from targets measured off the hand-made themes, with the wallpaper's seed as `accent` in `base0F`; run through `scripts/venv_python.sh`, which keeps `.venv` in sync with `scripts/requirements.txt`), `setWallpaper` (`Appearance.wallpaperBackend`: `quickshell`, the default, is drawn by `shell/Wallpaper` (one Background-layer `surfaces/wallpaper/WallpaperWindow` per screen, crossfading) straight from config; `awww` runs `setWallpaper.sh`, and Hyprland's `wallpaperDaemon` starts it only then), and `themeIntegrations()` (one `scripts/theme_<key>.sh` per `ThemeIntegrations` switch, hooked into its app by `IntegrationHookupManager` (Themes, below): `integrations` is the schema's boolean keys, with `integrationTitle(key)` and `integrationCommands(key)` (any of which shows the app is installed, for the onboarder); a failure, or a `Warning:` line on stderr, is logged), which run when the active theme's name or contents change, and for one integration as soon as its switch turns on (`_enabledIntegrations` against those of the last full run, `_themed`; nothing until the first full run, so loading the config doesn't run them twice). The choice of theme is persisted through `ConfigManager.setTheme`.
- **ShellManager** — cross-cutting UI signals (power menu, launcher, overlays) that modules connect to rather than calling each other directly, and screen targeting. `General.monitors` is `"primary"` | `"focused"` | `"all"`; the OSD, overlay and launcher have their own `monitors` setting (`"general"` | `"primary"` | `"focused"` | `"all"`, resolved by `modeFor(mode)`; the power menu uses General's). Surfaces are built on `General.screensFor(mode)` (`General.screens` for General's), and only the instance on `targetFor(mode)` (`isTarget(screen, mode)`: the focused monitor in "focused"/"all") answers a shortcut, IPC call or OSD event. In "all" (`everywhere(mode)`, `showsOn(screen, mode)`) the surface opens on every monitor at once: a `reusable/SurfaceGroup` per instance opens and closes the others with it (`ShellManager.surfaceShown`), and since only one `HyprlandFocusGrab` can be active, only the target's instance holds one, over every instance's window (`surfaceWindows`); the launcher's instances share `LauncherManager.text`. The workspace overview is built on every screen and opens on the one under the cursor (`HyprlandManager.withHoveredScreen`, a `hyprctl cursorpos` lookup). Wallpapers are per monitor (`Appearance.wallpapers[monitor]`, set from the overlay's Themes page; the primary monitor's is also `Appearance.wallpaper`, the lockscreen's). IPC handlers are `enabled` on the target instance only, since a target name can have one handler. Surfaces sharing a screen edge give way by rank (`edgeRanks`: dock < OSD < floating edge menu, the menu being opened by hand): an edge OSD and a floating edge menu claim their screen edge while open (`setEdgeClaim(owner, { screen, edge, kind })`, null to release; `edge` a `Bar.edgeName`), and a lower one on that edge closes and stays shut while `edgeOutranked(screen, edge, kind)` (the OSD ignores its pokes and hover strip; the dock is put away, a reserving one keeping its zone). A floating OSD and an integrated menu (whose zone pushes the others inwards) take no part.
- **SystemManager** — CPU/memory/temp/GPU/disk stats. Reference-counted through a `ConsumerRegistry` (shared with UpdatesManager; identical re-registrations are no-ops): consumers call `acquire(owner, {interval, metrics, diskPaths})` / `release(owner)`, and it polls only the union of requested metrics (sysfs/procfs `FileView` reads, no processes on the hot path), stopping entirely with no consumers.
- **UpdatesManager** — pending pacman/AUR updates shared by every Updates widget (same acquire/release pattern). Only one `checkupdates` may run at a time: concurrent runs share its temp db and fail. `upgrade(command, terminal)` runs the upgrade in a terminal (one at a time, `upgrading`) and checks again when it closes.
- **Polled data** (the rule is in CLAUDE.md): besides SystemManager and UpdatesManager, `WeatherManager`, `TailscaleManager` (`available`, `backendState`/`connected`, `tailnetName`, `ip`) and `CommandManager` (`outputs[command]`, shared by identical commands, e.g. a Button's label). `CommandManager.runDetached(command)` runs a widget's click commands, and `run(command, callback, input)` a service's one-off command (callback `(exitCode, stdout, stderr)`; `input` goes to stdin), so services keep no Process of their own. Widgets hold the request in a `readonly property var …Request` built from `properties` and acquire it in `Component.onCompleted` and `on…RequestChanged` (WeatherManager takes no request: its settings are global).
- **NetworkingManager** — Wi-Fi over `Quickshell.Networking` (NetworkManager D-Bus, event-driven): radio (`wifiEnabled`, `setWifiEnabled`), `networks` (connected, saved, then by name; fixed order), connect/disconnect/forget, the password prompt (`passwordFor`, `connectWithPsk`, set again on a `NoSecrets` failure), and the primary connection (`primaryDevice`: wired before Wi-Fi; `netInfo` `{ kind, name, device, signal, ip }`, all bindings, except the IPv4 address, which Quickshell.Networking lacks: one `ip -4 -j addr` whenever the connection changes, or on `refreshIp()`). Nothing runs `nmcli`. The scanner runs only while something holds `acquireScan(owner)`. Not named `Networking` (Quickshell's singleton). Throughput stays in SystemManager.
- **BluetoothManager** — adapter power, scanning, sorted device lists and connect/pair/forget over `Quickshell.Bluetooth`. Not named `Bluetooth`, which would shadow Quickshell's singleton (and the `Bluetooth` bar widget file).
- **NotificationManager** — the DBus notification server plus a persistent history: `entries` (plain objects, newest first, capped at 100) stay until the user removes them (`dismiss(uid)`, `clearAll()`, or the `notifications` IPC target), even when the app withdraws one, and are saved to `$XDG_STATE_HOME/axiom/notifications.json`. `liveNotification(uid)` gives the still-open Notification (for actions), and restored entries open their app instead (`openApp`). `NotificationsConfig` sets the history's size and age (`maxEntries`, `maxAgeDays`) and which user actions remove an entry: `clearOnFocus` (an `activewindow` event whose class matches the entry's desktop entry or app name), `removeOnClick`, `closeRemoves`. Toasts take their entry's uid at creation (`uidOf`), because invoking an action can close the notification. `dnd` (readonly; `setDnd`/`toggleDnd`) is saved in `config/state/notifications.json`. The toasts (`shell/Notifications`) stack once per screen of `NotificationsConfig.monitors` (`showsOn`); a toast the user closes closes on every screen. Images are cached as PNGs in `…/axiom/notifications/`, rendered through an `imageHost` item that `shell/Notifications` lends it (grabbing needs a window). `keepOnReload` keeps live notifications across QML reloads.
- **HyprlandConfigManager**: how axiom sets up Hyprland (`Hyprland` section, `HyprlandConfig` reader). It needs Hyprland's Lua config, 0.55+; axiom's own `hyprctl eval`/dispatch calls are all Lua (`hl.*`, stubs in `/usr/share/hypr/stubs/hl.meta.lua`). One Lua layer covers binds (`binds[]`: an IPC `action` or `exec`, `description` "Axiom: …"), required settings (`allow_session_lock_restore`, a named rule suppressing `maximize` requests, a `workspaces` animation), themed borders, blur and monitor profiles (see MonitorManager). `mode` picks how it gets there:
  - `detached`: `hyprctl eval` at startup and on every `configreloaded`, skipping keys `hyprctl binds -j` shows taken (`components/methods/HyprBinds`: `keyId`, `runtimeBinds`, and `userKeyCounts` for KeybindManager). The keys it bound live in Hyprland's Lua state (`AXIOM_RUNTIME_KEYS`), which a Hyprland reload resets along with the binds and which survives a qs reload. They are unbound before the binds are read.
  - `included`: `moduleLua()` goes to `$XDG_STATE_HOME/axiom/hyprland.lua`, a module the user loads with `includeLines`.
  - `managed`: `managedLua()` becomes `~/.config/hypr/hyprland.lua` itself (plus the `managed` options; `matchAxiom` takes window rounding and border width from `Appearance.shape`, rewriting the file when they change), loading `user/*.lua` after it via `require("user.<name>")`. Hyprland watches required files, so user edits reload it; `user/lib/` is for shared modules. The user's own setup is this: `user/` is a symlink to `~/repos/dotfiles/hypr/user`. `scripts/claim_hyprland.sh` (`check` for `checkManaged()`, `claim` for the takeover) refuses a symlinked or git-tracked dir, and treats a `hyprland.lua` that is Hyprland's example config (`/usr/share/hypr/hyprland.lua`, give or take whitespace; `$AXIOM_HYPR_EXAMPLE` in tests) as `stock`: `claim` only backs it up (`replaced`) instead of adopting it into `user/`, since its binds and `hl.monitor` rule would fight axiom's.
  - The `managed` options become one `hl.config({...})` through `components/methods/HyprLua` (pure), driven by schema annotations: `x-hypr` (the option's dotted path, or a list), `x-hyprScale` (integers shown scaled: 0.01 for a percent), `x-hyprValue` (`int`, `number` for numeric enums, `emptyIsDefault`, `color` for a theme color name, with `x-hyprAlpha`), `x-hyprIf` (a boolean sibling gates it) and `x-hyprAlways`. A field is written only when it differs from its default (Hyprland's own), so a new option is just a schema entry. `managed` stays flat (the settings page nests one level): its cards come from `x-group`/`x-order`. Not mapped: `animationPreset` (`hyprland` writes nothing; `axiom` follows `Appearance.animFast/Normal/Slow` and turns animations off with motion; `snappy`/`bouncy`; `custom` from `curves`/`customAnimations`), written after `axiom.setup()`, plus `env` and `autostart` (after axiom in the start hook) and the cursor.
  - Both file modes write only on change, then `hyprctl reload` (Hyprland doesn't watch `dofile`d files).
  - An `AXIOM_INCLUDED` global tells axiom the file is loaded. When it isn't, the runtime layer stands in and `problem` says why.
  - The settings page's Hyprland category starts with `HyprlandStatusCard`, built from `status` (`runtime` | `loaded` | `fallback` | `pending`) and `problem`. A mode picked there waits for Save (`x-applyOnSave`), and the card outlines what saving will do, predicting a managed takeover with `checkManaged()` (`managedCheck`: `ours` | `adopt` | `new` | `blocked`, a dry run of `claimManaged`).
  - `binds` are edited on the Keybinds page, not in settings (see KeybindManager). An action is an axiom IPC call (`_actions`, including the `audio`/`media` targets on AudioManager/MediaManager, so the OSD shows) or a Hyprland dispatcher bound directly (`_dispatchers`: focus/move/resize, close, fullscreen, floating, pin, special workspaces, mouse drag/resize on a `mouse:272` key, which Hyprland makes a mouse bind by itself; `exitHyprland`; and `terminal`/`fileManager`/`browser`, which exec `Apps.terminalCommand` etc., so the binds follow the `Apps` section's `terminal`/`fileManager`/`browser`, empty being the system default; `mediaStop` etc. on `media`). `screenshot` (argument `region`/`window`/`screen`) goes to **ScreenshotManager** (IPC `screenshot take <kind>` / `cancel`, launcher `/screenshot`, and the Screenshot card), with no grim or slurp (the chat's region attachments use it too, through `pick(path, callback)`, which saves to a path and calls back instead of copying): `shell/Screenshot` shows `surfaces/screenshot/ScreenshotPickerWindow` while `picking` (a frozen `ScreencopyView` frame per screen, `axiom-screenshot` layer rule with `no_anim`; the window under the cursor highlighted from the start (`HyprlandManager.withCursorPos`); `region`: drag a region or click a window, the screen off one; `window`: click a window; cropped through a `ShaderEffectSource` + `grabToImage` at the buffer's resolution; `screen` grabs at once on one screen), saved to `<Pictures>/Screenshots` (or only a runtime file with `copyOnly`, in `config/state/screenshot.json`), copied with wl-copy, then notified (with an "Edit in Satty/Swappy" button: a waiting `notify-send -A`, only the latest one live) or opened in satty/swappy straight away (`annotate`, the picker's "Edit in …" switch / E / Shift on release). One 3 s watchdog in the service fails a capture that gets no frame (a picker reports its frame with `frameArrived()`; an immediate `screen` capture must also report back), so nothing can wedge it. Recording lives there too, not in the card, which the overlay destroys when it closes: `toggleRecording(dir)` opens the same picker with kind `record` (no save/annotate controls; R or its Screenshot / Record switch, `setRecordMode`, flips an open picker between the two), whose pick goes to `record(area, screenName)` (global logical `-g`, or `-o <screen>` for a whole screen) and runs wf-recorder until `stopRecording()` (SIGINT to its own process; `pkill` only for one left from before a reload); the exit notifies the saved file (click opens it) or the failure. Entry points: IPC `screenRecord` (`toggle`/`enable`/`disable`/`status`), the `screenRecord` bind action (with a call), launcher `/record`, the card's Record tile. While it runs, `recordingElapsed` ticks for the `ScreenRecord` bar widget (hidden otherwise; click stops), and the Privacy widget's screen indicator shows it (wf-recorder uses screencopy, so Pipewire never sees it). Binds carry `repeating`/`locked`/`release` flags, preset from `actionFlags` when the action is picked.
  - Created from `shell.qml`'s `_services`, since other services don't reference it. Never switch the user's real config to `managed` to test it: test `claim_hyprland.sh` on scratch dirs (`tests/scripts/test_scripts.py` does), and render the Lua with node and `luac -p`.
- **MonitorManager** — the Monitors page (`views/Monitors.qml`, pieces in `views/monitors/`: `MonitorCanvas`, `MonitorInspector`). `outputs` is `hyprctl monitors all -j`, read at startup and on `monitoradded`/`monitorremoved`/`configreloaded` (never polled). `Hyprland.monitors.profiles` (`x-settings: false`) is a list of `{ name, outputs: [MonitorRule] }`: a layout per set of monitors, each rule's `output` a `desc:<description>` (follows the monitor across ports; the connector name when two share a description, `MonitorLayout.outputId`) with mode, position, scale, transform (0–7: quarter turns, +4 flipped), `disabled`, `mirror` (another rule's `output`), `vrr`, `bitdepth`, `cm`, `sdrBrightness`/`sdrSaturation`. The page edits a `ConfigDraft`; opening it detects (`_detect`: a new profile from the live state when none matches, or the matching one gains any unlisted output), and while it's open a hotplug re-detects unless edited. Tiles snap (`MonitorLayout.snap`: edge to edge, aligned starts/ends/centres, within 14 screen px) but drop anywhere else, so offsets stay possible; the view holds still during a drag. `issues` (overlap and every monitor off block Apply; islands, scales Hyprland will round and, in managed mode, `user/*.lua` files that call `hl.monitor` (`HyprlandConfigManager.monitorConflicts`, whose rules load later and win) warn). **Apply** evals the selected profile's `hl.monitor` calls (`HyprLua.monitorCalls`), snapshots the old state and shows `shell/MonitorPrompt` (`surfaces/monitors/MonitorPromptWindow`, on every screen, outside the overlay whose screen may change): `keep()` saves the draft, `revert()` or 15 s evals the snapshot back. A profile for monitors that aren't connected only saves. Where the profiles reach Hyprland (`HyprLua.monitorsLua`, the same Lua in every mode): `AXIOM_MONITOR_PROFILES` plus `axiom_apply_monitors()`, which picks as `MonitorLayout.matchProfile` does (exact set, where a disabled rule's output may be missing since `hl.get_monitors()` doesn't list it; else the one turning on most; the first profile before any monitor is reported), resets outputs only other profiles mention to Hyprland's defaults, resolves `mirror` to a connector, and runs again on `monitor.added`/`removed` (handlers kept in `AXIOM_MONITOR_SUBS`, removed before re-subscribing). Detached: in the runtime eval, only when the profiles changed or a reload dropped them (`_monitorsApplied`), since re-applying can flicker a modeset; included/managed: `M.monitors()` from `setup()`, so profiles follow hotplugs without qs. `General.primaryMonitor` is set from the inspector at once. IPC `monitors`: `open`, `keep`, `revert`, `identify`; launcher `/monitors`. Never Keep a layout while testing; test the picker through `tests/tst_HyprLua` (`monitors.run.lua`) and harmless evals (re-applying the current settings, or moving a lone monitor's origin and back).
- **KeybindManager** — the Keybinds page: every bind Hyprland reports (`hyprctl binds -j`, grouped by "Section: Label" descriptions), and the editor for axiom's own `Hyprland.binds` (a `ConfigDraft`, saved with `save()`). Per-bind `issues` (no key, bad modifier, missing argument, duplicate, and a key the user's own config binds: Hyprland's binds minus the saved axiom binds it applied, since every Lua bind is an opaque `__lua` dispatcher), `presets` (built from the workspace layout; `applyPreset` skips keys already used) and recording: `startRecording(index)` puts Hyprland in an empty `axiom_record` submap (Hyprland only registers a submap with a bind, so it has an unreachable one, and a Lua timer leaves it after 30 s even if qs dies) so bound combos reach `keybinds/KeyRecorder`; `components/methods/KeyNames` turns the Qt key event into a Hyprland key name. The page's list filters with a search and toggle chips (`query`, `sectionFilter`, `modFilter`, `sourceFilter`, here so they survive the page; `toggleFilter(group, value)`, `clearFilters()`; chips from `sectionOptions`/`modOptions`, built from the binds, not the filtered result) through `components/methods/KeybindFilter` (chips in a group are alternatives; groups and the search all apply). Each row carries `axiom`/`user`: whether any of its binds is one of axiom's applied binds (`_axiomIds`, by `HyprBinds.keyId`, never in a submap) or the user's own. The editor has its own chips (`editSectionFilter`, `editModFilter`, `editIssuesOnly`; `clearEditFilters()`, also on Add bind; options `editSectionOptions`/`editModOptions`) applied in `visibleKey`; any of them on turns off `reorderable`. Both tabs draw their chips with `views/keybinds/FilterChips` (groups of `{ value, label }` options, a `selection` map, `toggled`/`cleared`).
- **SelfUpdateManager**: axiom updating itself (not packages: that's UpdatesManager). `SelfUpdate.channel` picks what it follows on the clone's remote: `tags` (releases, `v*` tags) or `main` (every commit on the remote's main, else master; the notes are the new commits' subjects). `scripts/self_update.sh [--channel tags|main] check|apply <target>` does the git work and prints one JSON object (`channel`, `current`, `commit`, `latest` (the tag, or main's short commit), `state`: `uptodate` | `available` | `diverged`, `ahead`, `behind`, `blocked`: `dirty` | `diverged` | `branch` | `nogit`, `notes`, `error`). It only fast-forwards (`merge --ff-only`, or a detached `checkout` when detached) and never stashes, resets or forces; switching back from `main` to `tags` is never a downgrade (ahead of the newest tag is `uptodate`). A channel change rechecks. `SelfUpdate.mode`: `auto` applies, notifies and `Quickshell.reload`s (git replaces files by inode, which the watcher misses); `notify` sends a notification whose `desktopEntry` (`axiom-update`) is a `NotificationManager.registerHandler` key, so clicking it runs `openSettings()` (Settings → Updates, the `SelfUpdateStatusCard`); `off` never checks. Checks run once per qs launch (a `PersistentProperties` flag, so hot reloads don't recheck) and daily. `config/state/selfupdate.json` keeps `lastChecked`, `notifiedTag` (each release is notified once) and the last result. IPC `selfUpdate`: `check`, `update`, `open`; launcher `/update`. Created from `shell.qml`'s `_services`. Test the script on scratch clones; never `apply` on the live repo.
- **BrightnessManager** — brightness per monitor (`displays[screenName]`: `backlight` for an `eDP`/`LVDS`/`DSI` screen, from `/sys/class/backlight` and written with `brightnessctl`; `ddc` for monitors `ddcutil detect` maps to a DRM connector, VCP 0x10). Detected at startup and on screen changes, read then and when the OSD opens (`refresh`), never polled. `set`/`stepBy` update at once and coalesce writes per monitor (one process in flight, latest value next). `brightnessChanged(name)` fires only for axiom's own sets, so the OSD opens on them. IPC `brightness`: `up`, `down`, `set <percent>` on the focused monitor (bind actions `brightnessUp`/`brightnessDown`). Created from `shell.qml`'s `_services`.
- **NotesManager**: notes are Markdown files in `NotesConfig.directory` (`Notes.directory`; empty is `config/state/notes/`, gitignored, and a linked folder is never created). Paths are relative to it and `clean()` refuses any that leave it. `acquire(path)` returns a shared, counted document (`text`, `edit(text)` saving 600 ms later, `flush()`), so modules on one note stay in sync; `release(path)` flushes. A change on disk reloads a document unless it has edits waiting, which win. `createNote`/`createFolder`/`rename`/`trash` (`gio trash`, else `rm` behind a confirm) run argv processes and emit `moved`/`removed` for the modules showing them; `allNotes` (a `find`) feeds the `notes` `x-options`. At startup it moves pre-v17 `config/state/note-<name>.json` files to `<name>.md` (keeping `*.json.migrated`). `content/Notes` edits through `parts/notes/NoteEditor`: blocks from `methods/NoteMarkdown` (lossless: `serialize(parse(t)) === t`, and edits touch only their lines), a paragraph (split at blank lines, which stay with the paragraph above; a code fence is never split) or a task line with a checkbox, modelled by count and re-read in place on structural edits (Enter, Backspace/Delete across blocks, toggles, the toolbar, a typed `- [ ] ` or text after a blank line: `needsReparse`), never per keystroke. Every structural edit re-parses (`_normalize`), so blocks are always what `parse()` gives. A `NoteBlock` shows its Markdown rendered (`Text.MarkdownText`) unless it's focused or holds the find match; its clickables are `MouseArea`s, which accept the press so the editor's background `MouseArea` (focusing the note's end) never sees it: inside a `Flickable` an exclusive-grab `TapHandler` is cancelled and a passive one lets the press through. `NoteBrowser` walks the folder with a `FolderListModel`, and its search field lists `NotesManager.search(query, cb)` results (name matches, then `grep -F` lines, 0-based). Ctrl+F finds in the note (`NoteEditor.find`/`endFind`). Launcher `/notes` searches too and opens a result through `requestOpen(path, line, place)`: the overlay page with a Notes module, else an edge menu with one; the module whose `placeKey` matches shows it (`openRequested`, or `takeReveal` when it loads within 5 s). The last note per place (`overlay`, `edgeMenu:<id>`) is in `config/state/notes-modules.json`; `lockNote` pins a module to its `note`. Created from `shell.qml`'s `_services`.
- **OnboardingManager**: the first-run onboarder (`shell/Onboarding` → `surfaces/onboarding/OnboardingWindow`, pages in `onboarding/pages/`). It opens when there was no config.json (`ConfigManager.firstRun`, set by `_existsCheck`), and after a restart until finished or skipped (`config/state/onboarding.json`: `{ completedVersion, step }`; a config with no state file is never prompted; bump `version` for a page worth showing existing users). The step and the chosen Hyprland mode live in a `PersistentProperties`. The window is a `hosts/overlay/ReservedAreaWindow` like the overlay's, with the same `OverlayGrid` (so the Welcome page's `Overlay.size` shows on it), and the step bar is the overlay's `OverlayPageNavigator`. The Hyprland page reads `configState` (`none` | `stock` | `custom` | `ours` | `blocked` | `legacy`, from `checkManaged()` plus a `hyprland.conf` check) and recommends `managed` for a stock or missing config, `included` otherwise. It reuses the Monitors view, `WallpaperPicker` and `ThemePicker` as they are; the Look page's folder check, create and open are `WallpaperManager.checkFolder()` / `folderImages` / `createFolder()` / `openFolder()`. `DependencyManager.check(commands)` / `found` / `tools` say what's installed. IPC `onboarding`: `open`, `close`, `reset` (opens at the next start), `goTo <step>`; launcher `/welcome`; Settings → General's `OnboardingCard`. Test it with `ipc call onboarding goTo <n>` and grim screenshots, never by deleting the real config.json.
- **HypridleManager**: hypridle run by axiom (`Idle` section, `Idle` reader; off by default, the onboarder's Integrations page recommends it). While `Idle.enabled` it renders `components/methods/HypridleConf` (pure: a general block, then dim/lock/screen-off/suspend listeners in timeout order, 0 being off, then the user's `listeners`) to `$XDG_STATE_HOME/axiom/hypridle.conf`, writing only on change, and runs `hypridle -c` on it, stopping any other hypridle (hypridle doesn't watch its config, so a change restarts it). Turned off it stops its own and starts a plain `hypridle` again when `~/.config/hypr/hypridle.conf` exists; the user's file is never touched. Nothing is polled: `pgrep` on each apply and once 15 s after startup (`replacedOther` when a second hypridle turns up beside ours). Locks through `lockscreen lock` (in `none` mode `Lockscreen.lockCommand`, unless it's `loginctl lock-session`), dims through `brightness dim <percent>`/`undim` (every monitor, silent, so no OSD), DPMS through `hl.dsp.dpms({ action = … })`. Managed mode's autostart skips a plain `hypridle` entry while it's on. Settings → Idle starts with `IdleStatusCard`. Created from `shell.qml`'s `_services`. Ask before enabling it on the live config: it replaces the user's running hypridle.
- **ClipboardManager**: the launcher's clipboard history (`:` or `/clipboard`; `Launcher.clipboard`, on by default, also on the onboarder's Integrations page; turning it off clears it). `Launcher.clipboardSource` `axiom`: a `wl-paste --type text --watch` process records text clips while it's on, split at ASCII RS, skipping any whose `CLIPBOARD_STATE` isn't `data` (a password manager's `sensitive`), de-duplicated and capped at `clipboardMaxEntries`, in memory only (a `PersistentProperties` holding JSON, since a JS array can't cross into the reloaded engine; never on disk). `cliphist`: `cliphist list` on each `:` query (at most once a second; an unchanged list changes nothing, or the rows would loop), while axiom runs `wl-paste --type text|image --watch cliphist store` itself (cliphist drops duplicates, so a user's own watcher is harmless; text-only misses screenshots and keeps only a browser image copy's HTML). The newest 50 images are decoded as thumbnails into `$XDG_RUNTIME_DIR/axiom/clipboard/` (pruned to the listed ones, removed when off) and copied back with `wl-copy --type image/<format>`; HTML that is just an `<img>` is decoded for its `src` (the listed preview is cut at 100 chars) and previewed from it. No listing runs while a `cliphist delete` is in flight, or it would bring the entry back. Launcher row text is `Text.PlainText`, since clips can hold markup. `copy` pipes the text to `wl-copy` on stdin (cliphist: `cliphist decode <id> | wl-copy`), never argv, as `copyText(text)` does for every other text copy in axiom; Shift+Enter on a row `remove`s it. Created from `shell.qml`'s `_services`.
- **EmojiManager**: the launcher's emoji (`;` or `/emoji`; `Launcher.emoji`, on by default). `entries()` reads `config/json/emoji.json` on first use: `[{ e, n: name, g: group, k: [keywords] }]`, fully-qualified emoji without skin tones in Unicode's order, generated by `scripts/generate_emoji.py` (stdlib; downloads emoji-test.txt and CLDR's English annotations) and committed, so nothing downloads at runtime. LauncherManager scores them (name, then keywords and group only on a real match, plus frecency from `usage`, in `config/state/emoji.json`). A bind opens it with the `launcherSearch` action and argument `;`.
- **WallpaperManager**: what changes the look on its own. `Appearance.wallpaperMode`: `fixed`; `rotate` (`wallpaperRotation`: `interval` minutes, `random`/`sequential` via `methods/Schedules.nextWallpaper`, `sameOnAll`; the last change time is a `PersistentProperties`, checked every 30 s; IPC `wallpaper next`, bind `nextWallpaper`, launcher `/nextwallpaper`); `variant` (`variantWallpapers.dark`/`light` on every monitor, following `Appearance.darkMode`). Automatic changes regenerate only while a generated theme is active; picks by hand (`pick(url, monitor, variant)`, from `WallpaperPicker`) always do. Batch writes go through `ThemeManager.setWallpapers(map)` → `ConfigManager.setWallpapers` (one save). Also `Appearance.themeSchedule` (light from `lightAt`, dark from `darkAt`), through a `services/DailySchedule`: it fires `due(inWindow)` only on edges (window opens/closes, turned on, times moved across now), so a switch by hand lasts until the next edge; its last state survives reloads. The Themes page edits all of it inline (`WallpaperPicker`'s Fixed/Rotate/Light-Dark switch, `ThemePicker`'s Auto) through `forms/SettingRows` (dotted-path `SchemaField` rows saved by `SettingsManager.commitValues`). Created from `shell.qml`'s `_services`.
- **NightLightManager**: the night light (`NightLight` section, `NightLight` reader, `views/settings/NightLightStatus` as its `x-intro`): `hyprsunset -t <K> [-g <gamma>]`, or wlsunset pinned to one temperature, started detached and stopped with `pkill`; `active` is a `PersistentProperties` (probed with `pgrep` once per launch, `_probeOnce`, however the tool becomes known; the schedule waits for it). A `DailySchedule` turns it on at `startAt` and off at `endAt`; a new temperature/gamma restarts it while on. IPC `nightLight` (`toggle`/`enable`/`disable`/`status`), bind `nightLight`, launcher `/nightlight`, the QuickActions tile. Created from `shell.qml`'s `_services`.
- **DockManager**: the docks (`Dock` section, `DockConfig` reader; `enabled` off by default; `docks` is `[DockEntry]`, edited on `views/settings/DockListCard`, the section's `x-card` in its own `Dock` settings category). `shell/Dock` builds one `surfaces/dock/DockWindow` per enabled dock per screen (`DockConfig.screensOf`: its `monitor`, `"*"` for all). `itemsFor(dock, screen)` groups `HyprlandManager.windowList` by app (`appKey`: `DesktopEntries.heuristicLookup(class)`, else the class) through `methods/DockLayout` (pure: `buildItems` (pinned first, then running with `showRunning`), `inScope` (`windowScope`: `all` | `monitor` | `workspace`), `clickTarget` (focus the most recent, cycle when one is focused), `magnifiedSizes`, `covered`); delegates are keyed by the joined keys. Pinning from the dock (right-click `DockMenu`, dragging icons; off the dock unpins) saves at once through `SettingsManager.commitValues`. `DockWindow` is an Overlay-layer `axiom-dock` strip (arranged after the Top-layer border and bars, and by its layer rule's `order = -1` after floating bars: it sits inside them and never shortens the bars on other edges; blurred; hidden under fullscreen; put away while the overlay is open on its screen, unless it reserves its strip, or while an edge OSD or floating edge menu outranks it on its edge (`away`, see ShellManager's edge claims), a reserving one keeping its zone) as deep as the magnified icons, masked to the box. At `edgeDistance` 0 the box is an `AttachedSurface` joining the border's or a solid bar's stroke (`-borderWidth` edge margin, as EdgePopout), straight off a bare edge, and a plain box beside a transparent/pill bar; `visibility`: `always` (`reserveSpace` sets its zone), `hover` (an `EdgeTrigger`) or `intellihide` (hover, plus shown while no window on the monitor's workspace covers it: `obscured`, placed from the monitor's `reserved` via `lastIpcObject`). A dock reports what it reserves (`setZone`/`zoneOn`, per screen edge), and what would otherwise be pushed in by it reaches past it: `EdgePopout` (the OSD, floating edge menus: on its own edge and at both ends; its `axiom-edge-popout` layer rule `order = -2`, and the OSD's `axiom-osd` (`overNamespace`) `order = -4`, draw it over the dock and the OSD over the overlay; the edge popouts' `order = -5` draws floating edge menus over the overlay and the OSD too) and the border's corner pieces (`RoundedBorders.cornerMargin`). IPC `dock`: `open`/`close`/`toggle <id>` (empty: every dock; not `show`, which qs's CLI takes), bind action `dock`.
- **IdleInhibitManager** — shared caffeine state (a `PersistentProperties`, so it survives QML reloads but not restarts) + `idleInhibit` IPC target; the Wayland inhibitor itself lives in `shell/IdleInhibit.qml`, which maps a 1 px click-through Background-layer window on the primary monitor while it's on (it needs a surface), so it works without the bar widget.

## Config layer (`config/*.qml`)

Also `pragma Singleton`, but these are typed config *readers*, not owners — one per config section, exposing `readonly property` values from `ConfigManager.config`. No `??` fallbacks: the schema defaults are already filled in. Readers: `General` (displayName, primaryMonitor, `monitors`/`screens`, `screensNamed(name)`: that screen, else the primary, else the first), `Idle` (hypridle, see HypridleManager), `Appearance` (theme, font, shape, motion tokens), `Widget`, `Bar` (from `Bars`; the first bar is primary; `edgeName(location)` gives a `Bar.Location` as `"top"`…`"right"`), `PopoutConfig` (open/dismiss delays, edge trigger size — shared by bar and edge popouts), `OSDConfig` (the OSDs: shared scroll settings plus `osds`, `definitions/OSDEntry` each with its own `monitors`, `placement` (`edge`: an `EdgePopout` at `edge`/`position`; `floating`: a `FloatingPopout` with its centre `x`% across and `y`% up the work area), orientation, timeout and `bars`, each typed `master` | `other` | `microphone` | `brightness` | `app`, drawn by `surfaces/osd/OSDBar` in `OSDContent`; a change opens every OSD holding that bar (`OSDTriggers`), and Other apps skips the App bars of every OSD. Edited on the section's `x-card` `views/settings/OSDListCard` (tabs, a placement picker with presets, Show through `ShellManager.showOsd(id)`); the App field's chips come from `x-suggestions: "audioApps"`, `SettingsManager.suggestionsFor`), `LauncherConfig` (launcher placement, size and providers), `Apps` (the terminal, file manager and browser that binds and the launcher open), `NotificationsConfig` (the toasts' corner and gaps, measured inside the work area by an Overlay-layer anchor window with Normal exclusion, like `OverlayPanel`), `OverlayConfig` (views + card-grid constants), `EdgeMenusConfig` (edge menus), `IconConfig`, `ChatConfig`, `ThemeIntegrations`, plus `Paths` (derived filesystem paths from `$HOME` / `Quickshell.shellDir`, not configurable) and `Theme`. Readers whose section name collides with a type get a `Config` suffix (`Popouts`, `Overlay`, `Icons`, `OSD`, `Launcher`, `Notifications`). UI code should read colors/settings from these (`Theme.background`, `Widget.padding`, `Bar.bars`) rather than reaching into `ConfigManager.config` directly.

`config/Theme.qml` exposes the base16 palette (`base00`-`base0F`) plus semantic aliases (`background`, `accent`, `error`, etc.) resolved through `_themeData.semantic`, and a `stringToColorMap` + `resolveColor(name)` for dynamic color lookup by string (used when a color name comes from JSON/config rather than a static binding).

## Schema and the settings page (`config/json/config.schema.json`)

The schema is the single source of truth: shape, `default`s (there is no separate defaults file), and the generated settings page (`views/Settings.qml`). Adding a setting = a schema entry with a default + a reader property; changing the layout of existing config = bump `version` + a `ConfigMigration` step. The live file is `config/user/config.json` (gitignored, UI-owned). A schema reaches QML as a map, whose keys come out sorted, so order always comes from `x-order`.

**Annotations** (the settings page, forms and editors read them; add one rather than a list in QML):
- Placement: `x-settings: false` hides a key; `x-category` on a top-level section names its sidebar category, and the root's `x-categories` (`[{ name, icon, page }]`) orders the categories and gives their icons (`SchemaLayout.categories`; one left out comes last, with a generic icon); a category's `page` is a hand-built part shown after its cards (`views/settings/<page>.qml`: Maintenance's `SavedConfigsSection`), so a category can have no sections; `x-links` lists page types it links to (`Themes`, `Layouts`, or a view type; the link buttons take the page's label and icon from `OverlayConfig.viewLabel`/`viewIcon`); `x-order` on an object lists the keys shown first (its form's, or its settings cards', whose order is their first field's); `x-group` puts a field on a card of that name (one section or object can make several cards). The bar and edge menu editors group a `Bar`'s / `EdgeMenu`'s own fields the same way (`SchemaLayout.objectGroups`, as `Bar.fieldGroups` / `EdgeMenusConfig.fieldGroups`).
- Hand-built parts: a section's `x-card: "<Name>"` adds `views/settings/<Name>Card.qml` as its first card (with `x-cardFolds: true` it folds like the generated cards and joins Fold all, getting its group key `<Section>:<Name>` as `foldKey`); `x-intro: "<Name>"` puts `views/settings/<Name>.qml` at the top of the section's own card, above its fields (NightLight's `NightLightStatus`).
- Behaviour: `x-showIf` hides a field unless a sibling has a given value (a key starting with `/` is a dotted path from the config root, e.g. `"/Workspaces.layout"`, read through `SettingsManager.configValueAt`; `SchemaField` evaluates it, so it works in every form; on a nested object it hides that object's cards); `x-beside: true` puts a field beside the one before it on its settings card, each half wide (`SettingsGroupCard`'s two-column grid; Workspaces' rows beside columns; give the pair the same `x-showIf`); `x-applyOnSave` keeps a setting in the draft until Save instead of applying it live (Hyprland's `mode`, which can take over files).
- Controls: `x-options: "colors"` (a picker over `base00`–`base0F`; read with `Theme.resolveColor`, which also takes semantic names and hex), `"screens"` (a monitor; empty is the primary monitor, resolved by `General.screensNamed`: bars in `Bar.expandBars`, docks, edge menus; `x-emptyLabel` renames empty where it means something else, as in `General.primaryMonitor` itself; `x-allScreens` adds All monitors, `"*"`), `"languages"`, `"edgeMenus"`, `"overlayPages"`, `"notes"`; `x-suggestions` (chips under a text field, `SettingsManager.suggestionsFor`); `x-multiline: true` (a growing text area); integers render through `forms/SchemaNumberField` (a slider with a value box for 7–200 steps, else a stepper, ±10 buttons past 20 steps; steppers commit debounced, sliders on release), with `x-unit` (`px`, `%`, `ms`, …) after the value and `x-control: "slider" | "stepper"` overriding the choice; `x-auto: { value, start }` puts a switch in front of an integer whose `value` means automatic (on stores `start`, then the number shows: an edge menu's `padding`, `triggerLength`). `x-control: "readonly"` shows a string with a copy button instead of a field (an edge menu's `id`).
- Types: `x-icon` (a Material Symbols name) on bar widget, overlay module and view definitions; on overlay modules `x-defaultSize` (`[w, h]` in grid units: the size it's added at), `x-hosts` (`overlay`, `edgeMenu`, `lockscreen`; the first two when left out, so the lock screen only takes modules that list it) and `x-required` (part of every grid on its hosts: never removed, duplicated or in the library; the lock screen's `Password`); `x-tool: true` on the hand-built view types (the navigator's tool group); `x-hypr*` on Hyprland options (see HyprlandConfigManager).

**The settings page:** `methods/SchemaLayout` turns the schema into categories → groups → rows; only this page builds its own rows, and flat objects (array items, widget/module options, a bar's fields) render through `forms/SchemaPropertiesForm`. An `array` of objects renders as an add/remove/reorder list (`SchemaObjectArray`, items `SchemaArrayItem`). Generated cards are `settings/SettingsGroupCard`; the Dock and OSD list cards are `EntryListCard`s (entries as tabs, a screen picker with presets, Show/Duplicate/Delete, the entry's form; `entryContent` for extras such as the dock's pinned apps); both sit on `FoldingCard` (fold header with section line, heading, unsaved dot, chevron and `headerExtras`, animated body). Status cards (Hyprland, Idle, self-update, chat providers, onboarding) are `FieldGroup`s with a `StatusChip` in `headerExtras`. Clicking a card's header folds it (`SettingsManager.collapsed`, by group key, saved to `config/state/settings.json`; search results never fold). The masonry reads `layoutFolds`, a snapshot taken on category/search change and page unload, so a fold doesn't reshuffle the page. The sidebar (`SettingsSidebar`: a `TitledCard` of `ListEntryRow`s, search in its header) lists the selected category's shown cards (`SettingsContent.shownGroups`, one per title) under its row; clicking one calls `SettingsManager.jumpTo(key)`, which unfolds the card and emits `jumpRequested`, and the content scrolls to it (`TitledCard.scrollTo`, after the unfold animation) and outlines it in the accent for a moment. Search results are grouped by category (`blocks`: a heading with the category's icon, then its own two columns). Other services open the page on a section's category with `SettingsManager.openSection(key)`, so they don't depend on category names.

**Themes:** `config/themes/*.json` (static) and `config/themes/generated/*.json` (from a wallpaper). Static themes keep the hue slots fixed (`base08` red, `09` orange, `0A` yellow, `0B` green, `0C` cyan, `0D` blue, `0E` magenta), even where an upstream base16 port reorders them, because the semantic names and the terminal ANSI colors read them by slot. A scheme without some hue fills that slot with its nearest color (Rosé Pine's pine as green, Dracula's purple as blue), and each scheme sets `accent` to its signature color. An extra dark variant points `paired` at its family's light theme, and the light theme points back at the main dark one. `config/json/theme-defaults.json` is the one fallback palette and semantic → base16 map (dark and light), read (through `ThemeManager.defaults`) by `Theme` for keys a theme omits and for a missing theme, and by `scripts/generate_theme.py`. The `scripts/theme_*.sh` integrations share `scripts/lib/theme_env.sh`: dependency checks; `load_theme` (one jq pass filling what a theme leaves out, as `Theme` does); `export_theme_colors` (every semantic color as `UPPER_SNAKE`, plus `ANSI_0`–`ANSI_15`); `render_template`/`write_atomic`. Each writes only its own `axiom.*` file (under `$XDG_CONFIG_HOME`, as the apps read it). A missing main config may be created with the hookup (cava's config, GTK's `gtk.css`); one that exists is never touched by a script.

**Hookup** (loading that file from the app's config): each switch's `x-hookup` lists targets, `{ file, text, place, … }` that Apply can do or `{ text, where }` to copy (wezterm.lua, k9s's YAML, VS Code's settings.json), and `x-hookupNote` says what's peculiar (Alacritty's import order, lazygit's `LG_CONFIG_FILE`, Neovim). `scripts/integration_hookup.py status|apply <key>` (stdlib Python) does the work: `place` is `end` (read last, so it wins), `start` (CSS `@import` must come first), `top` (before the first `[section]`: TOML top-level keys, foot's main section), `section` (inside `[section]`, added when missing), `shellrc` (`$SHELL`'s rc; fish gets `conf.d/axiom.fish` with `set -gx`) or `copy` (Neovim's module, never overwriting); a line already setting the same key is commented out (`replace: comment`, the default), left beside it (`keep`) or blocks the target (`conflict`); `accept` is a regex for an equivalent line that already counts as done; `requires` skips a target without its command. Apply backs each changed file up beside the real file (`<name>.axiom-bak-<time>`), follows a symlink and keeps it (so a dotfiles repo's file is edited), writes atomically, never deletes a line, and does nothing for a target already done. `IntegrationHookupManager` runs it (`check(key)` → `status[key]`, `apply(key)` → `results[key]`, then checks again; nothing polled), and `forms/IntegrationHookup` shows it under a switched-on integration: the status, per target the text with a copy button and an outline of what Apply will do (backup, link, where it goes, lines commented out), then Apply. `SettingsField` adds it under any field with `x-hookup`; the onboarder's Integrations page lists the switched-on ones under "Finish setting up". Only Apply, on the user's click, edits a user's config.

**Neovim** has no line to add: colorschemes come from plugins, often loaded lazily after init.lua, so `theme_nvim.sh` writes `$XDG_STATE_HOME/axiom/nvim-theme.json` and calls `require("axiom_theme").reload()` in each running instance. `scripts/templates/nvim/axiom_theme.lua` is that module (copied into the user's config by Apply): its `M.map` maps every shipped theme's file stem to that theme's usual colorscheme plugin, `setup({ map, fallback })` merges the user's entries over it, and any other theme (or one whose plugin lazy.nvim doesn't know) is built from its base16 palette (mini.base16 when installed, else plain highlight groups), then given the theme's accent, Material-style (`apply_accents`: keywords, titles, the cursor line number, and selection/search/menu backgrounds blended from it), so a wallpaper theme's seed color leads. The JSON carries `colors` (base16), `semantic` (resolved hex) and `text` (accent and accentAlt floored to readable contrast against the background).

A new integration is a script, a schema boolean with its `x-hookup`, a reader property and an entry in `ThemeManager._integrations`. `tests/scripts/test_scripts.py` renders every theme through every script and parses each output as its format, and runs every hookup on empty configs.

## Translation (`config/I18n.qml`)

`General.language` picks the language. English is the source language: user-visible text is written in English, inline, as `I18n.tr("Text")`.
- **Dynamic values** use placeholders, so the whole sentence stays one key: `I18n.tr("{0} updates", count)`. Don't build sentences with template strings.
- **Dates and times** go through `I18n.formatDate(date, format)`, never `Qt.formatDateTime`, so day and month names follow the language. Named formats come from `I18n.dateFormat("longDate" | "mediumDate" | "shortDate" | "monthYear" | "fullDate" | "dateTime" | "time24" | "time12")`.
- **The schema form translates itself.** The generic `Schema*` form widgets translate their own `label`/`title`/`description` and dropdown option labels. Callers pass English, and schema titles and descriptions need no code.
- **Adding a language** means adding `config/i18n/<code>.json`: `{"_meta": {"name", "locale", "formats"}, "strings": {english: translation}}`. It then appears in the language dropdown (`x-options: "languages"`).
- **Missing entries fall back to English.** The active dictionary reloads live when edited.
- **Checking coverage.** Run `scripts/check_i18n.py` after changing text; it lists missing and unused entries (`--fill` adds the missing ones empty, `--untranslated` finds UI literals not wrapped in `tr()`).
  - Keys only chosen at runtime (e.g. `I18n.tr(form.shape)`) must be declared in a comment next to the call, as `I18n.tr("square") ...`, so the checker sees them.
- **Leave developer-facing strings in English:** logs, validation errors, migration notes.

## Bar / widget composition pattern

`shell/Bar.qml` renders one `BarPanel` per entry in `Bar.bars` (a `Variants`/model), so multi-monitor / multi-panel bars are data-driven from config, not hardcoded. Each module's options live under its `<Type>Widget.properties.properties` definition in the schema. `SchemaValidation` picks the `BarWidget` oneOf option by `type`, so widget properties get their defaults filled like the rest of the config and modules read `properties.<key>` directly. Widget types come from `Bar.availableWidgetTypes` (the `BarWidget` oneOf: label from the type's description, icon from its `x-icon`). `WidgetGroup` models its widgets by count, so live option edits reach a widget in place instead of rebuilding the section. The main-axis layout math (sections placed along the bar, the widgets hidden when it overflows, elastic widgets squeezed within a section) is pure, in `methods/BarLayout` (tested in `tst_BarLayout`); `BarContainer` and `WidgetGroup` only feed it measurements. Bar contents are built from `components/bar/{BarContainer,BarWidgetHost,WidgetGroup,BarPanel}.qml` composing widgets from `components/bar/widgets/<type>.qml` (Time, Battery, Network, Workspaces, Media, SystemTray, Notifications, etc.). A widget opens a popout by dropping in a `PopoutAnchor` with a `popoutName`; the per-bar `BarPopouts` (in `hosts/popout/`) loads `content/<popoutName>.qml` by URL, so a new popout is a content file plus an anchor.

**Bar widgets.** Icon + label widgets extend `bar/widgets/BarIconWidget.qml` (the `BarWidgetHost` inputs `barConfig`/`popouts`/`panel`/`screen`/`properties`, orientation, configured colors; override `backgroundColor` for states; `hidden` collapses one with nothing to show). It owns their pointer handling: `clickable` + `acceptedButtons` → `clicked(button)` (dimmed while pressed, off while hidden), `scrollable` → `scrolled(steps)`, `hovered` (what an edge menu a Button opened stays open for) and `dim` for fades of their own. Volume and Microphone share `AudioLevelWidget`. Widgets that draw their own content extend `bar/widgets/BarWidget.qml` (the same inputs and `isVertical`); `reusable/BaseWidget` is the sizing/background wrapper under both. Sizes come from the bar (CLAUDE.md): `Bar.enrichBarConfig` derives `extent` from `widgetSize` plus padding and whatever covers the bar, and resolves `fontSize`/`radius` from the bar's `overrideFontSize`/`overrideRadius`, else Appearance's and `Widget.radius`. A bar whose `monitor` is `"*"` is expanded by `Bar.expandBars` into one entry per screen (id `<id>@<screen>`, `sourceId`), the primary monitor's first; any other bar's monitor is resolved to a connected screen there.

**Icons** are Material Symbols names (`ttf-material-symbols-variable`, fonts.google.com/icons) drawn by `reusable/StyledIcon` in `Appearance.iconFamily`; it draws anything that isn't a name (a glyph or text typed into an icon field) in the text font. Services, schema defaults (`x-icon`, icon fields) and launcher `glyph`s hold names. `DependencyManager` warns once when the font is missing.

## Workspaces (`Workspaces` section, `WorkspacesConfig`)

One layout serves everything that shows or moves between workspaces: the `Workspaces` bar widget, its `WorkspaceGrid` popout, the workspace overview (`surfaces/workspaces/`), the `WorkspacesMap` module, the launcher's `/ws` and the `workspaces` IPC target.
- **Layouts.** `standard` is ids 1..`count`, shared by every monitor. `perMonitor` gives each monitor its own block of `count` ids and `grid` one of `columns × rows`, numbered in a stable monitor order (`WorkspaceGeometry.orderMonitors`: the primary first, then by output identity; `WorkspacesConfig.baseFor(index)`). Nothing else holds a workspace count or grid size.
- **Ids.** `HyprlandManager.workspaceBase(monitor)` / `workspaceIds(monitor)` give a monitor's ids. The overview lays them out `boardColumns × boardRows`; in the standard layout it shows windows from every monitor, each placed against its own monitor's origin.
- **Navigation.** Everything goes through `HyprlandManager.goToWorkspace(id, mode, monitor)`, `stepWorkspace(direction, mode)` and `nthWorkspace(n, mode)`, including focusing a window on another workspace (`focusWindow`, used by the overview, dock, launcher and notifications), so every switch slides the same way. Surfaces on a monitor pass their `monitor` (focused first; in a grid an id outside the focused monitor's block is otherwise refused). Never dispatch `hl.dsp.focus({ workspace })` or `{ window }` directly. `mode` is `go`, `move` or `moveSilent`. In a grid it only reaches the monitor's own ids, going sideways, then vertically, a slide along each axis in turn (`animate`; each leg of a two-leg trip at `_legSpeed` of the configured time). The slide briefly overrides Hyprland's `workspaces` animation (read with `hyprctl animations` at startup and on config reload) and puts it back. Keybinds call `qs -c axiom ipc call workspaces …` instead of scripts of their own.
- **Layout changes.** Hyprland's workspaces stay where they are when the layout or size changes, so `HyprlandManager` remaps them (`_remapWorkspaces`, 200 ms after `perMonitorBlocks`/`size` change, from the layout it last applied): `WorkspaceGeometry.remapWorkspaces` (pure, tested) sends each workspace's windows to the same place in its own monitor's new ids (the first in monitor order keeps a contested id, the rest take free ones, merging only when none is free) and picks each monitor's new active workspace. One Lua chunk does it with the `workspaces` animation off: windows to `name:axiom-remap-<id>` (created on their own monitor, so a chain like 10 → 11, 11 → 12 can't merge), every monitor to `name:axiom-remap-mon-<i>` (so its old, maybe empty, workspace is gone before its id is reused), windows to their ids, then monitors to theirs, the focused one last. IPC `workspaces reconcile` runs it for the current layout, re-homing workspaces left outside their monitor's ids.
- **The bar widget.** `bar/widgets/Workspaces.qml` loads `workspaces/WorkspaceStrip` (standard) or `workspaces/WorkspaceGridStrip` (the active row, or column on a vertical bar) by layout. Their options share one schema definition: layout-only options hide themselves with `x-showIf: { "/Workspaces.layout": … }`. In a grid the widget hands its `properties` to the `WorkspaceGrid` popout, which uses the same colors, labels (grid position), app icons and click to switch as the strip.

## Content (loaded by name, shown by hosts)

`components/content/<Name>.qml` holds every loadable panel. The name is the overlay module `type` (`OverlayModule.oneOf`) and/or a bar `popoutName`; one file can be both (AudioMixer, BluetoothDevices, Notifications, NowPlaying, SystemGraphs, Updates, WifiNetworks). Hosts load it by URL and pass their context:
- **Roots.** `Card` (`content/base/`) is a free-form card (box, `properties`, slot context); card-only content uses it. `Panel` lays its children out in a column and works in either host: in a bar popout it sizes to its content with the popout box (`wrapper` set, `hovered` read for dismissal); in a card the host passes `embedded: true`, it fills the slot with the card box, and `compactContent` (e.g. a `CompactFigure`) replaces the column when `compact` (see Writing overlay modules); a `Card`'s `compactContent` likewise replaces its children (they go into an inner item that hides). A popout with a text field sets `wantsKeyboardFocus` (BarPopouts then takes a focus grab and the bar takes keyboard focus on demand; a click outside emits `focusLost`). Both expose `properties`, `slotRect`, `cols`/`rows`, `shape`, `compact`, `pad` and `innerWidth`/`innerHeight` (the room inside `pad`).
- **Hosts.** `hosts/overlay/OverlaySlot` (card: `properties`, `slotRect`, `embedded: true`) and `hosts/popout/BarPopouts` (popout: `wrapper`, then, once loaded, the anchor's payload keys copied onto matching properties, so popouts declare what they take rather than reading `wrapper.currentData`). The tray's menu (`content/SystemTray`) is the one popout-only content rooted in a plain Item: it drives `TraySubmenuWrapper` through `wrapper`.
- Pairs that look different by design stay separate files: `Weather` (card) / `WeatherForecast` (popout), `ClockCalendar` / `Calendar`.

## Overlay composition (views → modules on a grid)

`Overlay.views` in the schema drives the overlay's pages, just as `Bars` drives the bar. A Custom view is a grid of modules, each with a `place` `{ x, y, w, h }` in **grid units, four to a card** (a quarter card each). Everything loads by naming convention, so there are no lookup tables:
- **View** (`OverlayPages` → `OverlayView`): `components/views/<type>.qml`, a `BaseView` that receives the screen's `grid` and its `viewConfig`, and gives hand-built pages their sizes (`pageHeight`, two cards; `cardPageWidth`; `sideWidth`). `Custom` (`views/Custom.qml`) is one `ModuleGrid` of its `modules`, with its own `icon` in the navigator (`OverlayConfig.pageIcon`; empty is the type's). `Themes`, `Keybinds`, `BarEditor`, `Settings` and `Monitors` are hand-built tool pages (`x-tool`), with their pieces in `views/<page>/`; `Layouts` (the layouts editor, `views/layouts/`) is pinned, not in config. `ShellManager.showOverlayPage(type)` switches the overlay to a page (`qs -c axiom ipc call overlay page <type or name>` opens it on one).
- **Grid** (`methods/GridPlacement`, pure, tested by `tst_GridPlacement`): `unitOf(card)` is a unit's size (`(card - 3 × spacing) / 4`, 110 px at the reference 500) and `span(n)` n units plus the gaps between, so `span(4)` is a card and `span(2)` half of one. `bounds(modules)` is how far they reach; `canPlace`/`overlaps` keep modules apart (holes are fine); `firstFree(modules, w, h)` finds a spot in reading order, else beside (or below a wide grid); `normalize` shifts a grid so its top left module sits at 0, 0; `trackSizes(bounds, unit, stretch)` gives one unit's width and height and the grid's size, growing either axis evenly into `stretch` room (never shrinking); `rectPx(place, sizes)` places a module; `fitScale` is how much an overlay's room shrinks a page. Edge menu geometry: `menuLattice`/`latticeOf` (the cells a menu sits on along its edge: as many as fit between the frame's pads, centred there, moved `gridOffset` px), `menuCell`/`alongStart`/`menuAlong` (where its modules start: centred on the lattice, `offset` cells on, kept on it), `offsetFor`/`offsetRange` (the offset for a cell, and those that keep it on the lattice), `unitsAlong`, `menuPlacement` (where they sit on the screen, in px), `menuOnScreen` (its box and modules' rects there), `menuReservedDepth` and `screenBox`. The layouts canvas: `canvasExtent` (the units drawn around the grid, and the `view` fitted: a menu's screen and a unit round it, in fractions, so the screen stays put while modules move on it), `canvasFit` (the view's scale and origin in the area), `canvasRect`/`canvasScreenRect`, `canvasDropPlace` (where a carried module lands, held by the unit it was grabbed by) and `edgeBand`/`edgeBar`.
- **Host** (`hosts/overlay/ModuleGrid`): sizes itself from `grid.sizes(bounds, stretch)` and places one clipped `OverlaySlot` per module (keyed by count), passing `GridPlacement.rectOf(place)` as the module's `slotRect`; it warns once for a module that overlaps another.
- **Module** (`OverlaySlot`): `content/<type>.qml`, filling its place. Its root is `Card` (box, `properties`, slot context; override only what differs, like `color`) or `Panel` (see Content). Titled scrolling panels (ThemePicker, the bar editor panels, the settings page's content) use `TitledCard`, which has a `CardHeader` with `title`, `dirty`, `save()`/`reset()`, `headerExtras`, children that go into the scrolling body, and `scrollTo(item)` (animated, to bring a descendant to the top). Adding a module means the file plus an `…OverlayModule` definition in `OverlayModule.oneOf` (with a `"place": { "$ref": "#/definitions/GridPlace" }` property like the others). Every module takes every size, from one unit up; `x-defaultSize` is only the size it's added at (left out, a card: `OverlayConfig.defaultSize`). Helpers used only by content go in `content/parts/` (subfolders for groups, e.g. `parts/settings/`). `OverlaySlot` imports `qs.components.content` so that `qs` scans the URL-loaded content; without it, their own `qs.*` imports fail with "not installed".

Views and modules are `oneOf`s discriminated by `type`, like `BarWidget`.

**Sizing:** the card size is per screen, not a constant. Each `OverlayPanel` has an `OverlayGrid` (`hosts/overlay/`) whose `unit` is what fits the page area above the navigator (`min(height / fitCardsHigh, width / fitCardsWide)`, capped at the reference `OverlayConfig.cardUnit` 500, times `Overlay.size`%, never below `minCardUnit`), and reports its room to `OverlayManager.reportArea` (the layouts editor's "fits" line). Views receive it as `grid` (`BaseView`) and size everything from `grid.unit` / `grid.span(n)` / `grid.sizes(bounds, stretch)`, passing plain numbers down to content; `OverlayConfig.span` without a unit, and `OverlayConfig.gridUnit`, are the reference size. A page that still doesn't fit is shrunk as a whole by `OverlayPages.fitScale` (Item.scale, last resort). `cardSpacing`/`cardPadding` don't scale.

**Loading:** one overlay per screen in `General.screens` (`shell/Overlay.qml`): a transparent `OverlayPanel` inside the reserved area (placed by its base, `ReservedAreaWindow`, shared with the onboarder), over a `reusable/ScreenBackdrop` that dims the whole monitor under the bars and border (a Top-layer surface kept under them by a Hyprland `order` layer rule that `HyprlandManager` adds at startup and on config reload; the workspace overview and launcher use it too). Its `HyprlandFocusGrab` also whitelists `ShellManager.grabPartnersFor(screen)`: the bars, bar popouts and tray submenus register themselves there (`registerGrabPartner(window, screenName)`), so they keep working while it's open. Only the current page and its neighbours (navigation wraps) are instantiated, and only while the overlay is open (`OverlayPages.isLoaded` → `OverlayPage.loaded`), so modules must not assume they live forever: acquire in `Component.onCompleted`, release in `onDestruction`, and keep state that must survive in a service. Pages come in two groups: the user's own (Custom) pages first, then the tool pages (view types with `x-tool`: Settings, BarEditor, Themes, Keybinds, Monitors), each group in config order (`OverlayPages.buildViewsModel`; `viewsModel[i].index` is the view's place in config), then the pinned Layouts page. Under the pages, `OverlayPageNavigator` shows a tab per page (`OverlayPages.pages`: icon, name and `tool` from `OverlayConfig.viewIcon`/`viewLabel`/`isTool`, shared with the layouts editor) with a sliding accent pill; tool tabs follow a divider as icons only (named in a tooltip), even when current, and when all names don't fit, the other tabs drop to icons too. A view with `visible: false` stays in config but isn't shown.

**Writing overlay modules:**
- **Any size.** `Card` and `Panel` (and `TitledCard`) take what they derive from their place from `base/SlotContext`, and expose its `slotRect` (`[x, y, w, h]`), `cols`/`rows` (grid units, four to a card), `shape` (`square` while the longer side is under 1.5× the shorter, else `horizontal`/`vertical`: `GridPlacement.slotShape`) and `compact`, plus `pad`. A unit is 25 to 140 px depending on the screen or menu (`OverlayGrid`; an edge menu uses its screen's overlay's) and text doesn't scale with it, so a module sets `fullMinWidth`/`fullMinHeight`, the px its full layout needs; `compact` is a quarter card or less (`cols <= 2 && rows <= 2`) or, once laid out, smaller than those. Compact shows the key figure (a `compactContent`, usually a `CompactFigure`, on Card, Panel or TitledCard); otherwise the module picks its layout from `shape` and its px room: side by side when wide, stacked when tall, sections dropped or rearranged where they don't fit (Weather's hours and days, ClockCalendar's calendar, Disks' header and columns), and a one-row form for strips where it has one (NowPlaying, AudioMixer's slider, Network). Thresholds that depend on text are in px from `Appearance.fontSize`, not grid units.
- **Shared parts** live in `content/parts/`: `ModuleHeader`, `Sparkline`, `StatFigure`, `TileGrid` (lays out `reusable/ActionTile`s, the icon-well tiles the power menu also uses), `RateLabel`, and the radio menus' `RadioHeader`, `DeviceList` (fixed-height in a popout, off and empty states) and `DeviceRow` (confirm-to-forget, connect; extras beside the title and content under it), shared by WifiNetworks and BluetoothDevices. `FigureValue` is the bold value + unit row of `StatFigure` and `CompactFigure`. `CompactFigure` fills its box (inside `pad`): icon, value and label stacked, or the icon beside them in a wide box, dropping the label and then the icon as room runs out and shrinking the value to fit. `EmptyState` takes an `availableHeight` and drops to its icon when short. `PasswordField` is the lock screen's field (see Lockscreen). Generic controls: see "Shared UI pieces".
- **Content can be both.** A `Panel`-rooted file is a bar popout and a card at once; branch on `embedded` for card-only parts (a header, a mode switch, acquiring with the card's `properties`).
- **Data sources.**
  - `SystemManager` adds `history: true` (60-sample ring buffers), a `net` metric (`/proc/net/dev` rates; the connection itself is `NetworkingManager.netInfo`) and a `processes` metric (two-frame `top`, with `kill(pid)`).
  - Weather comes from `WeatherManager` (`acquire(owner)`, read `source`): one `WeatherSource` for the Weather settings' location, units and refresh interval (`WeatherConfig`), shared by every bar widget, module and forecast popout. It fetches only while acquired and keeps its last data when released.
- **Repeater models** (rule in CLAUDE.md): for a derived set, `model: rows.length` with the delegate reading `rows[index] ?? fallback`; an `int`/`string` only notifies when it actually changes, so delegates (and Canvases) survive each sample or keystroke.
- **Testing a module safely.**
  - The running shell only picks up schema changes on a QML reload, and a reload only fires when a file it has *loaded* changes. A new module file doesn't count until something uses it.
  - A config checked against a stale schema fails validation, and the whole shell falls back to defaults until it's fixed.
  - So confirm the schema was reloaded after your edit before putting a new module into `config.json`. Add modules one at a time and watch `qs`'s RSS.

**Themes page:** `views/Themes.qml`, the `Themes` view type (in `Overlay.views` like any other, with nothing to configure). A `BaseView` in the editors' shape that hosts ordinary modules directly (as the onboarding Look page does): `WallpaperPicker` at `sideWidth` (two cards tall it adds a monitor picker and a preview, and sets the picked monitor's wallpaper), `ThemePicker` (the theme list and light mode switch), and a column of `Palette` (the 16 base colors with their hex and the semantic names that map to each, `Theme.roles`, written under each tile) over a Look card (`SettingRows` for font, corner radius and animations, and a link to Settings → Look & Feel).

**Layouts editor** (overlay pages and edge menus in one page):
- `views/Layouts.qml` with its pieces in `views/layouts/`. It's not in config: `OverlayPages` adds it (`pinnedPages`) as a persistent page after the Repeater, so it's always last, can't be removed, and survives the page rebuild that every `Overlay.views` change causes (pages are keyed by the views' JSON, so other config edits don't rebuild them; `_onPinned` keeps the user on it across that rebuild).
- What it edits is `OverlayManager.editTarget`: `"page"` (`OverlayManager.selectedViewIndex`, its draft of `Overlay.views`), `"menu"` (`EdgeMenuManager.selectedMenuIndex`, its draft of `EdgeMenus`) or `"lockscreen"` (`LockManager`'s draft of `Lockscreen.layout`); `editPage(i)`/`editMenu(i)`/`editLockscreen()`/`editPages()`/`editMenus()` switch it (the launcher's `/layouts` and `/menus`, `ipc call edgeMenu edit`). Each is an `EditTarget` (`PageTarget`, `MenuTarget`, `LockscreenTarget` in `views/layouts/`: the editor, modules, title, icon, screen box, fit line, …) that `Layouts.qml` binds the canvas and inspector to. Save/Reset on the canvas save or reset all three drafts, and `EditsManager` lists the page as unsaved when any is dirty.
- Layout: `LayoutsPanel` on the left (`PagesSection`: your pages, with show/hide, duplicate and remove actions and New page under them, then the tool pages as a dimmed group with only show/hide (every tool page is always in config; ConfigMigration v33 put back any that were removed, hidden), each group dragged to reorder within itself, then the Lock screen row (not a page, not dragged); `MenusSection`: the edge menus, dragged to reorder, duplicate/remove, New menu; then a page's name and icon, a tool page's Show in the navigator, and for any page buttons adding a bar Button or keybind that opens it (`OverlayManager.addBarButton`/`addKeybind`, the `overlayPage` action on its `OverlayConfig.pageKey`: a Custom page's name, else its type; only for a saved page, so an unnamed Custom page has none), a menu's field groups, or the lock screen's Show on screen and field groups (`LockscreenConfig.fieldGroups`), and "Can't save yet"), and on the right `GridCanvas` above `EditorInspector`, placed by `LayoutsEditorLayout`, a `GridDragLayer` covering it all.
- `GridCanvas` draws the selected page or menu at a scale it computes itself (not `Item.scale`): a lattice of unit squares (one `Canvas`) with room around the grid (`GridPlacement.canvasExtent`: a unit above/left, three below/right, or one past the screen), scaled to the area (`canvasFit`), `CanvasModule` tiles (drag to move, onto a module of the same size to swap; drag the corner handle to resize, snapping to units, red where it would overlap another), a menu's whole screen around it, where the menu really sits on it (`screenBox`: `EdgeMenuManager.screenBoxOf`, `GridPlacement.screenBox` from `placementOf`, below): a dashed outline with the units outside it tinted (they'd scroll), the screen edge as a faint accent bar with the menu's part solid, and a shaded band along it (`reservedDepth`, `GridPlacement.menuReservedDepth`, with a line where the windows start): the strip an integrated menu reserves, or the bars and border a floating one sits past. With "Show other menus" (`EdgeMenuManager.showingOthers`) the other enabled menus on that screen are drawn dimmed where they sit (`ghosts`: `EdgeMenuManager.othersOn`, in screen px through `pxScale`, since their module size can differ; not drop targets). Lattice squares and modules share `cellRadius`, and a header with the module count, a menu's arrows moving it along its edge (Edge menus, Editing) and how it fits (per monitor for a page, along the edge for a menu). The inspector shows the selected module's options (`OptionsGroup`) and its Size (steppers in units, shown as cards), or else the `ModuleLibrary` (`ModuleChip`s to drag, or click to add at `firstFree`).
- `GridDragLayer` payloads: `module-add { type, w, h }` (from the library, at the module's default size), `module-move { index }`, and the lists' `page-move`/`tool-move`/`menu-move`. Targets: the canvas (`targetKind: "grid"`, `placeAt(point, drag, grab)` snapped to units, a moved module keeping the unit it was grabbed by under the pointer; `hoverPlace`/`hoverValid` draw where it would land) and `EntryListTarget`s (`"list"`: `takes(drag)`, `indexAt`, `dropRequested`, which reorder their own rows, each an `EntryListRow` carrying its list's `moveKind`).
- The canvas pieces name no service: they edit through `dragLayer.editor`, a `services/GridEditor` (non-singleton: one grid of modules, its `selected` index, `addModule`/`moveModule`/`resizeModule`/`duplicateModule`/`removeModule`/`updateModuleProperty`, the `canAdd`/`canMove`/`canResize` checks and `problemsFor(modules, name)`; each edit keeps the selection on its module and normalizes the grid, so a place left of or above it makes room there (`shifted(shift, boundsBefore)` tells the owner, which EdgeMenuManager uses to keep a menu's modules on their cells); with an `area` `{ cols, rows }` the grid is bounded instead: places stay absolute and inside it, new modules go to `GridPlacement.firstFreeIn`, and `problemsFor` flags one outside it; required modules (`canRemove`) are never removed or duplicated, and a grid missing one is a problem). `OverlayManager.layout`, `EdgeMenuManager.layout` and `LockManager.layout` (bounded by the layout's `columns` × `rows`) each own one, pointing `modulesOf` at the selected page's or menu's modules, or the lock screen's.
- Module and view pickers read `OverlayConfig.availableModuleTypes` / `availableViewTypes` (`modulesFor(host)` for the `x-hosts` filter). These come from the schema's `oneOf`s, including `x-defaultSize`, `x-icon` and `x-tool`, so new types show up there automatically. `reusable/TypePickerPopup` is the shared "pick a type" popup used by the bar editor and the page list.

## Edge menus (`EdgeMenus` section, `EdgeMenusConfig`, `EdgeMenuManager`)

Menus that pop out of a screen edge, holding overlay modules. `EdgeMenus` is an array like `Bars` (`x-settings: false`, blocked from `/config`: the layouts editor owns it). Each entry has `id`, `name`, `monitor`, `edge`, `mode`, `offset`/`gridOffset` (below), `length` (`content`: as long as its modules; `edge`: stretched along the whole edge, the room shared evenly by its rows, or columns on a top/bottom edge), `moduleScale` (% of its screen's overlay card size), style (`padding`, `moduleBorders`, `pinButton`, `backgroundColor`/`borderColor` read through `EdgeMenusConfig.colorsOf`, floating `edgeDistance`, integrated `frame`), opening (`openOnHover`, `openDelay`, `triggerSize`, `triggerLength`: 0 is the menu's length, `EdgeMenusConfig.lengthOf` from config until it's loaded), closing (`closeOnLeave`, `closeDelay`, `closeOnOutsideClick`) and `modules` (placed as on a Custom page). Escape closes a focused menu (`EdgeMenuBody`), and the `edgeMenu` bind action toggles one by id.
- **State.** `EdgeMenuManager` holds which menus are open and pinned (a `PersistentProperties`, so a reload doesn't reflow windows) and the `edgeMenu` IPC target. The menus follow it and report back when they close by themselves. They work over the overlay: their windows and hover strips are its grab partners (`EdgeMenuSync`'s `window` and `triggerWindow`), a floating one draws over it and, while it's open on its screen, takes no focus grab of its own (`grabEnabled`), which would clear the overlay's and close it. An open floating menu claims its edge (ShellManager's edge claims), putting away an OSD or dock there. A bar `Button` with `action: "edgeMenu"` and `menu: <id>` toggles one, passing itself as the anchor, so a floating menu stays open while the button is hovered.
- **Hosts** (`surfaces/edgemenu/`). `shell/EdgeMenus` builds one `EdgeMenu` per enabled entry (keyed by id), which `LazyLoader`s the host for its mode. Both put `EdgeMenuBody` inside: a `ModuleGrid` on an `OverlayGrid` with `fixedUnit` the card size of its screen's overlay (`EdgeMenuManager.cardUnitOf`: `OverlayManager.areas`, else `OverlayConfig.cardUnitFor` the screen, so Overlay size scales menus too; times the menu's `moduleScale`%), stretched along the edge to `maxLength` when `length` is `edge` (`fillsEdge`), else scrolling along it past that; with `pinButton` it draws a pin in the corner away from the edge (`EdgeMenuManager.togglePinned`). Along the edge the modules sit on a lattice fixed to the screen (`GridPlacement.menuAlong`, at the host's `unit`): as many whole cells as fit between the host's `startPad`/`endPad`, centred there and moved `gridOffset` px; the modules start `offset` cells from centred on it (negative: towards the start), kept on it (so an offset past it is flush with that end's cell). A menu longer than its lattice starts at `startPad` and scrolls. Neither is a form field (`x-settings: false`, which `SchemaLayout.objectGroups` leaves out): the layouts editor sets them (Editing, below). Each host reports where its modules can sit (`EdgeMenuSync.frame` → `EdgeMenuManager.setFrame(id, { screen, startPad, endPad, across, before, after, reserves })`, cleared on destruction or an id change) for the editor, which also draws the other menus from it (`screenRectsOf`); `frameOf(menu)` falls back to the menu's padding for one without a host (disabled). `EdgeMenu` keeps the last live entry, so the hosts read its (schema-defaulted) fields directly. What both hosts share is `EdgeMenuSync`: following `EdgeMenuManager` (and telling it when the menu closes by itself), held/revealing state, `autoDismiss`, the trigger length, grab-partner registration and the reveal's cursor warp (`warpRequested`, each host warping into its own box).
  - `floating`: `FloatingEdgeMenu`, an `EdgePopout` (`contentPadding`, `edgeOffset`, `fillColor`/`strokeColor`, defaulting to what the OSD uses). It's `detached` (a plain box) when `edgeDistance` > 0 or its edge has a pill or transparent bar, else attached to the border or solid bar. Its window sits inside what's reserved on each screen edge (`reservedOn(location)`: the border's `screenMargin`, a bar's `reservedZone`, integrated menus' zones; not docks, which it reaches past), so its edge coordinates start at `alongOrigin` (what the perpendicular edge at its start reserves) and its ends keep `startPad`/`endPad` from the screen's. It places its box with `position: 0` and a `positionOffset` from the modules' start (from the box's natural length: the end joins depend on its position), and across its edge past `reservedOn(edge)`. Both hosts centre their hover strip on the modules from config (`EdgeTrigger.centre`, through `EdgePopout.triggerCentre` for this one), since the body only loads while open.
  - `integrated`: `IntegratedEdgeMenu`, a `PopoutWrapperBase` with a Top-layer `axiom-edge-menu` window along the whole edge. Its layer rule's `order = 7` (above the bars' 5) arranges it first, so it sits outermost and the border, bars and every Normal-exclusion surface move inwards. The zone is set once while it's mapped (windows retile in one step) and the strip slides in. With `frame`, a rounded stroked box runs the strip's whole length, its stroke's inner edge `screenMargin` in from the strip's edges (as the border's is, so the two line up), holding the modules `padding` in from its stroke. It reports its zone (`EdgeMenuManager.setZone`), which `BarPopouts.borderInset` takes off the perpendicular bars' length.
- **Editing** happens on the Layouts page (above). The draft (`ConfigDraft { path: ["EdgeMenus"] }`, `layout`: the selected menu's `GridEditor` with host `edgeMenu`) lives in `EdgeMenuManager`, and shows live on the running menus through `previews.EdgeMenus` while dirty, as the bar editor's does. The menu's fields come in `x-group`s (General, Opening, Placement, Style, Closing, Advanced: the read-only `id`); the Opening group leads with `MenuOpening`: "Show on screen" (sets `previewing` to the selected menu, following the selection and id renames, and opens it; `isHeld(id)`, pinned or previewing, makes a menu ignore `closeOnLeave` and outside clicks; the page's `onDestruction` stops it), what else opens the menu (`EdgeMenuManager.references(id)`: bar Buttons in the bar editor's draft or saved bars, binds in the keybind editor's draft or `HyprlandConfig.binds`), and buttons that add a bar Button (`addBarButton` → `BarManager.addWidgetTo`, into the bar editor's draft, then the bar editor on that bar) or a keybind (`addKeybind` → `KeybindManager.addAndRecord`, then the Keybinds page's editor recording its key), drawn by `OpenerButtons` (shared with the page's Opening group). A new menu (`addMenu`) opens on hover and starts previewing. Beside "Show on screen", "Show other menus" draws the others on the grid. The canvas's lattice is the menu's (its cells past the lattice along the edge tinted, `latticeSpan`), so it never moves when modules do, and edits never move modules on the screen: `GridEditor.shifted` hands `_keepPlace` the shift `normalize` took off and the bounds before the edit, and the menu's `offset` follows so its modules keep their cells (a module dropped left of the others lands where it was dropped). The arrows under the canvas title (`EditTarget`'s nudge fields, from `MenuTarget`: left/right on a top or bottom edge, up/down on a side) step `offset` a cell at a time within `GridPlacement.offsetRange` (`nudgeSelected(step)`; `centreSelected()` recentres), saying where it is (Centred, n cells from the centre, at an end), and the Grid stepper beside them moves the lattice up to half a cell either way (`setGridOffset`, `gridOffsetLimit`). One taking its whole edge has no place along it, and no arrows.
- **Pin.** `pinButton` puts a pin on the menu, and QuickActions has a `pin` action; both toggle `EdgeMenuManager.pinned[id]`. While pinned, a menu ignores `closeOnLeave` and outside clicks. Modules learn where they're shown from `host` (`{ kind: "overlay" }` or `{ kind: "edgeMenu", id, bare }`, on `Card`/`Panel`, passed down `ModuleGrid` → `OverlaySlot`). `x-hosts` on a module definition limits where it may go: `OverlayConfig.modulesFor(host)` feeds the library, and `GridEditor.problemsFor` flags a misplaced module.

## Editors (settings, bar, layouts, keybinds, monitors)

They share one shape; a new editor follows it:
- **Draft.** The manager owns a `ConfigDraft` of its config path: mutate `draft.local` in place, then `changed()` (re-clones next tick so bindings see it; `isDirty` by JSON compare). Structural editors show unsaved edits live through `ConfigManager.setPreview`. Save merges onto the latest config (`commit`, which may refuse: the draft stays dirty); Reset reloads. `ensureLoaded()` on page open reloads only a clean draft.
- **Selection** lives in the manager (`selectedBarIndex`, `selectedViewIndex`, `selectedMenuIndex`, `selectedProfile`, …) and changes through `select*()`, which clears or fixes what hangs off it. Add/remove/move functions keep it on the right entry.
- **Page.** A `BaseView` (sizes: `pageHeight`, `cardPageWidth`, `sideWidth`, and `editorWidth` for the main area beside it) with a `TitledCard` on the left: a list of `ListEntryRow`s (icon, name, badges, unsaved dot from `…Changed(index)`, `RowAction`s) and an `AddEntryButton`, then the selected entry's fields (`FieldGroup`s of `SchemaPropertiesForm`, grouped by `x-group`), then "Can't save yet" (`IssueList`) when `problems` block Save. Save/Reset are page-wide, so they sit top-right like Settings: on the right-hand top card (`SectionsBoard`'s header, `GridCanvas`'s through `LayoutsEditorLayout`), with the left panel's `showActions: false`.
- **Unsaved reminders** (`EditsManager`): drafts survive leaving a page or closing the overlay (bar and edge menu edits stay live through previews), so nothing blocks closing. `EditsManager.unsaved` lists the pages (view types) with dirty drafts; the navigator dots their tabs, and while another page has some it shows Save all / Discard all after its arrows (`saveAll()`/`discardAll()`, skipping `separate` pages: Monitors, which applies with a keep/revert step). A new editor adds its manager to both lists.
- **Text fields** bound to draft values follow the push pattern (CLAUDE.md pitfalls): set the text on selection change, and on draft change unless focused; write per keystroke while focused (`LayoutsPanel`, `Monitors`).
- **Drag.** A `reusable/DragLayer` subclass covers the page and draws the ghost: `BarDragLayer` (targets: the `SectionLane`s; payloads `{ kind: "move" | "add", zone, index, type, compact }`) and `GridDragLayer` (see Layouts editor). Draggables are `DragArea`s (`dragLayer`, `payload`) or `DragChip`s.
- **Inspector.** `InspectorHeader` + a `KeyedLoader` keyed on the selection building an `OptionsGroup` (widget/module `properties`), or a library of `DragChip`s in a `TileFlow` when nothing is selected.

**Bar editor** (`views/BarEditor.qml`, pieces in `views/barEditor/`): `BarsPanel` on the left (the bars, with duplicate/remove, then the selected bar's field groups; the Style group's header copies the bar's look, `BarManager.styleKeys` (its Size and Style settings), and pastes it onto one bar or all, the copied style following its bar by index). On the right, `BarDragLayer` holds `SectionsBoard` along the side of the page the selected bar is on (a strip across the top or bottom for a horizontal bar, a column at the left or right for a vertical one) and `WidgetInspector` beside it. The board's five `SectionLane`s are laid out the way the bar lays out its sections (`BarLayout.layoutSections` over each lane's `naturalLength`/`minLength`), each a row or column of `WidgetChip`s that scrolls when it can't show them all (a scroll bar, and the wheel through the lane's `WheelHandler`, sideways on a horizontal lane: the Flickable itself isn't interactive, so chips keep their drags); chips are dragged within and between lanes or dropped in from the library. The inspector shows the widget's options (and, for a Button opening an edge menu or page, `OverlayManager.openedBy`/`editOpenedBy` taking it to the layouts editor), plus its Sizing: the `LayoutOverrideField`s from `Bar.widgetLayoutSchema`, explained from, and starting at, what the bar uses now. With nothing selected it shows the widget library, whose click adds to `BarManager.lastZone` (the section last selected or added to). Edits show live on the running bars.
- **Live reports.** While a BarEditor page is visible (`BarManager.watch(page)`/`unwatch`, a `ConsumerRegistry`: `editing`), the running bars outline the selected widget (`BarManager.isSelectedWidget(source, zone, index)` → `BarWidgetHost.highlighted`), and each `BarContainer` reports `editorReport` to `BarManager.live` (`setLive(id, report)`, `clearLive(id, screen)` on destruction): its `source` (config id), `screen`, `hidden` (per section, the config indices `WidgetGroup.crowdedOut` hides for want of room) and `selected` (the highlighted host's `measure`: `policy`, `size`, `preferred`, `minimum`, `priority`). `BarManager.liveReports()` gives the selected bar's, one per screen: the board's fit line ("Fits DP-1", or what has no room where), the chips' crowded badge, and the inspector's sizing text. `BarContainer.widgetModel` keeps each widget's `configIndex`, since widgets hidden in config aren't on the bar.

## Popouts (bar + screen edge)

Shared pieces live in `components/hosts/popout/`: `PopoutWrapperBase` (open/close/queue state, `isOpen`/`show(data)`/`hide()`, hover-loss dismiss timer), `FloatingPopout` (a box floating in the free area at a fraction across and down, fading in; the floating OSD and launcher), `SlideAnimation`, and `AttachedSurface` (the content box + connector + `CornerPiece` fillets that make a popout look like it grows out of a bar or the screen border; `edge` is a `Bar.Location`). Bar popouts (`BarPopouts.qml`) share one wrapper per bar. Screen-edge popouts (`EdgePopout.qml`, used by `OSD.qml`, floating edge menus and the attached launcher) are one independent instance per screen (`Variants` over `Quickshell.screens`). Each is an Overlay-layer `PanelWindow` with Normal exclusion and a `-borderWidth` margin, so it lands on the inner stroke of whatever reserves that edge: the border (`surfaces/border/`) or a bar.

**Bars and the screen border share an edge by layer-shell ordering.** `Appearance.screenBorder` turns the border (`shell/ScreenBorder`: `surfaces/border/RoundedBorders`, four `BorderPanel` strips and four `CornerPiece` corners, layer namespace `axiom-border`) off.
- **Solid bar** (`Bar.background: "solid"`): Top layer, at the screen edge. The border's strip on that edge is arranged after it and overlaps its inner part, so the strip's stroke is the bar's inner edge.
- **Floating bar** (`barConfig.floating`: transparent or pills, with the border on): Overlay layer, whose exclusive zones Hyprland arranges after the Top-layer border. It sits just inside the border with a `-borderWidth` margin, so its outer edge lies on the border's stroke. It hides while its workspace has a fullscreen window. Hyprland counts that margin into the reserved space, so it reserves `extent`. `RoundedBorders.cornerMargin` pulls the corner pieces back out to the border's corners on a floating bar's edge.
- **Pills** (`BarContainer.pillRects`): one per section, merged when they're at most `pillMerge` apart. Each is an `AttachedSurface` growing out of the bar's outer edge, covering the border stroke (`barConfig.overlap`); widgets sit `overlap + pillPad` in from that edge. A pill at an end of the bar joins the perpendicular edge (`joinStart`/`joinEnd`: flush on its stroke, whose far corner meets it with a fillet). The bar window is `borderRadius` thicker than `extent` in pill mode for that fillet, masked to the bar itself. Floating bars take `-borderWidth` margins on both ends too, so bar-window 0 along the bar is the perpendicular stroke's outer edge.
- **Bar popouts** join an end the same way when their alignment would push them back from it. On a pill bar, a popout not wholly within its pill (`BarPopouts.mergeWithPill`) grows from the outer edge instead, deeper by the pill, with the pill's interior showing through the surface's notch (also cut out of the input mask); each side wall lands on the frame, or on the pill's far stroke (`startFoot`/`endFoot`) where the pill carries on past it. On a transparent bar popouts are `detached`: plain rounded boxes, except one pushed to an end (`BarPopouts.cornerAttach`), which attaches to that perpendicular edge instead, joining it on both sides. They're a layer surface of their own (`underWindow`, not a popup, which would always draw over its bar) in the `axiom-popout-under` namespace, whose layer rule (`order = 6`) stacks it under the bars and border; it starts at the bar's outer edge and the box (`AttachedSurface.detachedOffset`) slides out from beneath the bar. That rule also stacks it under the overlay, so while the overlay is open on its screen (`ShellManager.surfaceOpenOn("overlay", screen)`) the box shows from the bar's popup instead, which draws over it, without the slide. Detached floating edge menus do the same (`FloatingEdgeMenu._overOverlay`, followed only while the menu is closed, since it changes the window's namespace) (`EdgePopout.slideDistance`/`underLayer`).
- **Transparent bars** reserve `Hyprland gaps_out` less (`HyprlandManager.gapsOut`), so windows start at the bar's invisible inner edge and the widgets' gap to them matches their gap to the screen edge. Bar popouts use `adjustment: PopupAdjustment.None`: their placement is computed, and Hyprland otherwise nudges one flush on the screen edge a few pixels inwards.
- **Border off**: a solid bar draws its own inner stroke (`barConfig.innerStroke`, on its innermost `borderWidth` pixels, where its popouts attach). Surfaces on a bare screen edge (`Bar.screenEdgeOpen(screen, location)`: no border, no bar there) run straight off it, with no fillets and no `-borderWidth` margin: `AttachedSurface.straight` (attach edge) / `straightJoins` (joined ends) for pills, merged popouts and EdgePopout, and the overlay panel pushes its corners and stroke past the window on those sides.

## Launcher (`surfaces/launcher/`, `LauncherManager`)

`LauncherManager` turns the search text into rows, and the UI only draws them. `LauncherPanel` holds the field, list and hint, with no box of its own. `Launcher.qml` hosts it in a `FloatingPopout` (centred, or its top in the upper third; `maxContentHeight` keeps it from moving and `growUp` keeps a reversed field in place), or in an `EdgePopout` when `Launcher.position` is `top`/`bottom` (`LauncherConfig.attached`). Both have the same API (`show`/`hide`/`isOpen`/`contentItem`/`window`), and only the host in use is created, through `LazyLoader`s. `open(text)` searches first (so instances on other monitors show the same text); the panel created on opening then doesn't search again. `reverse` puts the field at the bottom and lays the list out bottom to top. Every provider returns the same row shape: `{ kind, image, glyph, title, usage, subtitle, hint, complete, run(shift) }`. `run` returns true to close, false to stay open (then the rows are rebuilt, keeping the selection), or a string to search for instead. Tab puts `complete` into the field.
- **Routing.** The first character picks the provider: `/` commands, `=` calculator, `>` run, `?` web, `@` chat, `:` clipboard history (ClipboardManager), `;` emoji (EmojiManager). Anything else searches apps (scored, plus frecency from `usage` `{id: {count, last}}` in `state/launcher.json`) and windows (`HyprlandManager.windowList`). A calculator row is added when the text is plain math, and a web row goes last. Each provider has a `Launcher` config toggle (`LauncherConfig`).
- **The calculator** runs `qalc` through one debounced Process, and the rows are rebuilt when it answers.
- **Commands** live in `services/LauncherCommands.qml`, a plain list of `{ name, aliases, glyph, description(), usage, needsArg, confirm, available(), status(), options(arg), run(arg, value) }`. A new shell feature gets a command by adding an entry that calls its service. `options` supplies argument completions. `confirm` (destructive session actions) asks for a second Enter.
- **`/config`** sets any setting by dotted path (`/config Appearance.font.size 14`), saving it at once through `SettingsManager.commitValue`, and holds `save` / `restore` for snapshots. It works inside the options contract: each option's title is the whole argument, so matching and Tab work unchanged. It offers `SettingsManager.settingPaths` only: the settings page's fields, minus `x-applyOnSave` ones and anything under `_blockedPrefixes` (`Bars`, `Overlay.views`), so it can never edit bars or overlays. Values are parsed and checked by `SettingsManager.parseValue`, and choices come from `SettingsManager.optionsFor` (shared with `SchemaField`).
- **IPC** is `appLauncher`: `open` / `close` / `toggle` / `search <text>`.
- **Opening a page.** `ShellManager.openOverlayPage(type)` opens the target overlay on a page, taking a view type or a view's name.

## Lockscreen (`Lockscreen.mode`)

`LockManager.lock()` is the one way to lock; lock buttons call it through `ShellManager.sessionAction("lock")`, and idle daemons through the `lockscreen` IPC target:
- **`quickshell`** (default): the built-in locker, `shell/Lockscreen.qml`. A `WlSessionLock` (Wayland `ext-session-lock-v1`, the protocol hyprlock uses) with one `WlSessionLockSurface` per screen showing `surfaces/lockscreen/LockSurface.qml`. While locked the compositor shows only the lock surfaces and sends them all input; if qs dies the session stays locked (Hyprland's fallback; `misc:allow_session_lock_restore` lets a restarted qs take it back). The locked state lives in a `PersistentProperties`, so a QML reload comes back locked. **Only `AuthManager.authenticationSucceeded` (PAM, `login` stack) unlocks**: there is no IPC unlock, and nothing on the surface may run commands.
- **`hyprlock`**: `ThemeManager.generateHyprlockConfig()` writes `$XDG_STATE_HOME/axiom/hyprlock.conf` from `scripts/templates/hyprlock_template.conf` (theme colors, font, wallpaper, blur, translated greeting) on theme/wallpaper/font/language changes and on switching to this mode; lock runs `hyprlock -c` with it. The user's own `hyprlock.conf` is never touched.
- **`none`**: axiom provides no locker and no IPC target (so an idle daemon pointed at axiom can't loop through `loginctl lock-session`); lock buttons run `Lockscreen.lockCommand`.
- **hypridle**: `Idle.enabled` has axiom run it with its own config (see HypridleManager). A user's own hypridle for the first two modes: `lock_cmd = qs -c axiom ipc call lockscreen lock`, `before_sleep_cmd = loginctl lock-session`; for `none`, no axiom references.

**The built-in lock screen's layout** (`Lockscreen.layout`, `x-settings: false`, edited on the Layouts page's Lock screen row; `LockscreenConfig.layout` is the saved one, which is all a real lock ever shows):
- **Grid.** Overlay modules on a bounded grid of `columns` × `rows` units (16 × 9 by default), absolute places from the top left. `fineGrid` ("Double grid") splits each unit in two each way (`LockscreenConfig.gridOf(layout)` is the grid in the units places use): turning it on or off rescales every place (`GridPlacement.scalePlace`, in `LockManager.updateLayoutField`; merging rounds each edge, so modules that met still meet), and the `GridEditor`'s `sizeScale` doubles new modules' default sizes. `LockSurface` fits it to each screen inside a `cardSpacing` margin: an `OverlayGrid` whose `fixedUnit` is `GridPlacement.latticeUnit` (the axis with less room decides), and a `ModuleGrid` with `extent` the lattice (or what the modules reach, if more) and `stretch` the screen, so the units stretch to fill a screen of another shape and placements keep their relative spot. The editor draws the lattice inside a screen outline (`LockscreenTarget.screenBox`).
- **Hosts.** Modules get `host: { kind: "lockscreen", target, preview, key, bare, passwordBorder, greetingBorder }` (`bare` is `!moduleBorders`: no card box, but unlike a bare edge menu module it keeps its padding, `SlotContext.pad`, since nothing else pads it). `Password` and `Greeting` ignore `bare` there: their boxes follow the layout's own `passwordBorder` / `greetingBorder` (off by default). Only module types whose `x-hosts` list `lockscreen` may go there: display-only ones plus NowPlaying (media transport) and VolumeDials, nothing that launches, dispatches, kills, writes files or shows private content. A new module stays off the lock screen unless it's added there deliberately.
- **Password.** The `Password` module (`x-hosts: ["lockscreen"]`, `x-required`) draws `content/parts/PasswordField`, which talks to `AuthManager` and keeps the keyboard focus only when `active`: on the `target` screen of a real lock (`host.target && !host.preview`); anywhere else it's inert. It reports itself to `LockManager.reportPasswordField(host.key, true)` (each surface's key comes from `LockManager.newSurfaceKey()`, never reused: keyed by screen name, a monitor that dropped out and came back while turning off had its old surface's teardown clear the new one's report, flickering the fallback in), and a surface whose key has no report shows a `PasswordField` of its own (a tick after loading, near the bottom, over the modules), so a hand-edited or broken layout can never lock anyone out.
- **Other screens** (`otherScreens`): `layout` shows the modules without `Password`, `background` only the background.
- **Background**: `background` `wallpaper` (`Appearance.wallpaperFor(screen)`, blurred by a `MultiEffect` when `Lockscreen.blurWallpaper`, which hyprlock's config also follows) or `color` (`backgroundColor`), under a black layer at `dim`%.
- **Greeting** (`content/Greeting`, any host): a line of text fitted to its slot (`Text.Fit`), with `{name}`, `{user}` and `{greeting}` (a `SystemClock` at hour precision, only while the text uses it); empty is the translated "Hey {0}".
- **Editing and preview.** `LockManager` holds the draft (`ConfigDraft` of `["Lockscreen", "layout"]`, so it never fights the settings page's draft over `mode`), its `GridEditor` (`layout`), `problems` and `updateLayoutField`. "Show on screen" (`startPreview()`) closes the overlay and shows `surfaces/lockscreen/LockPreviewWindow` on the target screen (fixed when it starts, `previewScreen`): an Overlay-layer window with exclusive keyboard focus holding `LockSurface { preview: true }` on the draft. Nothing is locked and the field is inert (it lets Escape through); Escape or a click on the background (`stopPreview()`) reopens the overlay on Layouts. `lock()` ends a preview first.
- `showMedia` became modules in ConfigMigration v34 (Greeting, NowPlaying unless it was off, Password, where the old column had them).
