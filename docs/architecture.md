# Architecture notes

Detailed notes on how each service and surface works, moved out of CLAUDE.md so they are read on demand instead of loaded every session. CLAUDE.md holds the rules; this file holds the mechanics. Keep it current when changing a feature, and trust the code over it where they disagree.

## Services layer (`services/*.qml`)

Every file is `pragma Singleton QtObject` — one global instance per name, imported as `qs.services`. Key ones:
- **ConfigManager** — the source of truth for runtime config. Owns `_config` (parsed `config/user/config.json`) and `_configSchema`, loaded eagerly at creation (the active theme's data belongs to ThemeManager). Load pipeline: parse → `ConfigMigration.migrate` (upgrades old layouts by `version`, writes the result back once, moves API keys to `SecretsManager`) → `SchemaValidation.pruneUnknown` (drops unknown keys with a warning) → `SchemaValidation.applyDefaults` (fills every schema `default`) → validate. Editors create new entries at their definition's defaults with `withDefaults(value, "Bar" | "BarWidget" | "EdgeMenu" | "OverlayView" | "OverlayModule")`. All config writes go through `setTheme()` / `setWallpaper()` / `saveConfig()` / `commit(object)` (draft services: runs prune/defaults/validate, returns false and changes nothing if rejected, so drafts stay dirty), which validate before writing, then `forceReload()`. Never mutate `ConfigManager.config` fields directly from UI code and expect persistence — call the setter functions (or `SettingsManager.setValue(path, value)` from settings UI). The editor services (SettingsManager, BarManager, OverlayManager) each hold a `ConfigDraft` (`services/ConfigDraft.qml`: working copy of one config path, `changed()` after in-place edits, `save()` merges onto the latest config via `commit`). `ConfigManager.previews` (`setPreview(section, value)` / `clearPreview(section)`) holds unsaved edits shown live without being part of `config`, so other saves and disk reloads don't touch them: BarManager previews `Bars` while dirty, and `Bar.bars` reads `previews.Bars ?? config.Bars`.
- **SecretsManager** — chat API keys, never in config.json: the provider's `keyEnv` env var, else the keyring (`secret-tool`, `service axiom provider <id>`; probed once, `keyringAvailable`), else `$XDG_STATE_HOME/axiom/secrets.json` (mode 600). `withKey(provider, cb)` is async (cached per session); `status(provider)` is `env` | `keyring` | `file` | `none` | `unneeded`; `setKey`/`clearKey` write through stdin, never argv. Keys are entered on `views/settings/ChatProvidersCard` (the Chat section's `x-card`, with Test and Fetch models), never through the settings draft.
- **ChatManager** — the chat: `conversation` (`{ id, title, preset, provider, model, messages }`), `conversations` (index, newest first), `send`/`stop`/`regenerate`, presets and models, attachments (clipboard, a region from `ScreenshotManager.pick`, dropped files; base64 per send), saved to `$XDG_STATE_HOME/axiom/chats/` (`<id>.json`, `index.json`, `<id>/` attachments) up to `Chat.keepConversations`. Each reply is a `services/ChatRequest` (curl with its config, key included, on stdin via `-K -`; the body in a `$XDG_RUNTIME_DIR` file; a `SplitParser` feeding SSE lines to `components/methods/ChatProtocol`, which builds requests and parses streams for the `anthropic`, `openai` (any OpenAI-style server) and `gemini` kinds). Streamed text lives in `streamingText`/`streamingThinking`, flushed every 50 ms, and replaces the placeholder message only when the reply ends, so the message list doesn't rebuild per token. Anthropic thinking blocks (with signatures) are sent back only to the model that wrote them. `components/methods/ChatMarkdown` splits replies into prose and code blocks. `content/Chat.qml` is a `Panel` (ready to be a popout). IPC `chat`: `open`, `newChat`, `ask <text>`, `settings`; launcher `@` and `/chat`; `OverlayConfig.pageWithModule(type)` finds the page to open. Created from `shell.qml`'s `_services` (for the IPC target).
- **ThemeManager** — owns the active theme: `currentTheme` (loaded eagerly, watched, reloaded when `Appearance.theme` or the file changes) and `defaults` (`theme-defaults.json`); `Appearance.darkMode` is derived from the theme's `variant`. Also theme discovery: `themeFamilies`, one entry `{ label, dark, light, generated }` per theme, where a dark/light pair (each file's `paired` naming the other) is one theme labelled by the words their names share, and `currentFamily`; `applyFamily(family)` picks the variant for the current mode and `setLightMode(bool)` switches the current theme's variant (the only light/dark switch; `Appearance.darkMode` follows the applied theme). Then generation from a wallpaper (`scripts/generate_theme.py`, one run writing a `generated/wallpaper-<style>-dark|light` pair per `STYLES` entry (`tonal`, `vibrant`, `faithful`, `muted`, `alternate`: factors on the one build, like Material's scheme variants): k-means in OKLab picks candidate colors, the palette is built in OKLCH from targets measured off the hand-made themes, with the wallpaper's seed as `accent` in `base0F`; run through `scripts/venv_python.sh`, which keeps `.venv` in sync with `scripts/requirements.txt`), `setWallpaper` (`Appearance.wallpaperBackend`: `quickshell`, the default, is drawn by `shell/Wallpaper` (one Background-layer `surfaces/wallpaper/WallpaperWindow` per screen, crossfading) straight from config; `awww` runs `setWallpaper.sh`, and Hyprland's `wallpaperDaemon` starts it only then), and `themeIntegrations()` (one `scripts/theme_<key>.sh` per `ThemeIntegrations` switch: `integrations` is the schema's boolean keys, with `integrationTitle(key)` and `integrationCommand(key)` (what shows the app is installed, for the onboarder); a failure, or a `Warning:` line on stderr, is logged), which run only when the active theme's name or contents change. The choice of theme is persisted through `ConfigManager.setTheme`.
- **ShellManager** — cross-cutting UI signals (power menu, launcher, overlays) that modules connect to rather than calling each other directly, and screen targeting. `General.monitors` is `"primary"` | `"focused"` | `"all"`; the OSD, overlay and launcher have their own `monitors` setting (`"general"` | `"primaryBar"` | `"focused"` | `"all"`, resolved by `modeFor(mode)`; the power menu uses General's). Surfaces are built on `General.screensFor(mode)` (`General.screens` for General's), and only the instance on `targetFor(mode)` (`isTarget(screen, mode)`: the focused monitor in "focused"/"all") answers a shortcut, IPC call or OSD event. In "all" (`everywhere(mode)`, `showsOn(screen, mode)`) the surface opens on every monitor at once: a `reusable/SurfaceGroup` per instance opens and closes the others with it (`ShellManager.surfaceShown`), and since only one `HyprlandFocusGrab` can be active, only the target's instance holds one, over every instance's window (`surfaceWindows`); the launcher's instances share `LauncherManager.text`. The workspace overview is built on every screen and opens on the one under the cursor (`HyprlandManager.withHoveredScreen`, a `hyprctl cursorpos` lookup). Wallpapers are per monitor (`Appearance.wallpapers[monitor]`, set from the overlay's Themes page; the primary monitor's is also `Appearance.wallpaper`, the lockscreen's). IPC handlers are `enabled` on the target instance only, since a target name can have one handler.
- **SystemManager** — CPU/memory/temp/GPU/disk stats. Reference-counted through a `ConsumerRegistry` (shared with UpdatesManager; identical re-registrations are no-ops): consumers call `acquire(owner, {interval, metrics, diskPaths})` / `release(owner)`, and it polls only the union of requested metrics (sysfs/procfs `FileView` reads, no processes on the hot path), stopping entirely with no consumers.
- **UpdatesManager** — pending pacman/AUR updates shared by every Updates widget (same acquire/release pattern). Only one `checkupdates` may run at a time: concurrent runs share its temp db and fail. `upgrade(command, terminal)` runs the upgrade in a terminal (one at a time, `upgrading`) and checks again when it closes.
- **Anything that polls goes through a service's `acquire(owner, request)` / `release(owner)`** (a `ConsumerRegistry` inside), so each thing is fetched once for all widgets, at the shortest interval asked for, and not at all when nothing shows it. Widgets never run their own polling Process or repeating Timer. Besides SystemManager and UpdatesManager: `WeatherManager`, `TailscaleManager` (`available`, `backendState`/`connected`, `tailnetName`, `ip`) and `CommandManager` (any shell command's output, `outputs[command]`, shared by identical commands; e.g. a Button's label; `CommandManager.runDetached(command)` also runs a widget's one-off click and middle-click commands, so widgets start no processes; and `CommandManager.run(command, callback, input)` runs a one-off command for a service and calls back with `(exitCode, stdout, stderr)`, writing `input` to its stdin first when given: services use it rather than each keeping a Process component of their own). Acquire in `Component.onCompleted` (and again when the config-derived request changes: identical requests are no-ops), release in `onDestruction`. Widgets hold the request in a `readonly property var …Request` built from `properties` and acquire it in `on…RequestChanged` as well as `Component.onCompleted`.
- **NetworkingManager** — Wi-Fi over `Quickshell.Networking` (NetworkManager D-Bus, event-driven): radio (`wifiEnabled`, `setWifiEnabled`), `networks` (connected, saved, then by name; fixed order), connect/disconnect/forget, the password prompt (`passwordFor`, `connectWithPsk`, set again on a `NoSecrets` failure), and the primary connection (`primaryDevice`: wired before Wi-Fi; `netInfo` `{ kind, name, device, signal, ip }`, all bindings, except the IPv4 address, which Quickshell.Networking lacks: one `ip -4 -j addr` whenever the connection changes, or on `refreshIp()`). Nothing runs `nmcli`. The scanner runs only while something holds `acquireScan(owner)`. Not named `Networking` (Quickshell's singleton). Throughput stays in SystemManager.
- **BluetoothManager** — adapter power, scanning, sorted device lists and connect/pair/forget over `Quickshell.Bluetooth`. Not named `Bluetooth`, which would shadow Quickshell's singleton (and the `Bluetooth` bar widget file).
- **NotificationManager** — the DBus notification server plus a persistent history: `entries` (plain objects, newest first, capped at 100) stay until the user removes them (`dismiss(uid)`, `clearAll()`, or the `notifications` IPC target), even when the app withdraws one, and are saved to `$XDG_STATE_HOME/axiom/notifications.json`. `liveNotification(uid)` gives the still-open Notification (for actions), and restored entries open their app instead (`openApp`). `NotificationsConfig` sets the history's size and age (`maxEntries`, `maxAgeDays`) and which user actions remove an entry: `clearOnFocus` (an `activewindow` event whose class matches the entry's desktop entry or app name), `removeOnClick`, `closeRemoves`. Toasts take their entry's uid at creation (`uidOf`), because invoking an action can close the notification. `dnd` (readonly; `setDnd`/`toggleDnd`) is saved in `config/state/notifications.json`. The toasts (`shell/Notifications`) stack once per screen of `NotificationsConfig.monitors` (`showsOn`); a toast the user closes closes on every screen. Images are cached as PNGs in `…/axiom/notifications/`, rendered through an `imageHost` item that `shell/Notifications` lends it (grabbing needs a window). `keepOnReload` keeps live notifications across QML reloads.
- **HyprlandConfigManager**: how axiom sets up Hyprland (`Hyprland` section, `HyprlandConfig` reader). It needs Hyprland's Lua config, 0.55+; axiom's own `hyprctl eval`/dispatch calls are all Lua (`hl.*`, stubs in `/usr/share/hypr/stubs/hl.meta.lua`). One Lua layer covers binds (`binds[]`: an IPC `action` or `exec`, `description` "Axiom: …"), required settings (`allow_session_lock_restore`, a named rule suppressing `maximize` requests, a `workspaces` animation), themed borders, blur and monitor profiles (see MonitorManager). `mode` picks how it gets there:
  - `detached`: `hyprctl eval` at startup and on every `configreloaded`, skipping keys `hyprctl binds -j` shows taken (`components/methods/HyprBinds`: `keyId`, `runtimeBinds`, and `userKeyCounts` for KeybindManager). The keys it bound live in Hyprland's Lua state (`AXIOM_RUNTIME_KEYS`), which a Hyprland reload resets along with the binds and which survives a qs reload. They are unbound before the binds are read.
  - `included`: `moduleLua()` goes to `$XDG_STATE_HOME/axiom/hyprland.lua`, a module the user loads with `includeLines`.
  - `managed`: `managedLua()` becomes `~/.config/hypr/hyprland.lua` itself (plus the `managed` options; `matchAxiom` takes window rounding and border width from `Appearance.shape`, rewriting the file when they change), loading `user/*.lua` after it via `require("user.<name>")`. Hyprland watches required files, so user edits reload it; `user/lib/` is for shared modules. The user's own setup is this: `user/` is a symlink to `~/repos/dotfiles/hypr/user`. `scripts/claim_hyprland.sh` (`check` for `checkManaged()`, `claim` for the takeover) refuses a symlinked or git-tracked dir, and treats a `hyprland.lua` that is Hyprland's example config (`/usr/share/hypr/hyprland.lua`, give or take whitespace; `$AXIOM_HYPR_EXAMPLE` in tests) as `stock`: `claim` only backs it up (`replaced`) instead of adopting it into `user/`, since its binds and `hl.monitor` rule would fight axiom's.
  - The `managed` options become one `hl.config({...})` through `components/methods/HyprLua` (pure), driven by schema annotations: `x-hypr` (the option's dotted path, or a list), `x-hyprScale` (integers shown scaled: 0.01 for a percent), `x-hyprValue` (`int`, `number` for numeric enums, `emptyIsDefault`, `color` for a theme color name, with `x-hyprAlpha`), `x-hyprIf` (a boolean sibling gates it) and `x-hyprAlways`. A field is written only when it differs from its default (Hyprland's own), so a new option is just a schema entry. `managed` stays flat (the settings page nests one level): its cards come from `x-group`/`x-order`. Not mapped: `animationPreset` (`hyprland` writes nothing; `axiom` follows `Appearance.animFast/Normal/Slow` and turns animations off with motion; `snappy`/`bouncy`; `custom` from `curves`/`customAnimations`), written after `axiom.setup()`, plus `env` and `autostart` (after axiom in the start hook) and the cursor.
  - Both file modes write only on change, then `hyprctl reload` (Hyprland doesn't watch `dofile`d files).
  - An `AXIOM_INCLUDED` global tells axiom the file is loaded. When it isn't, the runtime layer stands in and `problem` says why.
  - The settings page's Hyprland category starts with `HyprlandStatusCard`, built from `status` (`runtime` | `loaded` | `fallback` | `pending`) and `problem`. A mode picked there waits for Save (`x-applyOnSave`), and the card outlines what saving will do, predicting a managed takeover with `checkManaged()` (`managedCheck`: `ours` | `adopt` | `new` | `blocked`, a dry run of `claimManaged`).
  - `binds` are edited on the Keybinds page, not in settings (see KeybindManager). An action is an axiom IPC call (`_actions`, including the `audio`/`media` targets on AudioManager/MediaManager, so the OSD shows) or a Hyprland dispatcher bound directly (`_dispatchers`: focus/move/resize, close, fullscreen, floating, pin, special workspaces, mouse drag/resize on a `mouse:272` key, which Hyprland makes a mouse bind by itself; `exitHyprland`; and `terminal`/`fileManager`/`browser`, which exec `Apps.terminalCommand` etc., so the binds follow the `Apps` section's `terminal`/`fileManager`/`browser`, empty being the system default; `mediaStop` etc. on `media`). `screenshot` (argument `region`/`window`/`screen`) goes to **ScreenshotManager** (IPC `screenshot take <kind>` / `cancel`, launcher `/screenshot`, and the Screenshot card), with no grim or slurp (the chat's region attachments use it too, through `pick(path, callback)`, which saves to a path and calls back instead of copying): `shell/Screenshot` shows `surfaces/screenshot/ScreenshotPickerWindow` while `picking` (a frozen `ScreencopyView` frame per screen, `axiom-screenshot` layer rule with `no_anim`; the window under the cursor highlighted from the start (`HyprlandManager.withCursorPos`); `region`: drag a region or click a window, the screen off one; `window`: click a window; cropped through a `ShaderEffectSource` + `grabToImage` at the buffer's resolution; `screen` grabs at once on one screen), saved to `<Pictures>/Screenshots` (or only a runtime file with `copyOnly`, in `config/state/screenshot.json`), copied with wl-copy, then notified (with an "Edit in Satty/Swappy" button: a waiting `notify-send -A`, only the latest one live) or opened in satty/swappy straight away (`annotate`, the picker's "Edit in …" switch / E / Shift on release). One 3 s watchdog in the service fails a capture that gets no frame (a picker reports its frame with `frameArrived()`; an immediate `screen` capture must also report back), so nothing can wedge it. Recording lives there too, not in the card, which the overlay destroys when it closes: `toggleRecording(dir)` opens the same picker with kind `record` (no save/annotate controls; R or its Screenshot / Record switch, `setRecordMode`, flips an open picker between the two), whose pick goes to `record(area, screenName)` (global logical `-g`, or `-o <screen>` for a whole screen) and runs wf-recorder until `stopRecording()` (SIGINT to its own process; `pkill` only for one left from before a reload); the exit notifies the saved file (click opens it) or the failure. Entry points: IPC `screenRecord` (`toggle`/`enable`/`disable`/`status`), the `screenRecord` bind action (with a call), launcher `/record`, the card's Record tile. While it runs, `recordingElapsed` ticks for the `ScreenRecord` bar widget (hidden otherwise; click stops), and the Privacy widget's screen indicator shows it (wf-recorder uses screencopy, so Pipewire never sees it). Binds carry `repeating`/`locked`/`release` flags, preset from `actionFlags` when the action is picked.
  - Created from `shell.qml`'s `_services`, since other services don't reference it. Never switch the user's real config to `managed` to test it: test `claim_hyprland.sh` on scratch dirs (`tests/scripts/test_scripts.py` does), and render the Lua with node and `luac -p`.
- **MonitorManager** — the Monitors page (`views/Monitors.qml`, pieces in `views/monitors/`: `MonitorCanvas`, `MonitorInspector`). `outputs` is `hyprctl monitors all -j`, read at startup and on `monitoradded`/`monitorremoved`/`configreloaded` (never polled). `Hyprland.monitors.profiles` (`x-settings: false`) is a list of `{ name, outputs: [MonitorRule] }`: a layout per set of monitors, each rule's `output` a `desc:<description>` (follows the monitor across ports; the connector name when two share a description, `MonitorLayout.outputId`) with mode, position, scale, transform (0–7: quarter turns, +4 flipped), `disabled`, `mirror` (another rule's `output`), `vrr`, `bitdepth`, `cm`, `sdrBrightness`/`sdrSaturation`. The page edits a `ConfigDraft`; opening it detects (`_detect`: a new profile from the live state when none matches, or the matching one gains any unlisted output), and while it's open a hotplug re-detects unless edited. Tiles snap (`MonitorLayout.snap`: edge to edge, aligned starts/ends/centres, within 14 screen px) but drop anywhere else, so offsets stay possible; the view holds still during a drag. `issues` (overlap and every monitor off block Apply; islands, scales Hyprland will round and, in managed mode, `user/*.lua` files that call `hl.monitor` (`HyprlandConfigManager.monitorConflicts`, whose rules load later and win) warn). **Apply** evals the selected profile's `hl.monitor` calls (`HyprLua.monitorCalls`), snapshots the old state and shows `shell/MonitorPrompt` (`surfaces/monitors/MonitorPromptWindow`, on every screen, outside the overlay whose screen may change): `keep()` saves the draft, `revert()` or 15 s evals the snapshot back. A profile for monitors that aren't connected only saves. Where the profiles reach Hyprland (`HyprLua.monitorsLua`, the same Lua in every mode): `AXIOM_MONITOR_PROFILES` plus `axiom_apply_monitors()`, which picks as `MonitorLayout.matchProfile` does (exact set, where a disabled rule's output may be missing since `hl.get_monitors()` doesn't list it; else the one turning on most; the first profile before any monitor is reported), resets outputs only other profiles mention to Hyprland's defaults, resolves `mirror` to a connector, and runs again on `monitor.added`/`removed` (handlers kept in `AXIOM_MONITOR_SUBS`, removed before re-subscribing). Detached: in the runtime eval, only when the profiles changed or a reload dropped them (`_monitorsApplied`), since re-applying can flicker a modeset; included/managed: `M.monitors()` from `setup()`, so profiles follow hotplugs without qs. `General.primaryMonitor` is set from the inspector at once. IPC `monitors`: `open`, `keep`, `revert`, `identify`; launcher `/monitors`. Never Keep a layout while testing; test the picker through `tests/tst_HyprLua` (`monitors.run.lua`) and harmless evals (re-applying the current settings, or moving a lone monitor's origin and back).
- **KeybindManager** — the Keybinds page: every bind Hyprland reports (`hyprctl binds -j`, grouped by "Section: Label" descriptions), and the editor for axiom's own `Hyprland.binds` (a `ConfigDraft`, saved with `save()`). Per-bind `issues` (no key, bad modifier, missing argument, duplicate, and a key the user's own config binds: Hyprland's binds minus the saved axiom binds it applied, since every Lua bind is an opaque `__lua` dispatcher), `presets` (built from the workspace layout; `applyPreset` skips keys already used) and recording: `startRecording(index)` puts Hyprland in an empty `axiom_record` submap (Hyprland only registers a submap with a bind, so it has an unreachable one, and a Lua timer leaves it after 30 s even if qs dies) so bound combos reach `keybinds/KeyRecorder`; `components/methods/KeyNames` turns the Qt key event into a Hyprland key name.
- **SelfUpdateManager**: axiom updating itself (not packages: that's UpdatesManager). `SelfUpdate.channel` picks what it follows on the clone's remote: `tags` (releases, `v*` tags) or `main` (every commit on the remote's main, else master; the notes are the new commits' subjects). `scripts/self_update.sh [--channel tags|main] check|apply <target>` does the git work and prints one JSON object (`channel`, `current`, `commit`, `latest` (the tag, or main's short commit), `state`: `uptodate` | `available` | `diverged`, `ahead`, `behind`, `blocked`: `dirty` | `diverged` | `branch` | `nogit`, `notes`, `error`). It only fast-forwards (`merge --ff-only`, or a detached `checkout` when detached) and never stashes, resets or forces; switching back from `main` to `tags` is never a downgrade (ahead of the newest tag is `uptodate`). A channel change rechecks. `SelfUpdate.mode`: `auto` applies, notifies and `Quickshell.reload`s (git replaces files by inode, which the watcher misses); `notify` sends a notification whose `desktopEntry` (`axiom-update`) is a `NotificationManager.registerHandler` key, so clicking it runs `openSettings()` (Settings → Updates, the `SelfUpdateStatusCard`); `off` never checks. Checks run once per qs launch (a `PersistentProperties` flag, so hot reloads don't recheck) and daily. `config/state/selfupdate.json` keeps `lastChecked`, `notifiedTag` (each release is notified once) and the last result. IPC `selfUpdate`: `check`, `update`, `open`; launcher `/update`. Created from `shell.qml`'s `_services`. Test the script on scratch clones; never `apply` on the live repo.
- **BrightnessManager** — brightness per monitor (`displays[screenName]`: `backlight` for an `eDP`/`LVDS`/`DSI` screen, from `/sys/class/backlight` and written with `brightnessctl`; `ddc` for monitors `ddcutil detect` maps to a DRM connector, VCP 0x10). Detected at startup and on screen changes, read then and when the OSD opens (`refresh`), never polled. `set`/`stepBy` update at once and coalesce writes per monitor (one process in flight, latest value next). `brightnessChanged(name)` fires only for axiom's own sets, so the OSD opens on them. IPC `brightness`: `up`, `down`, `set <percent>` on the focused monitor (bind actions `brightnessUp`/`brightnessDown`). Created from `shell.qml`'s `_services`.
- **NotesManager**: notes are Markdown files in `NotesConfig.directory` (`Notes.directory`; empty is `config/state/notes/`, gitignored, and a linked folder is never created). Paths are relative to it and `clean()` refuses any that leave it. `acquire(path)` returns a shared, counted document (`text`, `edit(text)` saving 600 ms later, `flush()`), so modules on one note stay in sync; `release(path)` flushes. A change on disk reloads a document unless it has edits waiting, which win. `createNote`/`createFolder`/`rename`/`trash` (`gio trash`, else `rm` behind a confirm) run argv processes and emit `moved`/`removed` for the modules showing them; `allNotes` (a `find`) feeds the `notes` `x-options`. At startup it moves pre-v17 `config/state/note-<name>.json` files to `<name>.md` (keeping `*.json.migrated`). `content/Notes` edits through `parts/notes/NoteEditor`: blocks from `methods/NoteMarkdown` (lossless: `serialize(parse(t)) === t`, and edits touch only their lines), a paragraph (split at blank lines, which stay with the paragraph above; a code fence is never split) or a task line with a checkbox, modelled by count and re-read in place on structural edits (Enter, Backspace/Delete across blocks, toggles, the toolbar, a typed `- [ ] ` or text after a blank line: `needsReparse`), never per keystroke. Every structural edit re-parses (`_normalize`), so blocks are always what `parse()` gives. A `NoteBlock` shows its Markdown rendered (`Text.MarkdownText`) unless it's focused or holds the find match; its clickables are `MouseArea`s, which accept the press so the editor's background `MouseArea` (focusing the note's end) never sees it: inside a `Flickable` an exclusive-grab `TapHandler` is cancelled and a passive one lets the press through. `NoteBrowser` walks the folder with a `FolderListModel`, and its search field lists `NotesManager.search(query, cb)` results (name matches, then `grep -F` lines, 0-based). Ctrl+F finds in the note (`NoteEditor.find`/`endFind`). Launcher `/notes` searches too and opens a result through `requestOpen(path, line, place)`: the overlay page with a Notes module, else an edge menu with one; the module whose `placeKey` matches shows it (`openRequested`, or `takeReveal` when it loads within 5 s). The last note per place (`overlay`, `edgeMenu:<id>`) is in `config/state/notes-modules.json`; `lockNote` pins a module to its `note`. Created from `shell.qml`'s `_services`.
- **OnboardingManager**: the first-run onboarder (`shell/Onboarding` → `surfaces/onboarding/OnboardingWindow`, pages in `onboarding/pages/`). It opens when there was no config.json (`ConfigManager.firstRun`, set by `_existsCheck`), and after a restart until finished or skipped (`config/state/onboarding.json`: `{ completedVersion, step }`; a config with no state file is never prompted; bump `version` for a page worth showing existing users). The step and the chosen Hyprland mode live in a `PersistentProperties`. The window is a `hosts/overlay/ReservedAreaWindow` like the overlay's, with the same `OverlayGrid` (so the Welcome page's `Overlay.size` shows on it), and the step bar is the overlay's `OverlayPageNavigator`. Pages apply as the user goes (`SettingsManager.commitValues({ dottedPath: value })`, or `forms/SettingRows`, which shows config paths as `SchemaField` rows and saves them debounced); only the Hyprland mode waits for Finish. The Hyprland page reads `configState` (`none` | `stock` | `custom` | `ours` | `blocked` | `legacy`, from `checkManaged()` plus a `hyprland.conf` check) and recommends `managed` for a stock or missing config, `included` otherwise. It reuses the Monitors view, `WallpaperPicker` and `ThemeEditor` as they are; the Look page's folder check, create and open are `WallpaperManager.checkFolder()` / `folderImages` / `createFolder()` / `openFolder()`. `DependencyManager.check(commands)` / `found` / `tools` say what's installed. IPC `onboarding`: `open`, `close`, `reset` (opens at the next start), `goTo <step>`; launcher `/welcome`; Settings → General's `OnboardingCard`. Test it with `ipc call onboarding goTo <n>` and grim screenshots, never by deleting the real config.json.
- **HypridleManager**: hypridle run by axiom (`Idle` section, `Idle` reader; off by default, the onboarder's Integrations page recommends it). While `Idle.enabled` it renders `components/methods/HypridleConf` (pure: a general block, then dim/lock/screen-off/suspend listeners in timeout order, 0 being off, then the user's `listeners`) to `$XDG_STATE_HOME/axiom/hypridle.conf`, writing only on change, and runs `hypridle -c` on it, stopping any other hypridle (hypridle doesn't watch its config, so a change restarts it). Turned off it stops its own and starts a plain `hypridle` again when `~/.config/hypr/hypridle.conf` exists; the user's file is never touched. Nothing is polled: `pgrep` on each apply and once 15 s after startup (`replacedOther` when a second hypridle turns up beside ours). Locks through `lockscreen lock` (in `none` mode `Lockscreen.lockCommand`, unless it's `loginctl lock-session`), dims through `brightness dim <percent>`/`undim` (every monitor, silent, so no OSD), DPMS through `hl.dsp.dpms({ action = … })`. Managed mode's autostart skips a plain `hypridle` entry while it's on. Settings → Idle starts with `IdleStatusCard`. Created from `shell.qml`'s `_services`. Ask before enabling it on the live config: it replaces the user's running hypridle.
- **ClipboardManager**: the launcher's clipboard history (`:` or `/clipboard`; `Launcher.clipboard`, on by default, also on the onboarder's Integrations page; turning it off clears it). `Launcher.clipboardSource` `axiom`: a `wl-paste --type text --watch` process records text clips while it's on, split at ASCII RS, skipping any whose `CLIPBOARD_STATE` isn't `data` (a password manager's `sensitive`), de-duplicated and capped at `clipboardMaxEntries`, in memory only (a `PersistentProperties` holding JSON, since a JS array can't cross into the reloaded engine; never on disk). `cliphist`: `cliphist list` on each `:` query (at most once a second; an unchanged list changes nothing, or the rows would loop), while axiom runs `wl-paste --type text|image --watch cliphist store` itself (cliphist drops duplicates, so a user's own watcher is harmless; text-only misses screenshots and keeps only a browser image copy's HTML). The newest 50 images are decoded as thumbnails into `$XDG_RUNTIME_DIR/axiom/clipboard/` (pruned to the listed ones, removed when off) and copied back with `wl-copy --type image/<format>`; HTML that is just an `<img>` is decoded for its `src` (the listed preview is cut at 100 chars) and previewed from it. No listing runs while a `cliphist delete` is in flight, or it would bring the entry back. Launcher row text is `Text.PlainText`, since clips can hold markup. `copy` pipes the text to `wl-copy` on stdin (cliphist: `cliphist decode <id> | wl-copy`), never argv, as `copyText(text)` does for every other text copy in axiom; Shift+Enter on a row `remove`s it. Created from `shell.qml`'s `_services`.
- **EmojiManager**: the launcher's emoji (`;` or `/emoji`; `Launcher.emoji`, on by default). `entries()` reads `config/json/emoji.json` on first use: `[{ e, n: name, g: group, k: [keywords] }]`, fully-qualified emoji without skin tones in Unicode's order, generated by `scripts/generate_emoji.py` (stdlib; downloads emoji-test.txt and CLDR's English annotations) and committed, so nothing downloads at runtime. LauncherManager scores them (name, then keywords and group only on a real match, plus frecency from `usage`, in `config/state/emoji.json`). Enter `copy`s through wl-copy; Shift+Enter also `type`s it with `wtype` (optional, `canType` from `DependencyManager`) 150 ms later, once the launcher has let go of the keyboard. A bind opens it with the `launcherSearch` action and argument `;`.
- **WallpaperManager**: what changes the look on its own. `Appearance.wallpaperMode`: `fixed`; `rotate` (`wallpaperRotation`: `interval` minutes, `random`/`sequential` via `methods/Schedules.nextWallpaper`, `sameOnAll`; the last change time is a `PersistentProperties`, checked every 30 s; IPC `wallpaper next`, bind `nextWallpaper`, launcher `/nextwallpaper`); `variant` (`variantWallpapers.dark`/`light` on every monitor, following `Appearance.darkMode`). Automatic changes regenerate only while a generated theme is active; picks by hand (`pick(url, monitor, variant)`, from `WallpaperPicker`) always do. Batch writes go through `ThemeManager.setWallpapers(map)` → `ConfigManager.setWallpapers` (one save). Also `Appearance.themeSchedule` (light from `lightAt`, dark from `darkAt`), through a `services/DailySchedule`: it fires `due(inWindow)` only on edges (window opens/closes, turned on, times moved across now), so a switch by hand lasts until the next edge; its last state survives reloads. The Themes page edits all of it inline (`WallpaperPicker`'s Fixed/Rotate/Light-Dark switch, `ThemeEditor`'s Auto) through `forms/SettingRows` (dotted-path `SchemaField` rows saved by `SettingsManager.commitValues`). Created from `shell.qml`'s `_services`.
- **NightLightManager**: the night light (`NightLight` section, `NightLight` reader, `views/settings/NightLightStatus` as its `x-intro`): `hyprsunset -t <K> [-g <gamma>]`, or wlsunset pinned to one temperature, started detached and stopped with `pkill`; `active` is a `PersistentProperties` (probed with `pgrep` once per launch, `_probeOnce`, however the tool becomes known; the schedule waits for it). A `DailySchedule` turns it on at `startAt` and off at `endAt`; a new temperature/gamma restarts it while on. IPC `nightLight` (`toggle`/`enable`/`disable`/`status`), bind `nightLight`, launcher `/nightlight`, the QuickActions tile. Created from `shell.qml`'s `_services`.
- **DockManager**: the docks (`Dock` section, `DockConfig` reader; `enabled` off by default; `docks` is `[DockEntry]`, edited on `views/settings/DockListCard`, the section's `x-card` in its own `Dock` settings category). `shell/Dock` builds one `surfaces/dock/DockWindow` per enabled dock per screen (`DockConfig.screensOf`: its `monitor`, `"*"` for all). `itemsFor(dock, screen)` groups `HyprlandManager.windowList` by app (`appKey`: `DesktopEntries.heuristicLookup(class)`, else the class) through `methods/DockLayout` (pure: `buildItems` (pinned first, then running with `showRunning`), `inScope` (`windowScope`: `all` | `monitor` | `workspace`), `clickTarget` (focus the most recent, cycle when one is focused), `magnifiedSizes`, `covered`); delegates are keyed by the joined keys. Pinning from the dock (right-click `DockMenu`, dragging icons; off the dock unpins) saves at once through `SettingsManager.commitValues`. `DockWindow` is an Overlay-layer `axiom-dock` strip (arranged after the Top-layer border and bars, and by its layer rule's `order = -1` after floating bars: it sits inside them and never shortens the bars on other edges; blurred; hidden under fullscreen) as deep as the magnified icons, masked to the box. At `edgeDistance` 0 the box is an `AttachedSurface` joining the border's or a solid bar's stroke (`-borderWidth` edge margin, as EdgePopout), straight off a bare edge, and a plain box beside a transparent/pill bar; `visibility`: `always` (`reserveSpace` sets its zone), `hover` (an `EdgeTrigger`) or `intellihide` (hover, plus shown while no window on the monitor's workspace covers it: `obscured`, placed from the monitor's `reserved` via `lastIpcObject`). A dock reports what it reserves (`setZone`/`zoneOn`, per screen edge), and what would otherwise be pushed in by it reaches past it: `EdgePopout` (the OSD, floating edge menus: on its own edge and at both ends; its `axiom-edge-popout` layer rule `order = -2` draws it over the dock) and the border's corner pieces (`RoundedBorders.cornerMargin`). Hyprland sends no event when windows retile around a changed zone, so `refreshSoon()` re-reads monitors and windows after layer and zone changes (layer events only while a dock is built). IPC `dock`: `open`/`close`/`toggle <id>` (empty: every dock; not `show`, which qs's CLI takes), bind action `dock`.
- **IdleInhibitManager** — shared caffeine state (a `PersistentProperties`, so it survives QML reloads but not restarts) + `idleInhibit` IPC target; the Wayland inhibitor itself lives in `shell/IdleInhibit.qml`, which maps a 1 px click-through Background-layer window on the primary monitor while it's on (it needs a surface), so it works without the bar widget.
- Other domain services (AudioManager (also every write to a Pipewire node: `setNodesVolume`/`setNodesMuted`, and `matchStreams(apps, other, excluded)`, the OSD app bars' stream matching), BatteryManager (also the power profile, `level` against the `Battery` section's thresholds (`BatteryConfig`; the Battery widget and module colour from it), and the low battery notifications, once per drop into low and then critical, whatever bars exist; created from `shell.qml`'s `_services` so they run without a widget), KeyboardLayoutManager, MediaManager (MPRIS), NotificationManager, HyprlandManager, StateManager, BarManager, LauncherManager, SettingsManager, SavedConfigsManager, AuthManager, LockManager) follow the same singleton pattern. Services are named `*Manager` — one owns polling/IPC/process-spawning for its domain and exposes readonly properties + signals.

## Config layer (`config/*.qml`)

Also `pragma Singleton`, but these are typed config *readers*, not owners — one per config section, exposing `readonly property` values from `ConfigManager.config`. No `??` fallbacks: the schema defaults are already filled in. Readers: `General` (displayName, primaryMonitor, `monitors`/`screens`, `screensNamed(name)`: that screen, else the primary, else the first), `Idle` (hypridle, see HypridleManager), `Appearance` (theme, font, shape, motion tokens), `Widget`, `Bar` (from `Bars`; the first bar is primary; `edgeName(location)` gives a `Bar.Location` as `"top"`…`"right"`), `PopoutConfig` (open/dismiss delays, edge trigger size — shared by bar and edge popouts), `OSDConfig` (the OSDs: shared scroll settings plus `osds`, `definitions/OSDEntry` each with its own `monitors`, `placement` (`edge`: an `EdgePopout` at `edge`/`position`; `floating`: a `FloatingPopout` with its centre `x`% across and `y`% up the work area), orientation, timeout and `bars`, each typed `master` | `other` | `microphone` | `brightness` | `app`, drawn by `surfaces/osd/OSDBar` in `OSDContent`; a change opens every OSD holding that bar (`OSDTriggers`), and Other apps skips the App bars of every OSD. Edited on the section's `x-card` `views/settings/OSDListCard` (tabs, a placement picker with presets, Show through `ShellManager.showOsd(id)`); the App field's chips come from `x-suggestions: "audioApps"`, `SettingsManager.suggestionsFor`), `LauncherConfig` (launcher placement, size and providers), `Apps` (the terminal, file manager and browser that binds and the launcher open), `NotificationsConfig` (the toasts' corner and gaps, measured inside the work area by an Overlay-layer anchor window with Normal exclusion, like `OverlayPanel`), `OverlayConfig` (views + card-grid constants), `EdgeMenusConfig` (edge menus), `IconConfig`, `ChatConfig`, `ThemeIntegrations`, plus `Paths` (derived filesystem paths from `$HOME` / `Quickshell.shellDir`, not configurable) and `Theme`. Readers whose section name collides with a type get a `Config` suffix (`Popouts`, `Overlay`, `Icons`, `OSD`, `Launcher`, `Notifications`). UI code should read colors/settings from these (`Theme.background`, `Widget.padding`, `Bar.bars`) rather than reaching into `ConfigManager.config` directly.

**Animation timing is uniform:** every `duration:` uses `Appearance.animFast` / `animNormal` / `animSlow` (derived from `Appearance.motion.speed`, and 0 when `motion.enabled` is off), never a literal. Looping animations also gate `running` on `Appearance.animations`. Only behavior timings (cursor blink, notification timeout, polling) stay as literals.

`config/Theme.qml` exposes the base16 palette (`base00`-`base0F`) plus semantic aliases (`background`, `accent`, `error`, etc.) resolved through `_themeData.semantic`, and a `stringToColorMap` + `resolveColor(name)` for dynamic color lookup by string (used when a color name comes from JSON/config rather than a static binding).

`config/json/config.schema.json` is the single source of truth: shape, `default`s, and — via `title`/`description`/`minimum`/`maximum`/`enum`/`x-options` — the settings page, which is generated from it (`views/Settings.qml`; `x-settings: false` hides a key, `x-category` on a top-level section names its sidebar category, `x-links` lists page types it links to: `Themes`, `OverlayEditor`, or a view type). Adding a setting = add it to the schema (with a default) and a reader property. `x-options: "colors"` makes a string a color picker over `base00`–`base0F` (read it with `Theme.resolveColor`, which also accepts semantic names and hex); `x-hosts` on an overlay module lists where it may be placed (`overlay`, `edgeMenu`; both when left out); `x-showIf` hides a field unless a sibling has a given value (a key starting with `/` is a dotted path from the config root instead, e.g. `"/Workspaces.layout"`, read through `SettingsManager.configValueAt`; evaluated by `SchemaField` itself, so it works in every form; on a nested object it hides that object's settings cards); `x-applyOnSave` keeps a setting in the settings draft until Save instead of applying it live (Hyprland's `mode`, since it can take over files). `x-multiline: true` edits a string in a growing text area; integers render through `forms/SchemaNumberField` (a slider with a value box for 7–200 steps, otherwise a stepper beside the label with ±10 buttons past 20 steps; stepper clicks commit debounced, the slider on release), with `x-unit` (`px`, `%`, `ms`, `s`, `min`, `days`, …) shown after the value instead of in the title, and `x-control: "slider" | "stepper"` overriding the choice; `x-order` on an object schema lists the keys its form (or its settings cards, whose order is their first field's) shows first (a schema reaches QML as a map, whose keys come out sorted). On the settings page, `x-group` puts a field on a card of that name (so one section or object can make several cards) and a section's `x-card: "<Name>"` adds the hand-built `views/settings/<Name>Card.qml` as its first card (the Hyprland category's `HyprlandStatusCard`; `OSDListCard` and `DockListCard` fold like generated cards, keyed `<Section>:<Name>`), while `x-intro: "<Name>"` puts `views/settings/<Name>.qml` at the top of the section's own card, above its fields (NightLight's `NightLightStatus`). Clicking a card's header folds it (`SettingsManager.collapsed`, keyed by the group's `key`, saved to `config/state/settings.json`; search results never fold). The masonry reads `layoutFolds`, a snapshot taken on category/search change and page unload, so a fold doesn't reshuffle the page. Flat objects (array items, widget/module options, the bar's own fields) render through `forms/SchemaPropertiesForm.qml`; only the settings page builds its own rows (`methods/SchemaLayout`: categories → groups → rows). An `array` whose `items` is an object schema renders as an add/remove/reorder list of those fields (`SchemaArrayItem`). There is no separate defaults file. The live file is `config/user/config.json` (gitignored, UI-owned); bump `version` and extend `ConfigMigration` when changing its layout. Theme JSON files live in `config/themes/*.json` (static) and `config/themes/generated/*.json` (generated from wallpaper). `config/json/theme-defaults.json` is the one fallback palette and semantic → base16 map (dark and light), read (through `ThemeManager.defaults`) by `Theme` for keys a theme omits and for a missing theme, and by `scripts/generate_theme.py`. The `scripts/theme_*.sh` integrations share `scripts/lib/theme_env.sh`: dependency checks; `load_theme`, one jq pass that fills what a theme leaves out from `theme-defaults.json`, as `Theme` does; `export_theme_colors` (every semantic color as `UPPER_SNAKE`, plus `ANSI_0`–`ANSI_15`); and `render_template`/`write_atomic`. Each writes only its own `axiom.*` file and never edits a user's config: its header and schema description give the line to add. A main config that's missing may be created with that line (cava's config, GTK's `gtk.css`); one that exists, or a symlink, is never touched. A new integration is a script, a schema boolean, a reader property and an entry in `ThemeManager._integrations`.

## Translation (`config/I18n.qml`)

`General.language` picks the language. English is the source language: user-visible text is written in English, inline, as `I18n.tr("Text")`.
- **Dynamic values** use placeholders, so the whole sentence stays one key: `I18n.tr("{0} updates", count)`. Don't build sentences with template strings.
- **Dates and times** go through `I18n.formatDate(date, format)`, never `Qt.formatDateTime`, so day and month names follow the language. Named formats come from `I18n.dateFormat("longDate" | "mediumDate" | "shortDate" | "monthYear" | "fullDate" | "dateTime" | "time24" | "time12")`.
- **The schema form translates itself.** The generic `Schema*` form widgets translate their own `label`/`title`/`description` and dropdown option labels. Callers pass English, and schema titles and descriptions need no code.
- **Adding a language** means adding `config/i18n/<code>.json`: `{"_meta": {"name", "locale", "formats"}, "strings": {english: translation}}`. It then appears in the language dropdown (`x-options: "languages"`).
- **Missing entries fall back to English.** The active dictionary reloads live when edited.
- **Checking coverage.** Run `scripts/check_i18n.py` after changing text; it lists missing and unused entries (`--fill` adds the missing ones empty, `--untranslated` finds UI literals not wrapped in `tr()`).
  - Keys only chosen at runtime (e.g. `I18n.tr(form.shape)`) must be declared in a comment next to the call, as `I18n.tr("square") ...`, so the checker sees them.
- **Leave developer-facing strings in English:** logs, validation errors, migration notes.

## Bar / widget composition pattern

`shell/Bar.qml` renders one `BarPanel` per entry in `Bar.bars` (a `Variants`/model), so multi-monitor / multi-panel bars are data-driven from config, not hardcoded. Each module's options live under its `<Type>Widget.properties.properties` definition in the schema. `SchemaValidation` picks the `BarWidget` oneOf option by `type`, so widget properties get their defaults filled like the rest of the config and modules read `properties.<key>` directly. The bar editor (`views/BarEditor.qml`) has no preview of its own: edits show live on the running bars (see `ConfigManager.previews`) and Save writes them. Its `DragLayer` owns the one drag in progress (`begin`/`move`/`end`, hit-testing the registered `SectionLane`s) and the ghost chip, above both the `SectionsBoard` (five lanes of `WidgetChip`s, dragged within and between sections) and the `WidgetInspector` (the selected widget's options with the same `SchemaField` rows as the settings menu, plus `LayoutOverrideField`s; with nothing selected, the widget library to drag from). `WidgetGroup` models its widgets by count, so live option edits reach a widget in place instead of rebuilding the section. The main-axis layout math (sections placed along the bar, the widgets hidden when it overflows, elastic widgets squeezed within a section) is pure, in `methods/BarLayout` (tested in `tst_BarLayout`); `BarContainer` and `WidgetGroup` only feed it measurements. Bar contents are built from `components/bar/{BarContainer,BarWidgetHost,WidgetGroup,BarPanel}.qml` composing widgets from `components/bar/widgets/<type>.qml` (Time, Battery, Network, Workspaces, Media, SystemTray, Notifications, etc.). A widget opens a popout by dropping in a `PopoutAnchor` with a `popoutName`; the per-bar `BarPopouts` (in `hosts/popout/`) loads `content/<popoutName>.qml` by URL, so a new popout is a content file plus an anchor.

## Workspaces (`Workspaces` section, `WorkspacesConfig`)

One layout serves everything that shows or moves between workspaces: the `Workspaces` bar widget, its `WorkspaceGrid` popout, the workspace overview (`surfaces/workspaces/`), the `WorkspacesMap` module, the launcher's `/ws` and the `workspaces` IPC target.
- **Layouts.** `standard` is ids 1..`count`, shared by every monitor. `perMonitor` gives each monitor its own block of `count` ids and `grid` one of `columns × rows`, numbered in a stable monitor order (`WorkspaceGeometry.orderMonitors`: the primary first, then by output identity; `WorkspacesConfig.baseFor(index)`). Nothing else holds a workspace count or grid size.
- **Ids.** `HyprlandManager.workspaceBase(monitor)` / `workspaceIds(monitor)` give a monitor's ids. The overview lays them out `boardColumns × boardRows`; in the standard layout it shows windows from every monitor, each placed against its own monitor's origin.
- **Navigation.** Everything goes through `HyprlandManager.goToWorkspace(id, mode, monitor)`, `stepWorkspace(direction, mode)` and `nthWorkspace(n, mode)`, including focusing a window on another workspace (`focusWindow`, used by the overview, dock, launcher and notifications), so every switch slides the same way. Surfaces on a monitor pass their `monitor` (focused first; in a grid an id outside the focused monitor's block is otherwise refused). Never dispatch `hl.dsp.focus({ workspace })` or `{ window }` directly. `mode` is `go`, `move` or `moveSilent`. In a grid it only reaches the monitor's own ids, going sideways, then vertically, a slide along each axis in turn (`animate`; each leg of a two-leg trip at `_legSpeed` of the configured time). The slide briefly overrides Hyprland's `workspaces` animation (read with `hyprctl animations` at startup and on config reload) and puts it back. Keybinds call `qs -c axiom ipc call workspaces …` instead of scripts of their own.
- **Layout changes.** Hyprland's workspaces stay where they are when the layout or size changes, so `HyprlandManager` remaps them (`_remapWorkspaces`, 200 ms after `perMonitorBlocks`/`size` change, from the layout it last applied): `WorkspaceGeometry.remapWorkspaces` (pure, tested) sends each workspace's windows to the same place in its own monitor's new ids (the first in monitor order keeps a contested id, the rest take free ones, merging only when none is free) and picks each monitor's new active workspace. One Lua chunk does it with the `workspaces` animation off: windows to `name:axiom-remap-<id>` (created on their own monitor, so a chain like 10 → 11, 11 → 12 can't merge), every monitor to `name:axiom-remap-mon-<i>` (so its old, maybe empty, workspace is gone before its id is reused), windows to their ids, then monitors to theirs, the focused one last. IPC `workspaces reconcile` runs it for the current layout, re-homing workspaces left outside their monitor's ids.
- **The bar widget.** `bar/widgets/Workspaces.qml` loads `workspaces/WorkspaceStrip` (standard) or `workspaces/WorkspaceGridStrip` (the active row, or column on a vertical bar) by layout. Their options share one schema definition: layout-only options hide themselves with `x-showIf: { "/Workspaces.layout": … }`. In a grid the widget hands its `properties` to the `WorkspaceGrid` popout, which uses the same colors, labels (grid position), app icons and click to switch as the strip.

## Content (loaded by name, shown by hosts)

`components/content/<Name>.qml` holds every loadable panel. The name is the overlay module `type` (`OverlayModule.oneOf`) and/or a bar `popoutName`; one file can be both (AudioMixer, BluetoothDevices, Notifications, NowPlaying, SystemGraphs, Updates, WifiNetworks). Hosts load it by URL and pass their context:
- **Roots.** `Card` (`content/base/`) is a free-form card (box, `properties`, slot context); card-only content uses it. `Panel` lays its children out in a column and works in either host: in a bar popout it sizes to its content with the popout box (`wrapper` set, `hovered` read for dismissal); in a card the host passes `embedded: true`, it fills the slot with the card box, and `compactContent` (e.g. a `StatFigure`) replaces the column in a quarter slot. A popout with a text field sets `wantsKeyboardFocus` (BarPopouts then takes a focus grab and the bar takes keyboard focus on demand; a click outside emits `focusLost`). Both expose `properties`, `slotRect`, `cols`/`rows`, `shape`, `compact`, `pad`.
- **Hosts.** `hosts/overlay/OverlaySlot` (card: `properties`, `slotRect`, `embedded: true`) and `hosts/popout/BarPopouts` (popout: `wrapper`, then, once loaded, the anchor's payload keys copied onto matching properties, so popouts declare what they take rather than reading `wrapper.currentData`). The tray's menu (`content/SystemTray`) is the one popout-only content rooted in a plain Item: it drives `TraySubmenuWrapper` through `wrapper`.
- Pairs that look different by design stay separate files: `Weather` (card) / `WeatherForecast` (popout), `ClockCalendar` / `Calendar`.

## Overlay composition (views → columns → cells → modules)

`Overlay.views` in the schema drives the overlay's pages, just as `Bars` drives the bar. Views are made of columns, columns of cells, and cells of modules. Everything loads by naming convention, so there are no lookup tables:
- **View** (`OverlayPages` → `OverlayView`): `components/views/<type>.qml`, a `BaseView` that receives the screen's `grid` and its `viewConfig`. `Custom` (`views/Custom.qml`) places its `columns` side by side. `Themes`, `Keybinds`, `BarEditor`, `Settings`, `Monitors`, `OverlayEditor` and `EdgeMenuEditor` are hand-built pages, with their pieces in `views/<page>/` (`barEditor/`, `keybinds/`, `settings/`, `monitors/`, `overlayEditor/`, `edgeMenuEditor/`). `ShellManager.showOverlayPage(type)` switches the overlay to a page (`qs -c axiom ipc call overlay page <type>` opens it on one).
- **Column** (`OverlayColumn`): just `{ cells: [...] }`. The cells flow left to right and wrap at the column's widest cell, so Singles after a Wide sit side by side under it; an empty Single acts as a gap. `OverlayConfig.columnFlow(cells, unit, target)` (pure, in `methods/OverlayLayout` with the layouts, `span`, `slotShape`, `moveTo` and `remapSlots`; tested by `tst_OverlayLayout`) computes the arrangement: `OverlayColumn` places its cells from it (no `Flow`), and the editor preview uses it for sizing. A cell grows into `target` room (`{ width, height }`): with `fillWidth` into the rest of its row, with `fillHeight` to its row's height and spare column height split evenly between rows holding one, so two fillHeight cells around others centre them. `OverlayCell` sizes its slots from its real size, while modules keep the layout's `slotRect` (shape and fit checks don't change). `Custom` passes the tallest column's height (pages never grow); `EdgeMenuBody` passes the whole edge (`maxLength`) once a cell fills along it (fillHeight on left/right edges, fillWidth on top/bottom, where spare width goes to the columns holding one). The editor draws natural sizes with a fill badge (`ColumnsEditor.setCellFill(c, k, key, fill)`, the inspector's Fill width / Fill height switches).
- **Cell** (`OverlayCell`): `layout` names an entry in `OverlayConfig.layouts` (defined in `methods/OverlayLayout`). Each entry is `{ cols, rows, slots: { name: [col, row, colSpan, rowSpan] } }` on a half-card grid, and `span(n)` converts half units to pixels. `Tall` (two cards high) and `Wide` (two cards wide) hold panel-sized modules; `HalfWide` (2×1) and `HalfTall` (1×2) are half-card cells. Adding a layout means one entry there plus the `OverlayCell.layout` enum in the schema.
- **Module** (`OverlaySlot`): `content/<type>.qml`, filling its slot. Its root is `Card` (box, `properties`, slot context; override only what differs, like `color`) or `Panel` (see Content). Titled scrolling panels (ThemeEditor, the bar editor panels, the settings page's content) use `TitledCard`, which has a `CardHeader` with `title`, `dirty`, `save()`/`reset()`, `headerExtras`, and children that go into the scrolling body. Adding a module means the file plus an `…OverlayModule` definition in `OverlayModule.oneOf`, with `x-shapes` listing the slot shapes it fits. Shapes are `square`, `horizontal` and `vertical`, taken from the slot's span (`OverlayConfig.slotShape`/`fits`); leaving `x-shapes` out means any shape. The editor only offers modules that fit and treats a misfit as a problem that blocks Save, and `OverlayCell` logs a warning for one. Helpers used only by content go in `content/parts/` (subfolders for groups, e.g. `parts/settings/`). `OverlaySlot` imports `qs.components.content` so that `qs` scans the URL-loaded content; without it, their own `qs.*` imports fail with "not installed".

Views and modules are `oneOf`s discriminated by `type`, like `BarWidget`.

**Sizing:** the card size is per screen, not a constant. Each `OverlayPanel` has an `OverlayGrid` (`hosts/overlay/`) whose `unit` is what fits the page area above the navigator (`min(height / fitCardsHigh, width / fitCardsWide)`, capped at the reference `OverlayConfig.cardUnit` 500, times `Overlay.size`%, never below `minCardUnit`). Views receive it as `grid` (`BaseView`) and size everything from `grid.unit` / `grid.span(n)` / `grid.columnFlow(cells)`, passing plain numbers down to content; `OverlayConfig.span`/`columnFlow` without a unit are the reference size (the editor preview uses them, scaling by hand). A page that still doesn't fit is shrunk as a whole by `OverlayPages.fitScale` (Item.scale, last resort). `cardSpacing`/`cardPadding` don't scale.

**Loading:** one overlay per screen in `General.screens` (`shell/Overlay.qml`): a transparent `OverlayPanel` inside the reserved area (placed by its base, `ReservedAreaWindow`, shared with the onboarder), over a `reusable/ScreenBackdrop` that dims the whole monitor under the bars and border (a Top-layer surface kept under them by a Hyprland `order` layer rule that `HyprlandManager` adds at startup and on config reload; the workspace overview and launcher use it too). Its `HyprlandFocusGrab` also whitelists `ShellManager.grabPartnersFor(screen)`: the bars, bar popouts and tray submenus register themselves there (`registerGrabPartner(window, screenName)`), so they keep working while it's open. Only the current page and its neighbours (navigation wraps) are instantiated, and only while the overlay is open (`OverlayPages.isLoaded` → `OverlayPage.loaded`), so modules must not assume they live forever: acquire in `Component.onCompleted`, release in `onDestruction`, and keep state that must survive in a service. Under the pages, `OverlayPageNavigator` shows a tab per page (`OverlayPages.pages`: icon and name from `OverlayConfig.viewIcon`/`viewLabel`, shared with the overlay editor) with a sliding accent pill; when all names don't fit, the other tabs drop to icons with tooltips.

**Writing overlay modules:**
- **Shape-aware.** `Card` and `Panel` both take what they derive from the slot from `base/SlotContext`, and expose the slot's `slotRect`, `cols`/`rows` (half units), `shape` and `compact` (a quarter slot), plus `pad`. Each module picks its internal layout from these: side by side when horizontal, stacked when vertical, the key figure only when compact.
- **Shared parts** live in `content/parts/`: `ModuleHeader`, `Sparkline`, `StatFigure`, `TileGrid` (lays out `reusable/ActionTile`s, the icon-well tiles the power menu also uses), `RateLabel`, and the radio menus' `RadioHeader`, `DeviceList` (fixed-height in a popout, off and empty states) and `DeviceRow` (confirm-to-forget, connect; extras beside the title and content under it), shared by WifiNetworks and BluetoothDevices. `FigureValue` is the bold value + unit row of `StatFigure` and `CompactFigure`. Generic controls live in `reusable/`: `SectionHeading` (accent title + description, as in `FieldGroup`), `StyledSeparator` (a border-coloured divider), `DropdownSurface` (the bordered, shadowed box of anything that drops down), `FlatIconButton` (fixed-size flat toolbar button), `StyledTabBar`. Byte rates and sizes format through `Utils.formatRate`/`rateParts`/`formatSize`.
- **Content can be both.** A `Panel`-rooted file is a bar popout and a card at once; branch on `embedded` for card-only parts (a header, a mode switch, acquiring with the card's `properties`).
- **Data sources.**
  - `SystemManager` adds `history: true` (60-sample ring buffers), a `net` metric (`/proc/net/dev` rates; the connection itself is `NetworkingManager.netInfo`) and a `processes` metric (two-frame `top`, with `kill(pid)`).
  - Weather comes from `WeatherManager` (acquire with `{ latitude, longitude, location, units, intervalMinutes }`, read `sourceFor(request)`): one `WeatherSource` per distinct location and units, shared by the bar widget and the module.
- **Never derive a Repeater model, or anything passed to `acquire()`, from live values.** Build it from config (and tool availability) only. When the set of items is itself derived, model the Repeater by a joined string key or a count (`model: rows.length`, delegate reads `rows[index]`): an `int`/`string` only notifies when it actually changes, so the delegates survive each sample. A model that re-evaluates on every sample rebuilds its delegates (and Canvases) many times a second. That once pushed qs past 25 GB. `SystemManager.acquire()` now ignores identical re-registrations.
- **Testing a module safely.**
  - The running shell only picks up schema changes on a QML reload, and a reload only fires when a file it has *loaded* changes. A new module file doesn't count until something uses it.
  - A config checked against a stale schema fails validation, and the whole shell falls back to defaults until it's fixed.
  - So confirm the schema was reloaded after your edit before putting a new module into `config.json`. Add modules one at a time and watch `qs`'s RSS.

**Themes page:** `views/Themes.qml`, the `Themes` view type (in `Overlay.views` like any other, with nothing to configure). It's a `Custom` view that overrides `columns` with fixed ones: `WallpaperPicker` (in a Tall slot it adds a monitor picker and a preview, and sets the picked monitor's wallpaper), `ThemeEditor` (the theme list and light mode switch) and the 16 `ColorSwatch`es.

**Overlay editor:**
- `views/OverlayEditor.qml` with its pieces in `views/overlayEditor/`. It's not in config: `OverlayPages` adds it (`pinnedPages`) as a persistent page after the Repeater, so it's always last, can't be removed, and survives the page rebuild that every `Overlay.views` change causes (pages are keyed by the views' JSON, so other config edits don't rebuild them; `_onPinned` keeps the user on it across that rebuild).
- Layout, as in the bar editor: `PagesPanel` (pages, dragged to reorder; Save/Reset; the selected page's name; problems) on the left, and `PageCanvas` above `EditorInspector` on the right, placed by `ColumnsEditorLayout` (an `EditorDragLayer` the edge menu editor uses too; each passes its side panel as a child). `PageCanvas` draws the selected page at a scale it computes itself (not `Item.scale`): `CanvasColumn`s (header grip, cells placed from `OverlayConfig.columnFlow(...).rects`) with `ColumnGap`s between them, `CanvasCell`s (hover grip) and `SlotTile`s. The inspector shows a selected module's options plus its cell's layout thumbnails, or else the `ModuleLibrary` (modules and cell layouts to drag or click).
- `EditorDragLayer` covers the whole page. It owns the one drag in progress and its ghost, like the bar editor's `DragLayer`. Drop targets register themselves with a `targetKind` (`slot` > `gap` > `column` / `pages`, most specific first). Draggables use `reusable/DragArea` (press, a 6 px threshold, then begin/move/end) and pass `{ kind, icon, label, ... }` payloads: `module-add`/`module-move`, `cell-add`/`cell-move`, `column-move`, `page-move`.
- The canvas pieces are shared with the edge menu editor, so none of them names a service: they edit through `dragLayer.editor`, a `services/ColumnsEditor` (non-singleton: one set of columns, its selection, every column/cell/slot edit, `problemsFor(columns, name)`; the owner points `columnsOf` at the columns in its draft and saves on `edited`). `PageCanvas` takes `editColumns` (null: nothing to edit), `title`, `icon`, `emptyText`; `EditorInspector` takes `editable`; a `pages` drop is only reported (`pageMoved`).
- All edits go through `services/OverlayManager.qml`, a draft copy of `Overlay.views` like `BarManager`, whose `layout` is the selected page's `ColumnsEditor`. `problems` blocks Save, and Save merges onto the latest config. Drop places are `{ kind: "column", column, index }` or `{ kind: "gap", index }` (a new column), with indices counted as if the moved item were still in place. `_restructure` tracks cells by identity, so the selection follows what moved, and it removes any column a move empties. Dropping a module on an occupied slot swaps the two (`canMoveModule`: both must fit). Dropping one between cells gives it its own cell (`OverlayConfig.bestLayoutFor`).
- Module and view pickers read `OverlayConfig.availableModuleTypes` / `availableViewTypes`. These come from the schema's `oneOf`s, including `x-shapes` and `x-icon` (a Material Symbols name), so new types show up there automatically. The inspector generates property rows from each module's `properties` schema.
- `reusable/TypePickerPopup` is the shared "pick a type" popup used by both the bar editor and the overlay editor.

## Edge menus (`EdgeMenus` section, `EdgeMenusConfig`, `EdgeMenuManager`)

Menus that pop out of a screen edge, holding overlay modules. `EdgeMenus` is an array like `Bars` (`x-settings: false`, blocked from `/config`: the edge menu editor owns it). Each entry has `id`, `monitor`, `edge`, `mode`, `position`, `cardSize`, style (`padding`, `backgroundColor`/`borderColor` read through `EdgeMenusConfig.colorsOf`, floating `edgeDistance`, integrated `frame`/`margin`), hover (`openOnHover`, `openDelay`, `triggerSize`, `triggerLength`: 0 is the menu's length, `EdgeMenusConfig.lengthOf` from config until it's loaded; `closeOnLeave`, `closeDelay`), `closeOnOutsideClick` and `columns` (`[OverlayColumn]`, the overlay's column → cell → module chain as is). Escape closes a focused menu (`EdgeMenuBody`), and the `edgeMenu` bind action toggles one by id.
- **State.** `EdgeMenuManager` holds which menus are open and pinned (a `PersistentProperties`, so a reload doesn't reflow windows) and the `edgeMenu` IPC target. The menus follow it and report back when they close by themselves. A bar `Button` with `action: "edgeMenu"` and `menu: <id>` toggles one, passing itself as the anchor, so a floating menu stays open while the button is hovered.
- **Hosts** (`surfaces/edgemenu/`). `shell/EdgeMenus` builds one `EdgeMenu` per enabled entry (keyed by id), which `LazyLoader`s the host for its mode. Both put `EdgeMenuBody` inside: a row of `OverlayColumn`s on an `OverlayGrid` with `fixedUnit: cardSize`, scrolling along the edge when it's too long. `EdgeMenu` keeps the last live entry, so the hosts read its (schema-defaulted) fields directly. What both hosts share is `EdgeMenuSync`: following `EdgeMenuManager` (and telling it when the menu closes by itself), held/revealing state, `autoDismiss`, the trigger length, grab-partner registration and the reveal's cursor warp (`warpRequested`, each host warping into its own box).
  - `floating`: `FloatingEdgeMenu`, an `EdgePopout` (`contentPadding`, `edgeOffset`, `fillColor`/`strokeColor`, defaulting to what the OSD uses). It's `detached` (a plain box) when `edgeDistance` > 0 or its edge has a pill or transparent bar, else attached to the border or solid bar.
  - `integrated`: `IntegratedEdgeMenu`, a `PopoutWrapperBase` with a Top-layer `axiom-edge-menu` window along the whole edge. Its layer rule's `order = 7` (above the bars' 5) arranges it first, so it sits outermost and the border, bars and every Normal-exclusion surface move inwards. The zone is set once while it's mapped (windows retile in one step) and the strip slides in. With `frame`, a rounded stroked box runs the strip's whole length, its stroke's inner edge `margin` in from the strip's edges (as the border's is at `screenMargin`, so the two line up), holding the modules `padding` in from its stroke. It reports its zone (`EdgeMenuManager.setZone`), which `BarPopouts.borderInset` takes off the perpendicular bars' length.
- **Editor.** `views/EdgeMenuEditor.qml`, the `EdgeMenuEditor` view type: an ordinary page in `Overlay.views` (in the defaults; the user may remove it, and then `ipc call edgeMenu edit` / launcher `/menus` do nothing), with `edgeMenuEditor/MenusPanel` (the menus, "Show on screen", the selected menu's fields in groups from the `EdgeMenu` schema, problems) on the left and the overlay editor's `PageCanvas` / `EditorInspector` on the right. The draft (`ConfigDraft { path: ["EdgeMenus"] }`, `layout`: the selected menu's `ColumnsEditor` with host `edgeMenu`) lives in `EdgeMenuManager`, and shows live on the running menus through `previews.EdgeMenus` while dirty, as the bar editor's does. "Show on screen" sets `previewing` to the selected menu (following the selection and id renames) and opens it; `isHeld(id)` (pinned or previewing) makes a menu ignore `closeOnLeave` and outside clicks. The page's `onDestruction` (the overlay closing) stops it.
- **Pin.** `content/Pin` toggles `EdgeMenuManager.pinned[host.id]`. While pinned, a menu ignores `closeOnLeave` and outside clicks. Modules learn where they're shown from `host` (`{ kind: "overlay" }` or `{ kind: "edgeMenu", id }`, on `Card`/`Panel`, passed down `OverlayColumn` → `OverlayCell` → `OverlaySlot`). `x-hosts` on a module definition limits where it may go: `OverlayConfig.modulesFor(host)` feeds the pickers, and `OverlayManager.problems` flags a menu-only module on a page.

## Popouts (bar + screen edge)

Shared pieces live in `components/hosts/popout/`: `PopoutWrapperBase` (open/close/queue state, `isOpen`/`show(data)`/`hide()`, hover-loss dismiss timer), `FloatingPopout` (a box floating in the free area at a fraction across and down, fading in; the floating OSD and launcher), `SlideAnimation`, and `AttachedSurface` (the content box + connector + `CornerPiece` fillets that make a popout look like it grows out of a bar or the screen border; `edge` is a `Bar.Location`). Bar popouts (`BarPopouts.qml`) share one wrapper per bar. Screen-edge popouts (`EdgePopout.qml`, used by `OSD.qml`, floating edge menus and the attached launcher) are one independent instance per screen (`Variants` over `Quickshell.screens`). Each is an Overlay-layer `PanelWindow` with Normal exclusion and a `-borderWidth` margin, so it lands on the inner stroke of whatever reserves that edge: the border (`surfaces/border/`) or a bar.

**Bars and the screen border share an edge by layer-shell ordering.** `Appearance.screenBorder` turns the border (`shell/ScreenBorder`: `surfaces/border/RoundedBorders`, four `BorderPanel` strips and four `CornerPiece` corners, layer namespace `axiom-border`) off.
- **Solid bar** (`Bar.background: "solid"`): Top layer, at the screen edge. The border's strip on that edge is arranged after it and overlaps its inner part, so the strip's stroke is the bar's inner edge.
- **Floating bar** (`barConfig.floating`: transparent or pills, with the border on): Overlay layer, whose exclusive zones Hyprland arranges after the Top-layer border. It sits just inside the border with a `-borderWidth` margin, so its outer edge lies on the border's stroke. It hides while its workspace has a fullscreen window. Hyprland counts that margin into the reserved space, so it reserves `extent`. `RoundedBorders.cornerMargin` pulls the corner pieces back out to the border's corners on a floating bar's edge.
- **Pills** (`BarContainer.pillRects`): one per section, merged when they're at most `pillMerge` apart. Each is an `AttachedSurface` growing out of the bar's outer edge, covering the border stroke (`barConfig.overlap`); widgets sit `overlap + pillPad` in from that edge. A pill at an end of the bar joins the perpendicular edge (`joinStart`/`joinEnd`: flush on its stroke, whose far corner meets it with a fillet). The bar window is `borderRadius` thicker than `extent` in pill mode for that fillet, masked to the bar itself. Floating bars take `-borderWidth` margins on both ends too, so bar-window 0 along the bar is the perpendicular stroke's outer edge.
- **Bar popouts** join an end the same way when their alignment would push them back from it. On a pill bar, a popout not wholly within its pill (`BarPopouts.mergeWithPill`) grows from the outer edge instead, deeper by the pill, with the pill's interior showing through the surface's notch (also cut out of the input mask); each side wall lands on the frame, or on the pill's far stroke (`startFoot`/`endFoot`) where the pill carries on past it. On a transparent bar popouts are `detached`: plain rounded boxes, except one pushed to an end (`BarPopouts.cornerAttach`), which attaches to that perpendicular edge instead, joining it on both sides. They're a layer surface of their own (`underWindow`, not a popup, which would always draw over its bar) in the `axiom-popout-under` namespace, whose layer rule (`order = 6`) stacks it under the bars and border; it starts at the bar's outer edge and the box (`AttachedSurface.detachedOffset`) slides out from beneath the bar. Detached floating edge menus do the same (`EdgePopout.slideDistance`/`underLayer`).
- **Transparent bars** reserve `Hyprland gaps_out` less (`HyprlandManager.gapsOut`), so windows start at the bar's invisible inner edge and the widgets' gap to them matches their gap to the screen edge. Bar popouts use `adjustment: PopupAdjustment.None`: their placement is computed, and Hyprland otherwise nudges one flush on the screen edge a few pixels inwards.
- **Border off**: a solid bar draws its own inner stroke (`barConfig.innerStroke`, on its innermost `borderWidth` pixels, where its popouts attach). Surfaces on a bare screen edge (`Bar.screenEdgeOpen(screen, location)`: no border, no bar there) run straight off it, with no fillets and no `-borderWidth` margin: `AttachedSurface.straight` (attach edge) / `straightJoins` (joined ends) for pills, merged popouts and EdgePopout, and the overlay panel pushes its corners and stroke past the window on those sides.

**Icons are Material Symbols names** (`"wifi"`, `"battery_5_bar"`, from the `ttf-material-symbols-variable` font), drawn by `reusable/StyledIcon` in `Appearance.iconFamily`, never in the text font, so any text font works. Services, schema defaults (`x-icon`, icon fields) and launcher `glyph`s hold names. An icon never shares a Text with a label: put a `StyledIcon` next to a `StyledText`. `StyledIcon` draws anything that isn't a name (a glyph or text a user typed into an icon field) in the text font. `DependencyManager` warns and notifies once when the font is missing. Look names up at fonts.google.com/icons.

Icon + label bar widgets extend `bar/widgets/BarIconWidget.qml` (the BarWidgetHost inputs `barConfig`/`popouts`/`panel`/`screen`/`properties`, orientation, configured colors; override `backgroundColor` for states; `hidden` collapses one with nothing to show to zero size, padding included). It also owns their pointer handling: `clickable` + `acceptedButtons` → `clicked(button)` (a pointer, dimmed while `pressed`, off while hidden), `scrollable` → `scrolled(steps)`, `hovered` (what an edge menu a Button opened stays open for) and `dim` for fades of their own. Volume and Microphone share `AudioLevelWidget` (a device's level, mute, scroll, middle-click command, the mixer popout). Widgets that draw their own content extend `bar/widgets/BarWidget.qml` (the same inputs and `isVertical`, on a plain Item). `components/reusable/BaseWidget.qml` is the common sizing/background wrapper underneath (`crossSize`, `padding`, `radius`, `isVertical`; its `Widget.*` defaults are only for use outside the bar, and bar widgets always set them from `barConfig`). **Bar widgets are sized by their bar:** the cross axis is `barConfig.widgetSize`, and `Bar.enrichBarConfig` derives the bar's `extent` from it (plus padding and whatever covers the bar), so a widget can never be thicker than its bar; bar modules set `crossSize: barConfig.widgetSize`. `Widget.height` ("Control height") is only for controls outside the bar (form fields, buttons, card headers) and anything that opens from the bar). Everything drawn inside a bar reads its bar, never `Widget.*`: `barConfig.widgetPadding`, `widgetSpacing`, and `fontSize`/`radius` (resolved by `enrichBarConfig` from the bar's `overrideFontSize`/`overrideRadius`, else Appearance's font size and `Widget.radius`; pill and border fillets always use `Appearance.borderRadius`). **Corner radii:** `Appearance.borderRadius` is only for outer edges (screen border, bars and pills, popout/edge-menu surfaces, the overlay's outer box, the workspace overview box, floating windows, Hyprland's window rounding); anything inside something (cards, controls, rows, cells) uses `Widget.radius`, the interior radius, which follows it unless `Widget.overrideRadius`. `BarManager.styleKeys` (the bar editor's Size and Style groups) is what Copy/Paste style moves between bars. The `Widget` section ("Panels & controls") is for panels, popouts and controls. A bar whose `monitor` is `"*"` (All monitors, offered where a `screens` field has `x-allScreens`) is expanded by `Bar.expandBars` into one entry per screen, id `<id>@<screen>` with `sourceId`, the primary monitor's first.

## Launcher (`surfaces/launcher/`, `LauncherManager`)

`LauncherManager` turns the search text into rows, and the UI only draws them. `LauncherPanel` holds the field, list and hint, with no box of its own. `Launcher.qml` hosts it in a `FloatingPopout` (centred, or its top in the upper third; `maxContentHeight` keeps it from moving and `growUp` keeps a reversed field in place), or in an `EdgePopout` when `Launcher.position` is `top`/`bottom` (`LauncherConfig.attached`). Both have the same API (`show`/`hide`/`isOpen`/`contentItem`/`window`), and only the host in use is created, through `LazyLoader`s. `open(text)` searches first (so instances on other monitors show the same text); the panel created on opening then doesn't search again. `reverse` puts the field at the bottom and lays the list out bottom to top. Every provider returns the same row shape: `{ kind, image, glyph, title, usage, subtitle, hint, complete, run(shift) }`. `run` returns true to close, false to stay open (then the rows are rebuilt, keeping the selection), or a string to search for instead. Tab puts `complete` into the field.
- **Routing.** The first character picks the provider: `/` commands, `=` calculator, `>` run, `?` web, `@` chat, `:` clipboard history (ClipboardManager), `;` emoji (EmojiManager). Anything else searches apps (scored, plus frecency from `usage` `{id: {count, last}}` in `state/launcher.json`) and windows (`HyprlandManager.windowList`). A calculator row is added when the text is plain math, and a web row goes last. Each provider has a `Launcher` config toggle (`LauncherConfig`).
- **The calculator** runs `qalc` through one debounced Process, and the rows are rebuilt when it answers.
- **Commands** live in `services/LauncherCommands.qml`, a plain list of `{ name, aliases, glyph, description(), usage, needsArg, confirm, available(), status(), options(arg), run(arg, value) }`. A new shell feature gets a command by adding an entry that calls its service. `options` supplies argument completions. `confirm` (destructive session actions) asks for a second Enter.
- **`/config`** sets any setting by dotted path (`/config Appearance.font.size 14`), saving it at once through `SettingsManager.commitValue`, and holds `save` / `restore` for snapshots. It works inside the options contract: each option's title is the whole argument, so matching and Tab work unchanged. It offers `SettingsManager.settingPaths` only: the settings page's fields, minus `x-applyOnSave` ones and anything under `_blockedPrefixes` (`Bars`, `Overlay.views`), so it can never edit bars or overlays. Values are parsed and checked by `SettingsManager.parseValue`, and choices come from `SettingsManager.optionsFor` (shared with `SchemaField`).
- **IPC** is `appLauncher`: `open` / `close` / `toggle` / `search <text>`.
- **Opening a page.** `ShellManager.openOverlayPage(type)` opens the target overlay on a page, taking a view type or a view's name.

## Lockscreen (`Lockscreen.mode`)

`LockManager.lock()` is the one way to lock; lock buttons call it through `ShellManager.sessionAction("lock")`, and idle daemons through the `lockscreen` IPC target:
- **`quickshell`** (default): the built-in locker, `shell/Lockscreen.qml`. A `WlSessionLock` (Wayland `ext-session-lock-v1`, the protocol hyprlock uses) with one `WlSessionLockSurface` per screen showing `surfaces/lockscreen/LockSurface.qml`. While locked the compositor shows only the lock surfaces and sends them all input; if qs dies the session stays locked (Hyprland's fallback; `misc:allow_session_lock_restore` lets a restarted qs take it back). The locked state lives in a `PersistentProperties`, so a QML reload comes back locked. **Only `AuthManager.authenticationSucceeded` (PAM, `login` stack) unlocks**: there is no IPC unlock, and nothing on the surface may run commands.
- **`hyprlock`**: `ThemeManager.generateHyprlockConfig()` writes `$XDG_STATE_HOME/axiom/hyprlock.conf` from `scripts/templates/hyprlock_template.conf` (theme colors, font, wallpaper, blur, translated greeting) on theme/wallpaper/font/language changes and on switching to this mode; lock runs `hyprlock -c` with it. The user's own `hyprlock.conf` is never touched.
- **`none`**: axiom provides no locker and no IPC target (so an idle daemon pointed at axiom can't loop through `loginctl lock-session`); lock buttons run `Lockscreen.lockCommand`.
- **hypridle**: `Idle.enabled` has axiom run it with its own config (see HypridleManager). A user's own hypridle for the first two modes: `lock_cmd = qs -c axiom ipc call lockscreen lock`, `before_sleep_cmd = loginctl lock-session`; for `none`, no axiom references.
