# Architecture notes

## Services layer (`services/*.qml`)

Every file is `pragma Singleton QtObject` — one global instance per name, imported as `qs.services`. Key ones:
- **ConfigManager** — the source of truth for runtime config. Owns `_config` (parsed `config/user/config.json`) and `_configSchema`, loaded eagerly at creation (the active theme's data belongs to ThemeManager). Load pipeline: parse → `ConfigMigration.migrate` (upgrades old layouts by `version`, writes the result back once, moves API keys to `SecretsManager`) → `SchemaValidation.pruneUnknown` (drops unknown keys with a warning) → `SchemaValidation.applyDefaults` (fills every schema `default`) → validate. Editors create new entries at their definition's defaults with `withDefaults(value, "Bar" | "BarWidget" | "EdgeMenu" | "OverlayView" | "OverlayModule")`. All config writes go through `setTheme()` / `setWallpaper()` / `saveConfig()` / `commit(object)` (draft services: runs prune/defaults/validate, returns false and changes nothing if rejected, so drafts stay dirty), which validate before writing, then `forceReload()`. Never mutate `ConfigManager.config` fields directly from UI code and expect persistence — call the setter functions (or `SettingsManager.setValue(path, value)` from settings UI). The editor services (SettingsManager, BarManager, OverlayManager, EdgeMenuManager, KeybindManager, MonitorManager) each hold a `ConfigDraft` (`services/ConfigDraft.qml`: working copy of one config path, `changed()` after in-place edits, `save()` merges onto the latest config via `commit`). `ConfigManager.previews` (`setPreview(section, value)` / `clearPreview(section)`) holds unsaved edits shown live without being part of `config`, so other saves and disk reloads don't touch them: BarManager previews `Bars` while dirty, and `BarManager.bars` reads `previews.Bars ?? config.Bars`.
- **SecretsManager** — secrets, never in config.json, by scope: chat API keys (`provider`) and calendar account passwords (`calendar`). A provider's `keyEnv` env var first, else the keyring (`secret-tool`, `service axiom <scope> <id>`; probed once, `keyringAvailable`), else `$XDG_STATE_HOME/axiom/secrets.json` (mode 600; a provider's key under its bare id, as before scopes, any other under `<scope>:<id>`). `withSecret(scope, id, cb)` is async (cached per session); `secretStatus(scope, id)` is `keyring` | `file` | `none` ("" while looked up); `setSecret`/`clearSecret` write through stdin, never argv; `refreshSecrets(scope, ids)` for a card showing them. The provider calls (`withKey`, `status`, which adds `env` | `unneeded`, `setKey`, `clearKey`, `refresh`) wrap them. Keys are entered on `views/settings/ChatProvidersCard` (the Chat section's `x-card`, with Test and Fetch models) and passwords on `CalendarAccountsCard`, never through the settings draft.
- **ChatManager** — the chat: `conversation` (`{ id, title, preset, provider, model, messages }`), `conversations` (index, newest first), `send`/`stop`/`regenerate`, presets and models, attachments (clipboard, a region from `ScreenshotManager.pick`, dropped files; base64 per send), saved to `$XDG_STATE_HOME/axiom/chats/` (`<id>.json`, `index.json`, `<id>/` attachments) up to `Chat.keepConversations`. Each reply is a `services/ChatRequest` (curl with its config, key included, on stdin via `-K -`; the body in a `$XDG_RUNTIME_DIR` file; a `SplitParser` feeding SSE lines to `components/methods/ChatProtocol`, which builds requests and parses streams for the `anthropic`, `openai` (any OpenAI-style server) and `gemini` kinds). Streamed text lives in `streamingText`/`streamingThinking`, flushed every 50 ms, and replaces the placeholder message only when the reply ends, so the message list doesn't rebuild per token. Anthropic thinking blocks (with signatures) are sent back only to the model that wrote them. `components/methods/ChatMarkdown` splits replies into prose and code blocks. `content/Chat.qml` is a `Panel` (ready to be a popout). IPC `chat`: `open`, `newChat`, `ask <text>`, `settings`; launcher `@` and `/chat`; `OverlayConfig.pageWithModule(type)` finds the page to open. Created from `shell.qml`'s `_services` (for the IPC target).
- **ThemeManager** — owns the active theme: `currentTheme` (loaded eagerly, watched, reloaded when `Appearance.theme` or the file changes) and `defaults` (`theme-defaults.json`); `Appearance.darkMode` is derived from the theme's `variant`. Also theme discovery: `themeFamilies`, one entry `{ label, dark, light, generated }` per theme, where a dark/light pair (each file's `paired` naming the other) is one theme labelled by the words their names share, and `currentFamily`; `applyFamily(family)` picks the variant for the current mode and `setLightMode(bool)` switches the current theme's variant (the only light/dark switch; `Appearance.darkMode` follows the applied theme). Then generation from a wallpaper (`scripts/generate_theme.py`, one run writing a `generated/wallpaper-<style>-dark|light` pair per `STYLES` entry (`tonal`, `vibrant`, `faithful`, `muted`, `alternate`: factors on the one build, like Material's scheme variants): k-means in OKLab picks candidate colors, the palette is built in OKLCH from targets measured off the hand-made themes, with the wallpaper's seed as `accent` in `base0F`; run through `scripts/venv_python.sh`, which keeps `.venv` in sync with `scripts/requirements.txt`), `setWallpaper` (`Appearance.wallpaperBackend`: `quickshell`, the default, is drawn by `shell/Wallpaper` (one Background-layer `surfaces/wallpaper/WallpaperWindow` per screen, crossfading) straight from config; `awww` runs `setWallpaper.sh`, and Hyprland's `wallpaperDaemon` starts it only then), and `themeIntegrations()` (one `scripts/theme_<key>.sh` per `ThemeIntegrations` switch, hooked into its app by `IntegrationHookupManager` (Themes, below): `integrations` is the schema's boolean keys, with `integrationTitle(key)` and `integrationCommands(key)` (any of which shows the app is installed, for the onboarder); a failure, or a `Warning:` line on stderr, is logged), which run when the active theme's name or contents change, and for one integration as soon as its switch turns on (`_enabledIntegrations` against those of the last full run, `_themed`; nothing until the first full run, so loading the config doesn't run them twice). The choice of theme is persisted through `ConfigManager.setTheme`.
- **ShellManager** — cross-cutting UI signals (power menu, launcher, overlays) that modules connect to rather than calling each other directly, and screen targeting. `General.monitors` is `"primary"` | `"focused"` | `"all"`; the OSD, overlay and launcher have their own `monitors` setting (`"general"` | `"primary"` | `"focused"` | `"all"`, resolved by `modeFor(mode)`; the power menu uses General's), and docks and OSDs also take `"monitor"`, the one their `monitor` names (passed as the `name` argument below). Surfaces are built on `General.screensFor(mode, name)` (`General.screens` for General's), and only the instance on `targetFor(mode, name)` (`isTarget(screen, mode, name)`: the focused monitor in "focused"/"all") answers a shortcut, IPC call or OSD event. In "all" (`everywhere(mode)`, `showsOn(screen, mode, name)`) the surface opens on every monitor at once: a `reusable/SurfaceGroup` per instance opens and closes the others with it (`ShellManager.surfaceShown`), and since only one `HyprlandFocusGrab` can be active, only the target's instance holds one, over every instance's window (`surfaceWindows`); the launcher's instances share `LauncherManager.text`. The workspace overview is built on every screen and opens on the one under the cursor (`HyprlandManager.withHoveredScreen`, a `hyprctl cursorpos` lookup). Wallpapers are per monitor (`Appearance.wallpapers[monitor]`, set from the overlay's Themes page; the primary monitor's is also `Appearance.wallpaper`, the lockscreen's). IPC handlers are `enabled` on the target instance only, since a target name can have one handler. Surfaces sharing a screen edge give way by rank (`edgeRanks`: dock < OSD < floating edge menu, the menu being opened by hand): an OSD and a floating edge menu claim their screen edge while open (`setEdgeClaim(owner, { screen, edge, kind })`, null to release; `edge` a `Bar.edgeName`), and a lower one on that edge closes and stays shut while `edgeOutranked(screen, edge, kind)` (the OSD ignores its pokes and hover strip; the dock is put away, a reserving one keeping its zone). An integrated menu (whose zone pushes the others inwards) take no part. Every focus grab lets input through to `modalWindows`: the screenshot pickers (`captureWindows`) and modal prompts (`registerModal`, the polkit prompt). `beginStepAside(owner)`/`endStepAside(owner)` (`steppedAside`) is for a prompt axiom doesn't draw (another polkit agent's window, which opens under the Overlay layer): the overlay and the onboarder (`ReservedAreaWindow`) stay mapped, so their pages and state survive, but hide their content, take no input or keys (an empty `mask`) and drop their backdrop, and the overlay's grab is off (and its `cleared` ignored) until the last owner ends it. `newSurfaceKey(kind)` / `reportRequiredField(key, present)` / `requiredFields` are the screen layouts' required-field reports (Lockscreen: Password; Greeter: Login).
- **SystemManager** — CPU/memory/temp/GPU/disk stats. Reference-counted through a `ConsumerRegistry` (shared with UpdatesManager; identical re-registrations are no-ops): consumers call `acquire(owner, {interval, metrics, diskPaths})` / `release(owner)`, and it polls only the union of requested metrics (sysfs/procfs `FileView` reads, no processes on the hot path), stopping entirely with no consumers.
- **UpdatesManager** — pending pacman/AUR updates shared by every Updates widget (same acquire/release pattern). Only one `checkupdates` may run at a time: concurrent runs share its temp db and fail. `upgrade(command, terminal)` runs the upgrade in a terminal (one at a time, `upgrading`) and checks again when it closes.
- **Polled data** (the rule is in CLAUDE.md): besides SystemManager and UpdatesManager, `CalendarManager` (`acquire(owner)` with no request: its interval is the Calendar section's), `WeatherManager`, `TailscaleManager` (`available`, `backendState`/`connected`, `tailnetName`, `ip`) and `CommandManager` (`outputs[command]`, shared by identical commands, e.g. a Button's label). `CommandManager.runDetached(command)` runs a widget's click commands, and `run(command, callback, input)` a service's one-off command (callback `(exitCode, stdout, stderr)`; `input` goes to stdin), so services keep no Process of their own. Widgets hold the request in a `readonly property var …Request` built from `properties` and acquire it in `Component.onCompleted` and `on…RequestChanged` (WeatherManager takes no request: its settings are global).
- **NetworkingManager** — Wi-Fi over `Quickshell.Networking` (NetworkManager D-Bus, event-driven): radio (`wifiEnabled`, `setWifiEnabled`), `networks` (connected, saved, then by name; fixed order), connect/disconnect/forget, the password prompt (`passwordFor`, `connectWithPsk`, set again on a `NoSecrets` failure), and the primary connection (`primaryDevice`: wired before Wi-Fi; `netInfo` `{ kind, name, device, signal, ip }`, all bindings, except the IPv4 address, which Quickshell.Networking lacks: one `ip -4 -j addr` whenever the connection changes, or on `refreshIp()`). Nothing runs `nmcli`. The scanner runs only while something holds `acquireScan(owner)`. Not named `Networking` (Quickshell's singleton). Throughput stays in SystemManager.
- **BluetoothManager** — adapter power, scanning, sorted device lists and connect/pair/forget over `Quickshell.Bluetooth`. Not named `Bluetooth`, which would shadow Quickshell's singleton (and the `Bluetooth` bar widget file).
- **NotificationManager** — the DBus notification server plus a persistent history: `entries` (plain objects, newest first, capped at 100) stay until the user removes them (`dismiss(uid)`, `clearAll()`, or the `notifications` IPC target), even when the app withdraws one, and are saved to `$XDG_STATE_HOME/axiom/notifications.json`. `liveNotification(uid)` gives the still-open Notification (for actions), and restored entries open their app instead (`openApp`). `NotificationsConfig` sets the history's size and age (`maxEntries`, `maxAgeDays`) and which user actions remove an entry: `clearOnFocus` (an `activewindow` event whose class matches the entry's desktop entry or app name), `removeOnClick`, `closeRemoves`. Toasts take their entry's uid at creation (`uidOf`), because invoking an action can close the notification. `dnd` (readonly; `setDnd`/`toggleDnd`) is saved in `config/state/notifications.json`. The toasts (`shell/Notifications`) stack once per screen of `NotificationsConfig.monitors` (`showsOn`); a toast the user closes closes on every screen. Images are cached as PNGs in `…/axiom/notifications/`, rendered through an `imageHost` item that `shell/Notifications` lends it (grabbing needs a window). `keepOnReload` keeps live notifications across QML reloads.
- **HyprlandConfigManager**: how axiom sets up Hyprland (`Hyprland` section, `HyprlandConfig` reader). It needs Hyprland's Lua config, 0.55+; axiom's own `hyprctl eval`/dispatch calls are all Lua (`hl.*`, stubs in `/usr/share/hypr/stubs/hl.meta.lua`). One Lua layer covers binds (`binds[]`: an IPC `action` or `exec`, `description` "Axiom: …"), required settings (`allow_session_lock_restore`, a named rule suppressing `maximize` requests, a `workspaces` animation), the window look, blur, monitor profiles (see MonitorManager) and strips (see Workspaces). `mode` picks how it gets there:
  - The window look (`Hyprland.look`, `x-scope: look` inside the machine-scoped section, so exports, examples and imports carry it, and it isn't `x-takeover`): themed borders, axiom's shape (`decoration.rounding`/`general.border_size` from `Appearance`), `gaps_in`/`gaps_out`, Hyprland's blur (`blur`: `decoration.blur.*`, its size and passes the one strength windows and axiom's surfaces share) and window opacity (`opacity`), as one `hl.config` (`HyprLua.lookLua`; the blur and opacity fields are `x-hypr` fields gated by `x-hyprIf` on their part, so `configTable` writes them). With the blur part on, Hyprland's blur stays enabled while axiom's surfaces blur even if `windowBlur` is off, and the `axiom-no-window-blur` rule (redefined on or off) keeps windows and their popups unblurred then. Every part shows in every mode; a managed config writes them through `M.look()` like the rest (v51 turned `blur` and `opacity` on for managed configs, whose own fields they were). `HyprlandManager.blur` reads the blur in effect (`refreshOptions`) for the Translucency card's status (`views/settings/TranslucencyStatus`, its `x-intro`) and the lock screen's frost. It is in the layer like the rest (`M.look()`, `M.theme` its old name), and in the file modes also evaluated after every `configreloaded` (`_applyLook`), so it wins over the user's own lines while on. A runtime eval can't take a setting back: `_undoLook` reloads Hyprland's config when a part was turned off since it was evaluated (`_lookState.applied`, a `PersistentProperties`; the file modes reload anyway by rewriting their file). `HyprlandManager.refreshOptions()` waits for queued Lua, so `gapsOut` reads what the look set and Automatic bars follow it.
  - `detached`: `hyprctl eval` at startup and on every `configreloaded`, skipping keys `hyprctl binds -j` shows taken (`components/methods/HyprBinds`: `keyId`, `runtimeBinds`, and `userKeyCounts` for KeybindManager). The keys it bound live in Hyprland's Lua state (`AXIOM_RUNTIME_KEYS`), which a Hyprland reload resets along with the binds and which survives a qs reload. They are unbound before the binds are read.
  - `included`: `moduleLua()` goes to `$XDG_STATE_HOME/axiom/hyprland.lua`, a module the user loads with `includeLines`.
  - `managed`: `managedLua()` becomes `~/.config/hypr/hyprland.lua` itself (plus the `managed` options; their `rounding`/`borderSize` only while the window look's `shape` is off), loading `user/*.lua` after it via `require("user.<name>")`. Hyprland watches required files, so user edits reload it; `user/lib/` is for shared modules. The user's own setup is this: `user/` is a symlink to `~/repos/dotfiles/hypr/user`. `scripts/claim_hyprland.sh` (`check` for `checkManaged()`, `claim` for the takeover) refuses a symlinked or git-tracked dir (`blocked:link`, `blocked:git:<repo>`: `managedCheck` is `blocked`, `managedBlockedBy`/`managedBlockedRepo` say why, for the onboarder's greyed-out card and the status card), and treats a `hyprland.lua` that is Hyprland's example config (`/usr/share/hypr/hyprland.lua`, give or take whitespace, install.sh's `-- axiom` autostart line, and what Hyprland changes when it autogenerates one at its first start: a banner, `hl.config({ autogenerated = true })` and its `local menu` pick; `$AXIOM_HYPR_EXAMPLE` in tests) as `stock`: `claim` only backs it up (`replaced`) instead of adopting it into `user/`, since its binds and `hl.monitor` rule would fight axiom's. `claim` prints `adopted:<name>` (copied to `user/00-previous.lua`, or `00-previous-<date>.lua` when that's taken, with its lines that start axiom or `dofile` its included module commented out unless `luac -p` then rejects it: a second start without `-n` would be a second shell, and the include would bind everything twice) or `created` (there was no file); a file `release` wrote (`releasedLua()`, unedited, give or take the include lines) is `released` to `check` and only replaced, not kept. `claim` leaves hyprland.lua in place for the managed write to replace atomically (Hyprland reloads when the file changes and must never find it missing), and a claim of the same file again reuses its copies. Only the adopted file's binds are merged straight away (`mergeUserBinds(name)`, below, `extract --only`), so managed mode starts with no conflicts; the rest of `user/` waits for the Merge button.
  - `mergeUserBinds(only)` (managed only; the Keybinds page's Merge button, counted by `previewMerge()` → `mergeable` when the page opens, shown instead of "Remove binds your Hyprland config also has" while it has binds to move) moves `user/*.lua`'s binds into `Hyprland.binds`. `scripts/merge_hypr_binds.py extract` runs the files through `scripts/hypr_binds.lua` (plain `lua`, which Hyprland depends on: each required as `user.<name>` against a stand-in `hl` that records `hl.bind`/`hl.unbind` with their file and line, so variables, string building and loops work; `io.popen` reads empty, `io.open` only reads, `print` goes to stderr, a stand-in value lists as empty, and submap and `hl.on` handlers aren't seen) and maps each dispatcher onto an action (`exec_cmd` of wpctl/pactl/brightnessctl/playerctl onto the media actions, the example's exit command onto `exitHyprland`, others onto `exec`; focus/move/float/pseudo/togglesplit/special/drag onto theirs; Hyprland's example config maps completely; binds from an adopted `00-previous*.lua` on keys axiom's defaults use move, reported in `remapped` (`EXAMPLE_KEYS`; a key in the user's other files was their own choice): togglesplit from `SUPER + J` (focus down) to `SUPER + X`, the special workspace from `SUPER + S`/`SUPER + SHIFT + S` (WASD's down) to `SUPER + V`/`SUPER + SHIFT + V`, and float from `SUPER + V` to axiom's `SUPER + Z`), else the `lua` action with the dispatcher as written. A call moves only whole: every bind it makes (a loop makes several) must map, with no option axiom binds lack (`non_consuming`, …), it must be its own statement in a `user/*.lua` file (not a `user/lib/` module), and a variable it's kept in must be unused. The binds are committed first (`SettingsManager.commitValues`; `bindsMerged` lets KeybindManager add them to a dirty draft), then `remove` deletes those calls, and any `hl.unbind` of a moved key (it would unbind the moved bind too), after a dated `<file>.axiom-backup-<date>` copy (keeping the file's mode), leaving a file alone if `luac -p` rejects the result. Whatever it couldn't delete (`failed`, per file or per call) is taken back out: the binds are committed again as `mergeBinds(before, binds from the sites that went)`, so no key is bound twice, and only those go to `bindsMerged`. Reasons are codes (the script's docstring), translated by `BindEditor.reasonText`; `tracked` names files in a git repository. A key axiom already binds stays one bind: `HyprBinds.mergeBinds` puts the moved bind in place of axiom's (the user's config loads after axiom's layer, so it was the one in effect), as it does in a draft with unsaved edits. `lastMerge` (`moved`, `removed`, `kept` with reasons, `failed`, `remapped`, `tracked`, `errors`, `saveFailed`) shows above the bind list.
  - The `managed` options become one `hl.config({...})` through `components/methods/HyprLua` (pure), driven by schema annotations: `x-hypr` (the option's dotted path, or a list), `x-hyprScale` (integers shown scaled: 0.01 for a percent), `x-hyprValue` (`int`, `number` for numeric enums, `emptyIsDefault`, `color` for a theme color name, with `x-hyprAlpha`), `x-hyprIf` (a boolean sibling gates it) and `x-hyprAlways`. A field is written only when it differs from its default (Hyprland's own), so a new option is just a schema entry. `managed` stays flat (the settings page nests one level): its cards come from `x-group`/`x-order`. Not mapped: `animationPreset` (`hyprland` writes nothing; `axiom` follows `Appearance.animFast/Normal/Slow` and turns animations off with motion; `snappy`/`bouncy`/`lightning`; `custom` from `curves`/`customAnimations`), written after `axiom.setup()`, plus `env` (after `HyprLua.recommendedEnv` while `recommendedEnv` is on, so the user's win) and `autostart` (after axiom in the start hook) and the cursor.
  - Both file modes write only on change, then `hyprctl reload` (Hyprland doesn't watch `dofile`d files). `_writeFile` re-reads the file before each write (`blockLoading`): a FileView skips `setText` of the text it last wrote, which the file may no longer hold after a release.
  - Leaving a mode gives back what it took (`_leave`, for a switch made while axiom runs: `_appliedMode` is `""` until the first `apply()`, so a load never gives anything back). Leaving managed runs `claim_hyprland.sh release`: hyprland.lua becomes what `claim` set aside again (the newest adopted `user/00-previous*.lua`, its commented-out lines that start or load axiom enabled again, else the example config's backup; `restored:<from>:<n>`, with a warning when `<n>` files in `user/` are no longer loaded), or, with nothing set aside, `releasedLua()` (starts axiom, loads the module in included mode, and loads `user/*.lua` as the managed file does: `_userFilesLua()`); a symlinked or git-tracked file is refused, as `claim` refuses it. Leaving included, or managed for detached, empties the module if it exists (`_emptyModuleLua`: every part a no-op, so a hyprland.lua still loading it gets nothing). Otherwise the old layer would stay in Hyprland's config, and the runtime layer, which only adds, can't undo it (a strip removed in detached mode stayed a strip). `_reload()` reloads once more when asked while a reload runs, so a file written meanwhile isn't missed. Detached waits for a release (`_releasing`) before applying its runtime layer, and the runtime layer starts over when Hyprland reloads while it reads the binds (`_reloads`): a plan from another config would record that config's keys in `AXIOM_RUNTIME_KEYS`, and `_clearRuntime` would unbind them. The status card lists these steps before Save.
  - Strips (`Workspaces.strips`, `HyprLua.stripsLua`, the same Lua in every mode): a `*` strip makes `scrolling` (with its `scrolling.direction`: horizontal is `right`, vertical `down`) the layout everywhere, and each named monitor gets a `hl.workspace_rule` on `m[<name>]` with `layout = "scrolling"` and its direction in `layout_opts`, which wins over it. The Workspaces section's strip settings (`stripColumnWidth`, `stripFollowFocus`) are `x-hypr` fields like `managed`'s, through `configTable`. Included/managed: `M.strips()` from `setup()`, after managed's `hl.config` so it wins over `general.layout` (which only offers dwindle and master: scrolling is the strips'). Detached: in the runtime eval, wrapped by `HyprLua.stripsRuntimeLua` to apply once per Hyprland load (workspace rules add up rather than replace): `AXIOM_STRIPS`, in Hyprland's Lua state (reset by a Hyprland reload, kept across a shell reload), names the strips applied; different ones can't be taken back, so they `hyprctl reload`, whose `configreloaded` applies the new strips over the user's config alone.
  - `includeLines` (included) and `autostartLines` (one line marked `-- axiom` like install.sh's, for included and detached; managed starts axiom itself; both start it with `startCommand`, `qs -p … -n`, whose `--no-duplicate` exits at once if axiom already runs, as install.sh's `qs -n -c axiom` does) are also hookup targets (`includeTarget`, at the top of hyprland.lua, and `autostartTarget`, at the end; any `qs -c axiom`/`qs -p …axiom` line counts as done), which `IntegrationHookupManager` runs under the keys `hyprlandInclude` (both) and `hyprlandAutostart`, so the onboarder's Hyprland page offers Apply with a backup as a theme integration does.
  - An `AXIOM_INCLUDED` global tells axiom the file is loaded. When it isn't, the runtime layer stands in and `problem` says why.
  - The settings page's Hyprland category starts with `HyprlandStatusCard`, built from `status` (`runtime` | `loaded` | `fallback` | `pending`) and `problem`. A mode picked there waits for Save (`x-applyOnSave`), and the card outlines what saving will do, predicting a managed takeover with `checkManaged()` (`managedCheck`: `ours` | `adopt` | `new` | `blocked`, a dry run of `claimManaged`).
  - `binds` are edited on the Keybinds page, not in settings (see KeybindManager). An action is an axiom IPC call (`_actions`, including the `audio`/`media` targets on AudioManager/MediaManager, so the OSD shows) or a Hyprland dispatcher bound directly (`_dispatchers`: focus/move/resize, close, fullscreen, floating, pin, special workspaces, mouse drag/resize on a `mouse:272` key, which Hyprland makes a mouse bind by itself; the window switcher's `windowSwitcher`/`windowSwitcherReverse`, Lua functions entering its submap (see Window switcher); `exitHyprland`; `pseudo` and `toggleSplit`; `lua`, any dispatcher as Lua, compiled with `load` when the bind is made so a mistake leaves only that bind a `no_op`; and `terminal`/`fileManager`/`browser`, which exec `Apps.terminalCommand` etc., so the binds follow the `Apps` section's `terminal`/`fileManager`/`browser`, empty being the system default; `mediaStop` etc. on `media`). `screenshot` (argument `region`/`window`/`screen`) goes to **ScreenshotManager** (IPC `screenshot take <kind>` / `cancel`, launcher `/screenshot`, and the Screenshot card), with no grim or slurp (the chat's region attachments use it too, through `pick(path, callback)`, which saves to a path and calls back instead of copying): `shell/Screenshot` shows `surfaces/screenshot/ScreenshotPickerWindow` while `picking` (a frozen `ScreencopyView` frame per screen, `axiom-screenshot` layer rule with `no_anim`; the window under the cursor highlighted from the start (`HyprlandManager.withCursorPos`); `region`: drag a region or click a window, the screen off one; `window`: click a window; cropped through a `ShaderEffectSource` + `grabToImage` at the buffer's resolution; `screen` grabs at once on one screen), saved to `<Pictures>/Screenshots` (or only a runtime file with `copyOnly`, in `config/state/screenshot.json`), copied with wl-copy, then notified (with an "Edit in Satty/Swappy" button: a waiting `notify-send -A`, only the latest one live) or opened in satty/swappy straight away (`annotate`, the picker's "Edit in …" switch / E / Shift on release). One 3 s watchdog in the service fails a capture that gets no frame (a picker reports its frame with `frameArrived()`; an immediate `screen` capture must also report back), so nothing can wedge it. Held (`detached`, the default) it's a plain box `gap` from the frame lines on its edge and at its ends (Popouts: held off an edge; `boxOffset`, `startInset`/`endInset`); otherwise it meets its edge exactly as an `EdgePopout` does (`EdgeAttach`, Popouts): an `AttachedSurface` growing out of the border's or a solid bar's stroke (`edgeMargin` from `attachAt`), straight off a bare edge, joining a perpendicular stroke at an end, standing on or merged around a pill bar's pills, out of a floating bar's island (stretching it while it shows), or a detached box past a transparent bar; along the edge its window reaches onto the perpendicular strokes (`strokeInset`) and the icons sit where they want (`place.contentStart`), the surface growing around them; `visibility`: `always` (`reserveSpace` sets its zone), `hover` (an `EdgeTrigger`) or `intellihide` (hover, plus shown while no window on the monitor's workspace, or its open special workspace (`HyprlandManager.specialWorkspaceId`, monitors refreshed on `activespecial`), covers it: `obscured`, placed from the monitor's `reserved` via `lastIpcObject`). A dock reports what it reserves (`setZone`/`zoneOn`, per screen edge), and what would otherwise be pushed in by it reaches past it: `EdgePopout` (the OSD, floating edge menus: on its own edge and at both ends; its `axiom-edge-popout` layer rule `order = -2`, and the OSD's `axiom-osd` (`overNamespace`) `order = -4`, draw it over the dock and the OSD over the overlay; the edge popouts' `order = -5` draws floating edge menus over the overlay and the OSD too) and the border's corner pieces (`RoundedBorders.cornerMargin`). Hyprland sends no event when windows retile around a changed zone, so `refreshSoon()` re-reads monitors and windows after layer and zone changes (layer events only while a dock is built). IPC `dock`: `open`/`close`/`toggle <id>` (empty: every dock; not `show`, which qs's CLI takes), bind action `dock`. The settings card's Show is a preview (`DockManager.preview(entry)`, the entry as edited, saved or not): since the dock is put away under the overlay the card sits in, `shell/Dock` builds a second `DockWindow` with `preview: true` on the screen the dock would show on (`previewScreen`, `ShellManager.targetFor`), an Overlay-layer `axiom-dock-preview` (its layer rule's `order = -4`, after the overlay's panel) with no trigger, zone, input or IPC, reaching back past the docks' zones on its edge to where a dock sits. It slides in, holds for 2s and slides out; meanwhile the dock's own copy there hides its content (`previewing`, keeping its zone). An always-shown dock reserving its strip, visible beside the overlay, isn't slid out: the preview is dropped at once and the dock shows again.
- **IdleInhibitManager** — shared caffeine state (a `PersistentProperties`, so it survives QML reloads but not restarts) + `idleInhibit` IPC target; the Wayland inhibitor itself lives in `shell/IdleInhibit.qml`, which maps a 1 px click-through Background-layer window on the primary monitor while it's on (it needs a surface), so it works without the bar widget.
- Other domain services (AudioManager (also every write to a Pipewire node: `setNodesVolume`/`setNodesMuted`, and `matchStreams(apps, other, excluded)`, the OSD app bars' playback stream matching (recording streams are left out: an app's mic capture shares its name)), BatteryManager (also the power profile, `level` against the `Battery` section's thresholds (`BatteryConfig`; the Battery widget and module colour from it), and the low battery notifications, once per drop into low and then critical, whatever bars exist; created from `shell.qml`'s `_services` so they run without a widget), KeyboardLayoutManager, MediaManager (MPRIS), HyprlandManager, StateManager, BarManager, LauncherManager, SettingsManager, SavedConfigsManager, AuthManager, LockManager) follow the same pattern.

## Config layer (`config/*.qml`)

Also `pragma Singleton`, but these are typed config *readers*, not owners — one per config section, exposing `readonly property` values from `ConfigManager.config`. No `??` fallbacks: the schema defaults are already filled in. Readers: `General` (displayName, primaryMonitor, `monitors`/`screens`, `screensNamed(name)`: that screen, else the primary, else the first), `Idle` (hypridle, see HypridleManager), `PolkitConfig` (see PolkitManager), `GreeterConfig` (see Greeter), `Appearance` (theme, font, shape, motion tokens), `Widget`, `Bar` (from `Bars`; the first bar is primary; `edgeName(location)` gives a `Bar.Location` as `"top"`…`"right"`), `PopoutConfig` (open/dismiss delays, edge trigger size — shared by bar and edge popouts), `OSDConfig` (the OSDs: shared scroll settings plus `osds`, `definitions/OSDEntry` each with its own `monitors`/`monitor`, an `EdgePopout` at `edge`/`position` (held off it with `detached`/`gap`, Popouts: held off an edge, as a dock), orientation, timeout and `bars`, each typed `master` | `other` | `microphone` | `brightness` | `app`, drawn by `surfaces/osd/OSDBar` in `OSDContent`; a change opens every OSD holding that bar (`OSDTriggers`), and Other apps skips the App bars of every OSD. Edited on the section's `x-card` `views/settings/OSDListCard` (tabs, an edge picker with presets, Show through `ShellManager.showOsd(id)`); the App field's chips come from `x-suggestions: "audioApps"`, `SettingsManager.suggestionsFor`), `LauncherConfig` (launcher placement, size and providers), `Apps` (the terminal, file manager and browser that binds and the launcher open), `NotificationsConfig` (the toasts' corner and gaps, measured inside the work area by an Overlay-layer anchor window with Normal exclusion, like `OverlayPanel`), `OverlayConfig` (views + card-grid constants), `EdgeMenusConfig` (edge menus), `IconConfig`, `ChatConfig`, `CalendarConfig` (accounts with their ids filled in, `calendars` flattened with resolved colors, `shownCalendars`/`writableCalendars`, `newEventCalendar`, `colors` by calendar id, `timeFormat` from `use24Hour`), `ThemeIntegrations`, plus `Paths` (derived filesystem paths from `$HOME` / `Quickshell.shellDir`, not configurable; `greeter` and the greeter's folders, see Greeter) and `Theme`. Readers whose section name collides with a type get a `Config` suffix (`Popouts`, `Overlay`, `Icons`, `OSD`, `Launcher`, `Notifications`). UI code should read colors/settings from these (`Theme.background`, `Widget.padding`) rather than reaching into `ConfigManager.config` directly.

`config/Theme.qml` exposes the base16 palette (`base00`-`base0F`) plus semantic aliases (`background`, `accent`, `error`, etc.) resolved through `_themeData.semantic`, and a `stringToColorMap` + `resolveColor(name)` for dynamic color lookup by string (used when a color name comes from JSON/config rather than a static binding).

## Schema and the settings page (`config/json/config.schema.json`)

The schema is the single source of truth: shape, `default`s (there is no separate defaults file), and the generated settings page (`views/Settings.qml`). Adding a setting = a schema entry with a default + a reader property; changing the layout of existing config = bump `version` + a `ConfigMigration` step. The live file is `config/user/config.json` (gitignored, UI-owned). A schema reaches QML as a map, whose keys come out sorted, so order always comes from `x-order`.

**Annotations** (the settings page, forms and editors read them; add one rather than a list in QML):
- Placement: `x-settings: false` hides a key; `x-category` on a top-level section names its sidebar category, and the root's `x-categories` (`[{ name, icon, page }]`) orders the categories and gives their icons (`SchemaLayout.categories`; one left out comes last, with a generic icon); a category's `page` is a hand-built part shown after its cards (`views/settings/<page>.qml`: Maintenance's `SavedConfigsSection`: `SavedConfigsManager`'s snapshots in `config/user/saved/` and, below them, sharing (Share: Export, Import…) and the example setups in `examples/` (`SavedConfigsManager.examples`). What a shared file carries is the schema's `x-scope` (inherited; the root is `machine`): `look` (the layout and style sections, and the theme, font, shape and motion), `personal` (`Apps`, `Hyprland.binds`, a dock's `pinned`, Favourites' apps, widget commands, OSD audio apps; carried only when asked for) and `machine` (monitor names, wallpapers, accounts, paths, AUR settings, every other section; never carried). `ConfigExamples` (pure) walks a value along the schema: `pick(config, schema, personal)` keeps the carried leaves; `apply(current, example, schema, personal)` takes the example's carried parts (an array outright, so nothing of the old layout stays) and, inside them, keeps the user's other values from the same item, matched by `id`, then `name`, then (machine values only, since a personal one such as a command must not land on another button) position, else the default; `sparse(config, schema)` drops what loading fills back in; `keepTakeovers(config, current, paths)` puts back the current value of every `x-takeover` setting (`takeoverPaths(schema)`, kept as `ConfigManager.takeoverPaths`: `Hyprland.mode`, `Lockscreen.mode`, `Greeter.enabled`, `Idle.enabled`, `Polkit.enabled`), which `ConfigManager.restoreConfig` applies to everything it loads (a snapshot, the defaults, an example, an import): those settings take something over (hyprland.lua, the session's locker, hypridle, the polkit agent, greetd), so only their own cards switch them, doing the takeover or giving it back. `applyExample(name)` and `confirmImport(personal)` load the file through `ConfigManager.normalizeConfig` (any version migrates), save the running config as `before-<name>`, then, once that is written, restore `ConfigExamples.apply`. `browseImport()` runs `scripts/pick_file.py` (xdg-desktop-portal's FileChooser through python-gobject, else zenity/kdialog) with the overlay stepped aside (`ShellManager.beginStepAside`: the picker is a window, under the Overlay layer); the chosen file becomes `importing` (title and description from its `_example` header) for the page's confirm row, whose switch for personal parts starts off. `exportConfig(personal)` writes `~/axiom-[<active>-]<date>-<time>.json`: `_example` + `version` + the sparse pick (which applies as the whole pick would: `tst_ConfigExamples`' round trips). Exports and examples are one format. Among the snapshots, only `active` (the one last saved or restored, kept in `state/savedconfigs.json`) offers Overwrite on its row and `modified` (the running config against the snapshot through `ConfigManager.normalizeConfig`, by `ConfigExamples.equalApartFrom`, which leaves the takeover settings out without copying either) dots it), so a category can have no sections; `x-links` lists page types it links to (`Themes`, `Layouts`, or a view type; the link buttons take the page's label and icon from `OverlayConfig.viewLabel`/`viewIcon`); `x-order` on an object lists the keys shown first (its form's, or its settings cards', whose order is their first field's); `x-group` puts a field on a card of that name (one section or object can make several cards). The bar and edge menu editors group a `Bar`'s / `EdgeMenu`'s own fields the same way (`SchemaLayout.objectGroups`, as `Bar.fieldGroups` / `EdgeMenusConfig.fieldGroups`).
- Hand-built parts: a section's `x-card: "<Name>"` adds `views/settings/<Name>Card.qml` as its first card (with `x-cardFolds: true` it folds like the generated cards and joins Fold all, getting its group key `<Section>:<Name>` as `foldKey`); `x-intro: "<Name>"` puts `views/settings/<Name>.qml` at the top of the section's own card, above its fields (NightLight's `NightLightStatus`).
- Behaviour: `x-showIf` hides a field unless a sibling has a given value (every key must hold; `anyOf: [conditions]` holds when one of them does, as the OSD's `alongEdge`, shown only while its bars run along its edge; a key starting with `/` is a dotted path from the config root, e.g. `"/Workspaces.layout"`, read through `SettingsManager.configValueAt`; `SchemaField` evaluates it, so it works in every form; on a nested object it hides that object's cards); `x-beside: true` puts a field beside the one before it on its settings card, each half wide (`SettingsGroupCard`'s two-column grid; Workspaces' rows beside columns; give the pair the same `x-showIf`); `x-applyOnSave` keeps a setting in the draft until Save instead of applying it live (Hyprland's `mode`, which can take over files).
- Controls: `x-options: "colors"` (a picker over `base00`–`base0F`; read with `Theme.resolveColor`, which also takes semantic names and hex), `x-emptyLabel` on a color offers an empty value under that label (automatic: a bar's `widgetTextColor`), `"screens"` (a monitor; empty is the primary monitor, resolved by `General.screensNamed`: bars in `Bar.expandBars`, docks, edge menus; `x-emptyLabel` renames empty where it means something else, as in `General.primaryMonitor` itself; `x-allScreens` adds All monitors, `"*"`; docks and OSDs pick all monitors through `monitors` instead), `"languages"`, `"edgeMenus"`, `"overlayPages"`, `"notes"`; `x-suggestions` (chips under a text field, `SettingsManager.suggestionsFor`); `x-multiline: true` (a growing text area); integers render through `forms/SchemaNumberField` (a slider with a value box for 7–200 steps, else a stepper, ±10 buttons past 20 steps; steppers commit debounced, sliders on release), with `x-unit` (`px`, `%`, `ms`, …) after the value and `x-control: "slider" | "stepper"` overriding the choice; `x-auto: { value, start }` puts a switch in front of an integer whose `value` means automatic (on stores `start`, then the number shows: an edge menu's `padding`, `triggerLength`). `x-control: "readonly"` shows a string with a copy button instead of a field (an edge menu's `id`).
- Types: `x-icon` (a Material Symbols name) on bar widget, overlay module and view definitions; on overlay modules `x-defaultSize` (`[w, h]` in grid units: the size it's added at), `x-minSize` (the least a drop into a gap shrinks it to; half the default when left out: `OverlayConfig.minSize`), `x-hosts` (`overlay`, `edgeMenu`, `lockscreen`, `greeter`; the first two when left out, so the lock screen and the greeter only take modules that list them) and `x-required` (part of every grid on its hosts: never removed, duplicated or in the library; the lock screen's `Password`); `x-tool: true` on the hand-built view types (the navigator's tool group); `x-hypr*` on Hyprland options (see HyprlandConfigManager), and `x-greeter: true` on the `Hyprland.managed` options the greeter's Hyprland takes (see Greeter). A `$ref` may carry keys beside it (`default`, `title`, …) that override the definition's (`SchemaValidation._resolve`): `Lockscreen.layout` and `Greeter.layout` share `definitions/ScreenLayout`, each with its own default modules.

**The settings page:** `methods/SchemaLayout` turns the schema into categories → groups → rows; only this page builds its own rows, and flat objects (array items, widget/module options, a bar's fields) render through `forms/SchemaPropertiesForm`. An `array` of objects renders as an add/remove/reorder list (`SchemaObjectArray`, items `SchemaArrayItem`). Generated cards are `settings/SettingsGroupCard`; the Dock and OSD list cards are `EntryListCard`s (entries as tabs, a screen picker with presets (by default an edge's middle or the bottom edge's ends, with `spotOf` reading `edge`/`position`), Show/Duplicate/Delete, the entry's form; `entryContent` for extras such as the dock's pinned apps); both sit on `FoldingCard` (fold header with section line, heading, unsaved dot, chevron and `headerExtras`, and a `FoldingColumn` body). Status cards (Hyprland, Idle, self-update, chat providers, onboarding) are `FieldGroup`s with a `StatusChip` in `headerExtras`. Clicking a card's header folds it (`SettingsManager.collapsed`, by group key, saved to `config/state/settings.json`; search results never fold). The masonry reads `layoutFolds`, a snapshot taken on category/search change and page unload, so a fold doesn't reshuffle the page. The sidebar (`SettingsSidebar`: a `TitledCard` of `ListEntryRow`s, search in its header) lists the selected category's shown cards (`SettingsContent.shownGroups`, one per title) under its row, in a `FoldingColumn` that holds the links it opened with while it folds shut (by then `cardLinks` is the next category's); clicking one calls `SettingsManager.jumpTo(key)`, which unfolds the card and emits `jumpRequested`, and the content scrolls to it (`TitledCard.scrollTo`, after the unfold animation) and outlines it in the accent for a moment. A new category (or entering/leaving search) fades the content in, sliding from the side of the sidebar it was picked from (`_pageIndex`). Search results are grouped by category (`blocks`: a heading with the category's icon, then its own two columns). Other services open the page on a section's category with `SettingsManager.openSection(key)`, so they don't depend on category names.

**Themes:** `config/themes/*.json` (static) and `config/themes/generated/*.json` (from a wallpaper). Static themes keep the hue slots fixed (`base08` red, `09` orange, `0A` yellow, `0B` green, `0C` cyan, `0D` blue, `0E` magenta), even where an upstream base16 port reorders them, because the semantic names and the terminal ANSI colors read them by slot. A scheme without some hue fills that slot with its nearest color (Rosé Pine's pine as green, Dracula's purple as blue), and each scheme sets `accent` to its signature color. An extra dark variant points `paired` at its family's light theme, and the light theme points back at the main dark one. `config/json/theme-defaults.json` is the one fallback palette and semantic → base16 map (dark and light), read (through `ThemeManager.defaults`) by `Theme` for keys a theme omits and for a missing theme, and by `scripts/generate_theme.py`. The `scripts/theme_*.sh` integrations share `scripts/lib/theme_env.sh`: dependency checks; `load_theme` (one jq pass filling what a theme leaves out, as `Theme` does); `export_theme_colors` (every semantic color as `UPPER_SNAKE`, plus `ANSI_0`–`ANSI_15`); `render_template`/`write_atomic`. Each writes only its own `axiom.*` file (under `$XDG_CONFIG_HOME`, as the apps read it). A missing main config may be created with the hookup (cava's config, GTK's `gtk.css`); one that exists is never touched by a script. The exception is ncspot, which can't include a file: `theme_ncspot.sh` writes `$XDG_STATE_HOME/axiom/ncspot-theme.toml` and copies it between the two marker lines its Apply put in `config.toml`'s `[theme]` (`x-hookupNote` says so), leaving out keys the user sets in `[theme]` outside them; with no markers it only warns. It edits the file a symlink points at, rewrites only on a change, and sends `reload` to ncspot's socket. Zathura reloads through D-Bus (`SourceConfig` on each `org.pwmt.zathura.PID-*` name).

**Hookup** (loading that file from the app's config): each switch's `x-hookup` lists targets, `{ file, text, place, … }` that Apply can do or `{ text, where }` to copy (wezterm.lua, k9s's YAML, VS Code's and Zed's settings.json, Vesktop's Themes tab: Vencord keeps its enabled themes in a JSON array, and reloads `axiom.theme.css` live through its watch on the themes folder; the Flatpak Vesktop's folder is under `~/.var/app/dev.vencord.Vesktop/config/vesktop`), and `x-hookupNote` says what's peculiar (Alacritty's import order, lazygit's `LG_CONFIG_FILE`, Neovim). `scripts/integration_hookup.py status|apply <key>` (stdlib Python) does the work: `place` is `end` (read last, so it wins), `start` (CSS `@import` must come first), `top` (before the first `[section]`: TOML top-level keys, foot's main section), `section` (inside `[section]`, added when missing), `shellrc` (`$SHELL`'s rc; fish gets `conf.d/axiom.fish` with `set -gx`) or `copy` (Neovim's module, never overwriting); a line already setting the same key is commented out (`replace: comment`, the default), left beside it (`keep`) or blocks the target (`conflict`); `accept` is a regex for an equivalent line that already counts as done; `requires` skips a target without its command. A `perProfile` target is repeated for every browser profile the integration's `x-profiles` profiles.ini files list (Firefox and its forks, native and Flatpak; skipped as `profiles` when there are none), its `file` relative to the profile; `integration_hookup.py profiles <key>` prints those profiles, which is how `theme_firefox.sh` finds where to write `chrome/axiom.css` (imported atop `userChrome.css`, with `toolkit.legacyUserProfileCustomizations.stylesheets` in `user.js`; the browser reads it at startup). Apply backs each changed file up beside the real file (`<name>.axiom-bak-<time>`), follows a symlink and keeps it (so a dotfiles repo's file is edited), writes atomically, never deletes a line, and does nothing for a target already done. `--targets JSON` passes the targets instead of a schema key (with `title`, naming a target above its path, and `note`, replacing the line about where it goes): the Hyprland lines (HyprlandConfigManager). `IntegrationHookupManager` runs it (`check(key)` → `status[key]`, `apply(key)` → `results[key]`, then checks again, and runs the integration for the current theme when Apply changed something; nothing polled), and `forms/IntegrationHookup` shows it under a switched-on integration: the status, per target the text with a copy button and an outline of what Apply will do (backup, link, where it goes, lines commented out), then Apply. `SettingsField` adds it under any field with `x-hookup`; the onboarder's Integrations page lists the switched-on ones under "Finish setting up". Only Apply, on the user's click, edits a user's config.

**Neovim** has no line to add: colorschemes come from plugins, often loaded lazily after init.lua, so `theme_nvim.sh` writes `$XDG_STATE_HOME/axiom/nvim-theme.json` and calls `require("axiom_theme").reload()` in each running instance. `scripts/templates/nvim/axiom_theme.lua` is that module (copied into the user's config by Apply): its `M.map` maps every shipped theme's file stem to that theme's usual colorscheme plugin, `setup({ map, fallback })` merges the user's entries over it, and any other theme (or one whose plugin lazy.nvim doesn't know) is built from its base16 palette (mini.base16 when installed, else plain highlight groups), then given the theme's accent, Material-style (`apply_accents`: keywords, titles, the cursor line number, and selection/search/menu backgrounds blended from it), so a wallpaper theme's seed color leads. The JSON carries `colors` (base16), `semantic` (resolved hex) and `text` (accent and accentAlt floored to readable contrast against the background).

A new integration is a script, a schema boolean with its `x-hookup`, a reader property and an entry in `ThemeManager._integrations`. `tests/scripts/test_scripts.py` renders every theme through every script and parses each output as its format, and runs every hookup on empty configs.

## Translation (`config/I18n.qml`)

`General.language` picks the language. English is the source language: user-visible text is written in English, inline, as `I18n.tr("Text")`.
- **Dynamic values** use placeholders, so the whole sentence stays one key: `I18n.tr("{0} updates", count)`. Don't build sentences with template strings.
- **Dates and times** go through `I18n.formatDate(date, format)`, never `Qt.formatDateTime`, so day and month names follow the language. Named formats come from `I18n.dateFormat("longDate" | "mediumDate" | "shortDate" | "monthYear" | "fullDate" | "dateTime" | "time24" | "time12")`.
- **The schema form translates itself.** The generic `Schema*` form widgets translate their own `label`/`title`/`description` and dropdown option labels. Callers pass English, and schema titles and descriptions need no code.
- **Adding a language** means adding `config/i18n/<code>.json`: `{"_meta": {"name", "locale", "formats"}, "strings": {english: translation}}`. It then appears in the language dropdown (`x-options: "languages"`).
- **Missing entries fall back to English.** The active dictionary reloads live when edited.
- **Checking coverage.** Run `scripts/check_i18n.py` after changing text; it lists missing and unused entries (`--fill` adds the missing ones empty, `--untranslated` finds UI literals not wrapped in `tr()`).
  - Keys only chosen at runtime (e.g. `I18n.tr(form.shape)`) must be declared in a comment next to the call, as `I18n.tr("square") ...`, so the checker sees them.
- **Leave developer-facing strings in English:** logs, validation errors, migration notes.

## Bar / widget composition pattern

`shell/Bar.qml` renders one `BarPanel` per entry in `BarManager.bars` (a `Variants`/model; the running bars, `Bar.enrichBarConfig`ed with Hyprland's `gapsOut`, which a reader can't read, along with what they leave on each screen edge: `edgesFor`, `screenEdgeOpen`, `reservedOn`, `frameLine`, `detachedGaps`), so multi-monitor / multi-panel bars are data-driven from config, not hardcoded. Each module's options live under its `<Type>Widget.properties.properties` definition in the schema. `SchemaValidation` picks the `BarWidget` oneOf option by `type`, so widget properties get their defaults filled like the rest of the config and modules read `properties.<key>` directly. Widget types come from `Bar.availableWidgetTypes` (the `BarWidget` oneOf: label from the type's description, icon from its `x-icon`). `WidgetGroup` models its widgets by count, so live option edits reach a widget in place instead of rebuilding the section. The main-axis layout math (sections placed along the bar, the widgets hidden when it overflows, elastic widgets squeezed within a section) is pure, in `methods/BarLayout` (tested in `tst_BarLayout`); `BarContainer` and `WidgetGroup` only feed it measurements. Bar contents are built from `components/bar/{BarContainer,BarWidgetHost,WidgetGroup,BarPanel}.qml` composing widgets from `components/bar/widgets/<type>.qml` (Time, Battery, Network, Workspaces, Media, SystemTray, Notifications, etc.). A widget opens a popout by dropping in a `PopoutAnchor` with a `popoutName`; the per-bar `BarPopouts` (in `hosts/popout/`) loads `content/<popoutName>.qml` by URL, so a new popout is a content file plus an anchor.

**Bar widgets.** Icon + label widgets extend `bar/widgets/BarIconWidget.qml` (the `BarWidgetHost` inputs `barConfig`/`popouts`/`panel`/`screen`/`properties`, orientation, configured colors; override `backgroundColor` for states; `hidden` collapses one with nothing to show). It owns their pointer handling: `clickable` + `acceptedButtons` → `clicked(button)` (dimmed while pressed, off while hidden), `scrollable` → `scrolled(steps)`, `hovered` (what an edge menu a Button opened stays open for) and `dim` for fades of their own. Volume and Microphone share `AudioLevelWidget`. Widgets that draw their own content extend `bar/widgets/BarWidget.qml` (the same inputs and `isVertical`); `reusable/BaseWidget` is the sizing/background wrapper under both. Sizes come from the bar (CLAUDE.md): `Bar.enrichBarConfig` derives `extent` from `widgetSize` plus padding and whatever covers the bar, and resolves `fontSize`/`radius` from the bar's `overrideFontSize`/`overrideRadius`, else Appearance's and `Widget.radius`. **Widget style.** Widgets don't draw their own backgrounds: each reports `hasBackground` (on by default for `BarIconWidget`, opt-in on `BarWidget`) and an `accentColor` (its color for its state, the old background: a critical battery, a muted mic), and draws in `colors` = `Bar.widgetColors(barConfig, accent, foregroundName)` (`{ fill, stroke, indicator, text, icon }`, worked out by the pure `methods/BarWidgetStyle` from the bar's `widgetStyle`: filled, tinted, outline, underline, colored icons, plain; `widgetTextColor` overrides the automatic text color). **Auto colors.** A widget color field with an `x-autoColor` role is Auto when empty (its default): `Bar.enrichBarConfig` fills it in the widgets it hands out (`Bar.withAutoColors`, the fields per type in `Bar.autoColorFields`), so widgets just resolve `properties.X`. The pure `methods/BarAutoColors` picks along the bar's shown widgets, every section in order: `accent` (the widget's own color: a base08–0F accent unlike its neighbours', fixed ones included, every one used before any repeats, and kept apart from its own warning/critical colors), `alt` (a second state, as unlike its accent as possible), `warning`/`critical` (the theme's `warning`/`error`), `off` and `neutral` (the subtlest of base01–04 that stands out: an off state, or a box whose content has its own colors, the tray's and Workspaces'). Each must stand out (WCAG contrast) from what it's seen on: the bar, or a filled merged run's `groupColor`; a fill only has to show (1.3), text, strokes and icons have to read (3). Text colors and Workspaces' cells (but its active one) aren't Auto. **Look groups.** A bar's widget style, accents and shadow come from the `BarStyle` section (Look & Feel, reader `BarStyle`), each group unless the bar overrides it (`overrideWidgetStyle` / `overrideAccents` / `overrideShadow`, its fields shown only then): `Bar.lookOf` fills them in before `enrichBarConfig` (`Bar.lookGroups`: each flag and the keys of its `x-group`). The section's fields and the bar's copies are kept identical by `tst_Config`'s `test_bar_look_fields_match_bar_style`. Workspaces sits on a background like the rest (`backgroundColor`), its cells (`workspaces/WorkspaceCell`) inset by `widgetSpacing` inside a box; its box is Auto (`neutral`). The cells draw in the same style (`Bar.cellColors` → `BarWidgetStyle.cell`, `{ fill, stroke, indicator, content }` from the cell's state color): filled, tinted or outlined boxes, or with no box (underline, colored icons, plain) its number or a dot (a pill when wide, the cells narrowed to fit) straight on the bar, each underlined itself for underline (the widget's own line is off); there an empty cell's content is the bar text faded, and plain tells the states apart by fading alone. `WidgetGroup` draws a `bar/WidgetBackground` under each host that has one (`BarWidgetHost.background`, following its geometry and `contentOpacity`), in the bar's `widgetShape` (rounded, capsule, slanted, arrow), `widgetEnds` (a slanted or arrow widget's or run's own ends: shaped (an arrow's notched and pointed); pointed at both, an arrow's alone (`x-enumShowIf`); or rounded) and `widgetGrouping`. Neighbouring widgets with backgrounds form runs (`BarLayout.runs`/`runPlaces`): **merged** draws one background per run in `groupColor` (`Bar.groupColors`), its widgets' colors moving to their icons (`BarWidgetStyle`'s `group`); **powerline** chains them with no gap (`groupSpacing` 0), each segment's end cap running into the next, which reaches back under it (`back`; with a see-through fill, tinted or outline, it fits against it instead, and an outline's two strokes lie on the shared seam: `seamStart`/`seamEnd`). A segment's content is centred on what shows of it (from half a join before its box to half a join before its end), so its `trail` takes the difference. A widget shown without a background (the Separator) splits a chain, keeping `spacing` to the widgets beside it in its section (none at the section's end, where the gap to the next section stands in, as on any bar); one showing nothing (hidden) is passed over (`runs` flags it null). `methods/BarShapes` gives each widget's caps and the room its content keeps clear of them (`segment`), which `WidgetGroup` sets as the host's `leadInset`/`trailInset` (added to its sizes, the module inset by them), and the outline as an SVG path (`path`; a `Rectangle` draws rounded and capsule ends). Insets follow what widgets have to show, never the room they're given (which the insets help decide), so they can't feed back into the layout; shapes follow what's shown. The background follows a widget's `dim` (not its press fade, which would show a powerline neighbour's square start through it), and draws a press as a tint of its text color (`pressed`), the hover outline (`hoverOutline` widgets: Button) and the bar editor's highlight in the widget's shape as it shows (`shownStart`: a powerline segment's start is the cap before it, whatever it's drawn with), inset all round. Widgets are hovered and clicked in that same shape: `WidgetGroup` hands each host with a background its drawn segment (`hitShape`), the host keeps a `hitArea` item over it (reaching `back` under the segment before) whose `mask` tests points with `BarShapes.contains`, over the module, tracking `hovered` with its own HoverHandler; `BarIconWidget`'s MouseArea reparents into it (clicks in the shape), and a `PopoutAnchor` given the widget's `hitArea` reads its `hovered` (nothing under the hit area is hovered, so a widget with several anchors, the tray's icons, gives each one `hitArea.hovers(item)`, as the Workspaces switchers pass the widget's on to their anchors) (a HoverHandler moved in after it's made isn't reliably hovered); so slants and arrows have no dead gaps or cut-off corners that answer for a neighbour. **Separators at a section's end** stand in the gap between sections rather than in their own (`BarLayout.edgeHang`, from each group's `divides` widgets): the center section is centered without them (`layoutSections`' `centerHang`; `overflowHidden` reads `divides` from the measures itself), and they're left out of the section's pill or island (except at the ends of the first and last sections showing, where they're padding), so a Separator closing the center and one opening right-center look the same. **Accents.** `WidgetGroup` draws a `SeparatorMark` in each gap between shown widgets (`separatorStyle`; none beside a widget that `divides`, the Separator, nor in a powerline). `BarContainer` paints the bar in one `surface` layer (its background, inner stroke and pills), so a `shadow` (a `MultiEffect` shadow falling toward the windows, cast evenly by pills, which join the edge they grow from; or a glow) follows their outline without redrawing for the widgets; `shadowReach` widens the bar window on its inner side, the input mask staying the bar. The screen border casts the `BarStyle` section's shadow inward all the way round (`RoundedBorders`' shadow window: one click-through, exclusion-ignoring window over the screen, the frame's shape blurred and masked to its inside (`innerInset`: past a solid bar reserving its edge), in the `axiom-border-shadow` namespace, whose layer rule (`order = 11`) stacks it under every other axiom surface, the overlay backdrop included); a solid bar reserving its edge under the border casts none of its own (`Bar.enrichBarConfig`'s `borderShadowed`). `Bar.shadowColor` resolves a shadow's color for both. Above it, an `AccentLine` runs along the bar's inner or outer edge (`accentLine`, fading into `accentLineFade`), inside whatever stroke lies there, or along each pill. Colors that are content rather than a background (workspace cells, separators, badges, the DND icon) stay the widget's own. A bar whose `monitor` is `"*"` is expanded by `Bar.expandBars` into one entry per screen (id `<id>@<screen>`, `sourceId`), the primary monitor's first; any other bar's monitor is resolved to a connected screen there.

**Icons** are Material Symbols names (`ttf-material-symbols-variable`, fonts.google.com/icons) drawn by `reusable/StyledIcon` in `Appearance.iconFamily`; it draws anything that isn't a name (a glyph or text typed into an icon field) in the text font. Services, schema defaults (`x-icon`, icon fields) and launcher `glyph`s hold names. `DependencyManager` warns once when the font is missing.

**Bar motion: drawn, not measured.** The layout (`naturalSize`/`preferredSize`, `WidgetGroup.allocation`, `BarContainer.slots`, a section's `mainPos`/`usedLength`) is measured from modules' implicit sizes and never animates. What's drawn glides to it: each `BarWidgetHost`'s `x`/`y`/`width`/`height` (animFast, off until `_settled`), with the module laid out at its target `mainSize` and centred in the drawn box (clipped while they differ, so labels never re-elide mid-animation), and each `Section`'s `drawnPos`/`drawnLength`, which `_spans` and so the pills read. Backgrounds and separator marks follow the hosts as drawn; a widget going keeps its last place and colors while its host still draws, fading with its opacity. `BarContainer.layoutMoved()` emits `layoutUpdated` at once and again after `animNormal`, so an open popout re-anchors on the settled widget. Colors (`WidgetBackground`, `IconTextWidget`) fade with ColorAnimations; the tray's icons grow in (Grid `add`/`move`).

## Workspaces (`Workspaces` section, `WorkspacesConfig`)

One layout serves everything that shows or moves between workspaces: the `Workspaces` bar widget, its `WorkspaceGrid` and `WorkspaceStrips` popouts, the workspace overview (`surfaces/workspaces/`), the `WorkspacesMap` module, the launcher's `/ws` and the `workspaces` IPC target.
- **Layouts.** `standard` is ids 1..`count`, shared by every monitor. `perMonitor` gives each monitor its own block of `count` ids and `grid` one of `columns × rows`, numbered in a stable monitor order (`WorkspaceGeometry.orderMonitors`: the primary first, then by output identity; `WorkspacesConfig.baseFor(index)`). Nothing else holds a workspace count or grid size.
- **Ids.** `HyprlandManager.workspaceBase(monitor)` / `workspaceIds(monitor)` give a monitor's ids. The overview lays them out `boardColumns × boardRows`; in the standard layout it shows windows from every monitor, each placed against its own monitor's origin.
- **Navigation.** Everything goes through `HyprlandManager.goToWorkspace(id, mode, monitor)`, `stepWorkspace(direction, mode)` and `nthWorkspace(n, mode)`, including focusing a window on another workspace (`focusWindow`, used by the overview, dock, launcher and notifications), so every switch slides the same way. Surfaces on a monitor pass their `monitor` (focused first; in a grid an id outside the focused monitor's block is otherwise refused). Never dispatch `hl.dsp.focus({ workspace })` or `{ window }` directly. `mode` is `go`, `move` or `moveSilent`. In a grid it only reaches the monitor's own ids, going sideways, then vertically, a slide along each axis in turn (`animate`; each leg of a two-leg trip at `_legSpeed` of the configured time). The slide briefly overrides Hyprland's `workspaces` animation (read with `hyprctl animations` at startup and on config reload) and puts it back. Keybinds call `qs -c axiom ipc call workspaces …` instead of scripts of their own.
- **Layout changes.** Hyprland's workspaces stay where they are when the layout or size changes, so `HyprlandManager` remaps them (`_remapWorkspaces`, 200 ms after `perMonitorBlocks`/`size` change, from the layout it last applied): `WorkspaceGeometry.remapWorkspaces` (pure, tested) sends each workspace's windows to the same place in its own monitor's new ids (the first in monitor order keeps a contested id, the rest take free ones, merging only when none is free) and picks each monitor's new active workspace. One Lua chunk does it with the `workspaces` animation off: windows to `name:axiom-remap-<id>` (created on their own monitor, so a chain like 10 → 11, 11 → 12 can't merge), every monitor to `name:axiom-remap-mon-<i>` (so its old, maybe empty, workspace is gone before its id is reused), windows to their ids, then monitors to theirs, the focused one last. IPC `workspaces reconcile` runs it for the current layout, re-homing workspaces left outside their monitor's ids.
- **The bar widget.** `bar/widgets/Workspaces.qml` loads `workspaces/WorkspaceStrip` (standard) or `workspaces/WorkspaceGridStrip` (the active row, or column on a vertical bar) by layout, both with the active `WorkspaceCell` twice as long under `wideActive`. Both lay their cells out with `workspaces/WorkspaceCellRow` (every shown workspace, or one grid row; `glyphOf` for the grid's position arrow): the active cell's box is one `workspaces/ActiveCellIndicator` sliding along the row, drawn between the cells' two parts (`WorkspaceCell`'s `part`: the boxes at rest under it, the labels and icons over it); a step past an end (`HyprlandManager.workspaceWrapped`, or the strip's own wheel wrap) sends it out of that end and in at the other. The grid strip cross-fades (`CrossFade`) to another row or column, the old one keeping its active cell while it fades, and `ActiveStrip` cross-fades the windows of the next workspace. The widget keeps its start put while its box resizes (`pinStart`, which `BarWidgetHost` reads), so its cells don't drift as the strip after them comes and goes. Their options share one schema definition: layout-only options hide themselves with `x-showIf: { "/Workspaces.layout": … }`. In a grid the widget hands its `properties` and its bar's config to the `WorkspaceGrid` popout, whose cells are the strip's `WorkspaceCell`s: the same size, spacing, corners, widget style, colors, labels (grid position), app icons and click to switch.
- **Strips.** `strips` lists monitors on Hyprland's scrolling layout (`{ monitor, direction }`; `*` every monitor, a named entry winning over it, empty the primary monitor; how it reaches Hyprland is under HyprlandConfigManager), with `stripColumnWidth`/`stripFollowFocus` (shown while there are strips: `x-showIf` `{ notEmpty: true }`). `WorkspacesConfig.strips` resolves the monitors and keeps a monitor's first entry; `stripDirection(screenName)` is `horizontal`, `vertical` or `""` (tiles). Hyprland reports no columns, so strip order is the windows' places (`WorkspaceGeometry.stripOrder`: tiled windows along the strip, a column's across it, floating ones last; `HyprlandManager.stripWindows(id, vertical)`). On a strip monitor both switchers follow their workspaces (all of them, or the shown grid row) with `workspaces/ActiveStrip`: a divider (`SeparatorMark` in the bar's `separatorStyle`, a line when that's none), then the active workspace's windows in that order (`workspaces/StripWindows`: bar cells with app icons, the last focused one active, click focuses). The wheel scrolls the strip a column at a time (`HyprlandManager.stepStrip`: `layout("move ±col")`, on the focused monitor only, since layout messages act on the focused workspace, and only with windows on it, since Hyprland refuses it on an empty one). Hyprland focuses the column it moves to and warps the cursor there. `WorkspaceStrip`'s popout there is `WorkspaceStrips`: each occupied workspace (and the active one) as its number cell then its `StripWindows`. The overview squeezes a strip workspace's tiled windows into its cell along the strip (`WorkspaceGeometry.stripRects`), so off-screen columns show, and a tiled window dropped on one lands as a new column after the nearest (`stripDropTarget`: `placeWindow` focuses the target, after which scrolling opens it). The Keybinds page's Strips preset (listed while there are strips) binds the `strip*` dispatcher actions (`swapcol`, `colresize ±conf`, `fit visible`), and `SUPER + mouse_down`/`mouse_up` to focus right/left (`focusDir`), which moves along the strip. The onboarder's Workspaces page offers tiling, horizontal or vertical strips on every monitor, and the list for per-monitor ones.

## Window switcher (`WindowSwitcher` section, `WindowSwitcherConfig`, `WindowSwitcherManager`)

Alt+Tab: the bind actions `windowSwitcher` and `windowSwitcherReverse` (defaults ALT + Tab and ALT + SHIFT + Tab; the Keybinds page's "Window switcher" preset adds them to an existing config). **Hyprland holds every key**, since a surface can't see a modifier released before it maps and takes focus (a quick tap always is):
- The bind is a Lua function (`HyprLua.switcherBindLua`) that enters the `axiom_switcher` submap on the press itself, then emits `hl.dsp.event("axiom-switcher:step ±1")`. The submap (`HyprLua.switcherLua`, from the switcher binds `KeyNames.split`; emitted with the binds in every mode, in detached mode only for the binds applied) repeats each switcher combo as a step and binds Return (pick) and Escape (cancel). The release is no bind: Hyprland fires a release bind on a modifier only when no other key came between (a tapped SUPER), and Tab always does. Instead the bind starts `axiom_switcher_watch()`, an `input.keyboard.key` listener that, 10 ms after each key release, picks once none of the held keys (`AXIOM_SWITCHER_HELD`, from `switcherHeld`: the bind's modifiers but SHIFT, which only turns it around; `Alt_L`/`Alt_R`, …) is down by `hl.is_key_down`, and removes itself on leaving. Picking, cancelling and the listener all leave the submap in Hyprland itself, so it can't stick while qs is down. Redefining a submap adds to its binds, so the chunk first unbinds the keys its last run bound (`AXIOM_SWITCHER_KEYS`). KeybindManager leaves the submap out of the page, and flags a switcher key with no modifier to hold.
- What happens arrives on socket2 as `custom>>axiom-switcher:<verb>` (`Hyprland.rawEvent`: no process per key, in order; HyprlandManager ignores `custom` events). `WindowSwitcherManager.step(n)` opens on the first: a snapshot of `HyprlandManager.windowList` most recently used first (`methods/WindowOrder.mru`: by `focusHistoryID`, the event-driven `Hyprland.activeToplevel` first, since hyprctl's list lags a quick second switch; filtered by `DockLayout.inScope` for `scope`), on the focused monitor, fixed until it closes. `commit()` focuses the selection through `HyprlandManager.focusWindow` (nothing when it's the window focused at open); a tile click `pick`s and leaves through `HyprLua.switcherLeaveLua` (`axiom_switcher_leave()`: the listener stops and `HyprLua.leaveSubmap` resets, as the record submap leaves). A commit while closed does nothing, so a late Return or release can't refocus the last pick.
- It draws only once held for `showDelay` (`shown`), so a tap swaps windows invisibly. `shell/WindowSwitcher` is a `FloatingPopout` per screen (`axiom-switcher`, blurred with the launcher) shown on the opening monitor, holding `surfaces/switcher/SwitcherStrip` (a `TileFlow` of `SwitcherTile`s by count, up to 80% of the screen wide): the overview's `WindowPreview` (live while selected) or, with `previews` off, the app icon, over the title. It takes no keyboard focus, so focus stays on the window until one is picked.
- IPC `windowSwitcher`: `next`, `previous`, `commit`, `cancel` (no submap, so nothing picks on a release: for scripts and testing).

## Content (loaded by name, shown by hosts)

`components/content/<Name>.qml` holds every loadable panel. The name is the overlay module `type` (`OverlayModule.oneOf`) and/or a bar `popoutName`; one file can be both (AudioMixer, BluetoothDevices, Notifications, NowPlaying, SystemGraphs, Updates, WifiNetworks). Hosts load it by URL and pass their context:
- **Roots.** `Card` (`content/base/`) is a free-form card (box, `properties`, slot context); card-only content uses it. `Panel` lays its children out in a column and works in either host: in a bar popout it sizes to its content with the popout box (`wrapper` set, `hovered` read for dismissal); in a card the host passes `embedded: true`, it fills the slot with the card box, and `compactContent` (e.g. a `CompactFigure`) replaces the column when `compact` (see Writing overlay modules); a `Card`'s `compactContent` likewise replaces its children (they go into an inner item that hides). A bar popout's window never follows its content: along the bar it spans the whole bar (`windowFrom`/`windowTo`), and across it keeps the most room the box has needed since it opened (`BarPopouts.spareAcross`), or that the content declares up front (`maxImplicitHeight`/`maxImplicitWidth`, as the Calendar does for its editor), with the surface on the bar side, as `EdgePopout.maxContentDepth` does. Content changing size so redraws the scene instead of resizing the Wayland window (a compositor round trip the outline visibly lagged): the box animates to its new size and place (`shownBoxWidth`/`shownBoxHeight`/`shownBoxStart`, `animFast`, from the first frame it shows), while the content sits at its target size, hung from the box's start and bar side, clipped to the box. A popout with a text field sets `wantsKeyboardFocus` (BarPopouts then takes a focus grab and the bar takes keyboard focus on demand; a click outside emits `focusLost`). Both expose `properties`, `slotRect`, `cols`/`rows`, `shape`, `compact`, `pad` and `innerWidth`/`innerHeight` (the room inside `pad`).
- **Hosts.** `hosts/overlay/OverlaySlot` (card: `properties`, `slotRect`, `embedded: true`) and `hosts/popout/BarPopouts` (popout: `wrapper`, then, once loaded, the anchor's payload keys copied onto matching properties, so popouts declare what they take rather than reading `wrapper.currentData`). The tray's menu (`content/SystemTray`) is the one popout-only content rooted in a plain Item: it drives `TraySubmenuWrapper` through `wrapper`.
- Pairs that look different by design stay separate files: `Weather` (card) / `WeatherForecast` (popout), `ClockCalendar` / `Calendar` (the month and its events: the Time widget's popout and a module; both, and the CalendarPage view, are built from `parts/calendar/`).

- **Calendar parts** (`content/parts/calendar/`): `MonthGrid` (six weeks from the language's first weekday; owns the month shown, `step`/`showDay`/`showToday`, asks `CalendarManager.ensureMonth`; a dot per calendar with events on a day, modelled by the joined colors, or with `titles` the events in cells tall enough, by count with "+n more"; `showEvents: false` for a plain date picker), `EventRow` (calendar color, title, time and place), `DayAgenda` (a day's rows under its date, + to add, empty and no-calendar states), `EventEditor` (`open(draft)` of a `CalendarEvents.newDraft`/`draftOf`; asks This event / All events for a recurring one; read-only for a calendar axiom can't change), `DateTimeField` (a date button folding a `MonthGrid` open, and a typed time), `DayPane` (the agenda turning into the editor, `editing`). Drafts and everything about days, spans, dots, what's next, reminders due and quick add are pure, in `methods/CalendarEvents` (tested in `tst_CalendarEvents`).
- **Pure helpers** (`methods/Utils`): `clone`, `freeId(base, taken, sep)` (`dock2` → `dock3`), `spaceWords` (CamelCase → words), `edgeArrow(edge)`, `formatRate`/`rateParts`/`formatSize`, `recordUse`, `truncate`; `Paths.expandHome`/`shortenHome`; `KeyNames.modifierLabel`.

## Overlay composition (views → modules on a grid)

`Overlay.views` in the schema drives the overlay's pages, just as `Bars` drives the bar. A Custom view is a grid of modules, each with a `place` `{ x, y, w, h }` in **grid units, four to a card** (a quarter card each). Everything loads by naming convention, so there are no lookup tables:
- **View** (`OverlayPages` → `OverlayView`): `components/views/<type>.qml`, a `BaseView` that receives the screen's `grid` and its `viewConfig`, and gives hand-built pages their sizes (`pageHeight`, two cards; `cardPageWidth`; `sideWidth`). `Custom` (`views/Custom.qml`) is one `ModuleGrid` of its `modules`, with its own `icon` in the navigator (`OverlayConfig.pageIcon`; empty is the type's). `Themes`, `Keybinds`, `BarEditor`, `Settings`, `Monitors` and `CalendarPage` (the month with its events, the selected day's `DayPane`, and the calendars to switch on and off; not `Calendar`, which `views/Themes`' import of `content/` would see twice) are hand-built tool pages (`x-tool`), with their pieces in `views/<page>/`; `Layouts` (the layouts editor, `views/layouts/`) is pinned, not in config. `ShellManager.showOverlayPage(type)` switches the overlay to a page (`qs -c axiom ipc call overlay page <type or name>` opens it on one).
- **Grid** (`methods/GridPlacement`, pure, tested by `tst_GridPlacement`): `unitOf(card)` is a unit's size (`(card - 3 × spacing) / 4`, 110 px at the reference 500) and `span(n)` n units plus the gaps between, so `span(4)` is a card and `span(2)` half of one. `bounds(modules)` is how far they reach; `canPlace`/`overlaps` keep modules apart (holes are fine); `firstFree(modules, w, h)` finds a spot in reading order, else beside (or below a wide grid); `normalize` shifts a grid so its top left module sits at 0, 0; `trackSizes(bounds, unit, stretch)` gives one unit's width and height and the grid's size, growing either axis evenly into `stretch` room (never shrinking); `rectPx(place, sizes)` places a module; `fitScale` is how much an overlay's room shrinks a page. Edge menu geometry: `menuLattice`/`latticeOf` (the cells a menu sits on along its edge: as many as fit between the frame's pads, centred there, moved `gridOffset` px), `menuCell`/`alongStart`/`menuAlong` (where its modules start: centred on the lattice, `offset` cells on, kept on it), `offsetFor`/`offsetRange` (the offset for a cell, and those that keep it on the lattice), `unitsAlong`, `menuPlacement` (where they sit on the screen, in px), `menuOnScreen` (its box and modules' rects there), `menuReservedDepth` and `screenBox`. The layouts canvas: `canvasExtent` (the units drawn around the grid, and the `view` fitted: a menu's screen and a unit round it, in fractions, so the screen stays put while modules move on it), `canvasFit` (the view's scale and origin in the area), `canvasRect`/`canvasScreenRect`, `canvasDropPlace` (where a carried module lands, held by the unit it was grabbed by) and `edgeBand`/`edgeBar`.
- **Host** (`hosts/overlay/ModuleGrid`): sizes itself from `grid.sizes(bounds, stretch)` and places one clipped `OverlaySlot` per module (keyed by count), passing `GridPlacement.rectOf(place)` as the module's `slotRect`; it warns once for a module that overlaps another.
- **Module** (`OverlaySlot`): `content/<type>.qml`, filling its place. Its root is `Card` (box, `properties`, slot context; override only what differs, like `color`) or `Panel` (see Content). Titled scrolling panels (ThemePicker, the bar editor panels, the settings page's content) use `TitledCard`, which has a `CardHeader` with `title`, `dirty`, `save()`/`reset()`, `headerExtras`, children that go into the scrolling body, and `scrollTo(item)` (animated, to bring a descendant to the top). Adding a module means the file plus an `…OverlayModule` definition in `OverlayModule.oneOf` (with a `"place": { "$ref": "#/definitions/GridPlace" }` property like the others). Every module takes every size, from one unit up; `x-defaultSize` is only the size it's added at (left out, a card: `OverlayConfig.defaultSize`), and `x-minSize` only how far a drop into a gap shrinks it. Helpers used only by content go in `content/parts/` (subfolders for groups, e.g. `parts/settings/`). `OverlaySlot` imports `qs.components.content` so that `qs` scans the URL-loaded content; without it, their own `qs.*` imports fail with "not installed".

Views and modules are `oneOf`s discriminated by `type`, like `BarWidget`.

**Sizing:** the card size is per screen, not a constant. Each `OverlayPanel` has an `OverlayGrid` (`hosts/overlay/`) whose `unit` is what fits the page area above the navigator (`min(height / fitCardsHigh, width / fitCardsWide)`, capped at the reference `OverlayConfig.cardUnit` 500, times `Overlay.size`%, never below `minCardUnit`), and reports its room to `OverlayManager.reportArea` (the layouts editor's "fits" line). Views receive it as `grid` (`BaseView`) and size everything from `grid.unit` / `grid.span(n)` / `grid.sizes(bounds, stretch)`, passing plain numbers down to content; `OverlayConfig.span` without a unit, and `OverlayConfig.gridUnit`, are the reference size. A page that still doesn't fit is shrunk as a whole by `OverlayPages.fitScale` (Item.scale, last resort). `cardSpacing`/`cardPadding` don't scale.

**Loading:** one overlay per screen in `General.screens` (`shell/Overlay.qml`): a transparent `OverlayPanel` inside the reserved area (placed by its base, `ReservedAreaWindow`, shared with the onboarder), over a `reusable/ScreenBackdrop` that dims the whole monitor under the bars and border (a Top-layer surface kept under them by a Hyprland `order` layer rule that `HyprlandManager` adds at startup and on config reload; the workspace overview and launcher use it too). Its `HyprlandFocusGrab` also whitelists `ShellManager.grabPartnersFor(screen)`: the bars, bar popouts and tray submenus register themselves there (`registerGrabPartner(window, screenName)`), so they keep working while it's open. Only the current page and its neighbours (navigation wraps) are instantiated, and only while the overlay is open (`OverlayPages.isLoaded` → `OverlayPage.loaded`), so modules must not assume they live forever: acquire in `Component.onCompleted`, release in `onDestruction`, and keep state that must survive in a service. Pages come in two groups: the user's own (Custom) pages first, then the tool pages (view types with `x-tool`: Settings, BarEditor, Themes, Keybinds, Monitors), each group in config order (`OverlayPages.buildViewsModel`; `viewsModel[i].index` is the view's place in config), then the pinned Layouts page. Under the pages, `OverlayPageNavigator` shows a tab per page (`OverlayPages.pages`: icon, name and `tool` from `OverlayConfig.viewIcon`/`viewLabel`/`isTool`, shared with the layouts editor) with a sliding accent pill; tool tabs follow a divider as icons only (named in a tooltip), even when current, and when all names don't fit, the other tabs drop to icons too. A view with `visible: false` stays in config but isn't shown.

**Writing overlay modules:**
- **Any size.** `Card` and `Panel` (and `TitledCard`) take what they derive from their place from `base/SlotContext`, and expose its `slotRect` (`[x, y, w, h]`), `cols`/`rows` (grid units, four to a card), `shape` (`square` while the longer side is under 1.5× the shorter, else `horizontal`/`vertical`: `GridPlacement.slotShape`) and `compact`, plus `pad`. A unit is 25 to 140 px depending on the screen or menu (`OverlayGrid`; an edge menu uses its screen's overlay's) and text doesn't scale with it, so a module sets `fullMinWidth`/`fullMinHeight`, the px its full layout needs; `compact` is a quarter card or less (`cols <= 2 && rows <= 2`) or, once laid out, smaller than those. Compact shows the key figure (a `compactContent`, usually a `CompactFigure`, on Card, Panel or TitledCard); otherwise the module picks its layout from `shape` and its px room: side by side when wide, stacked when tall, sections dropped or rearranged where they don't fit (Weather's hours and days, ClockCalendar's calendar, Disks' header and columns), and a one-row form for strips where it has one (NowPlaying, AudioMixer's slider, Network). Thresholds that depend on text are in px from `Appearance.fontSize`, not grid units. An edge menu's units aren't square, so a layout choice that must match the slot's real proportions reads `innerWidth`/`innerHeight` rather than `shape` (NowPlaying's side-by-side). A bare edge menu module drops its padding, unless it draws a box of its own (`drawsBox`, e.g. NowPlaying's blurred cover), which keeps it inside that box.
- **Shared parts** live in `content/parts/`: `ModuleHeader`, `Sparkline`, `StatFigure`, `TileGrid` (lays out `reusable/ActionTile`s, the icon-well tiles the power menu also uses), `RateLabel`, and the radio menus' `RadioHeader`, `DeviceList` (fixed-height in a popout, off and empty states) and `DeviceRow` (confirm-to-forget, connect; extras beside the title and content under it), shared by WifiNetworks and BluetoothDevices. `FigureValue` is the bold value + unit row of `StatFigure` and `CompactFigure`. `CompactFigure` fills its box (inside `pad`): icon, value and label stacked, or the icon beside them in a wide box, dropping the label and then the icon as room runs out and shrinking the value to fit. `EmptyState` takes an `availableHeight` and drops to its icon when short. `PasswordField` is the lock screen's field and `LoginField` the greeter's box (see Lockscreen); `FocusKeeper` keeps the keyboard on them. Generic controls: see "Shared UI pieces".
- **Content can be both.** A `Panel`-rooted file is a bar popout and a card at once; branch on `embedded` for card-only parts (a header, a mode switch, acquiring with the card's `properties`).
- **Data sources.**
  - `SystemManager` adds `history: true` (60-sample ring buffers), a `net` metric (`/proc/net/dev` rates; the connection itself is `NetworkingManager.netInfo`) and a `processes` metric (two-frame `top`, with `kill(pid)`).
  - Weather comes from `WeatherManager` (`acquire(owner)`, read `source`): one `WeatherSource` for the Weather settings' location, units and refresh interval (`WeatherConfig`), shared by every bar widget, module and forecast popout. It fetches only while acquired and keeps its last data when released.
- **Repeater models** (rule in CLAUDE.md): for a derived set, `model: rows.length` with the delegate reading `rows[index] ?? fallback`; an `int`/`string` only notifies when it actually changes, so delegates (and Canvases) survive each sample or keystroke.
- **Testing a module safely.**
  - The running shell only picks up schema changes on a QML reload, and a reload only fires when a file it has *loaded* changes. A new module file doesn't count until something uses it.
  - A config checked against a stale schema fails validation, and the whole shell falls back to defaults until it's fixed.
  - So confirm the schema was reloaded after your edit before putting a new module into `config.json`. Add modules one at a time and watch `qs`'s RSS.

**Themes page:** `views/Themes.qml`, the `Themes` view type (in `Overlay.views` like any other, with nothing to configure). A `BaseView` in the editors' shape that hosts ordinary modules directly (as the onboarding Look page does): `WallpaperPicker` at `sideWidth` (two cards tall it adds a monitor picker and a preview, and sets the picked monitor's wallpaper), `ThemePicker` (the theme list and light mode switch), and a column of `Palette` (the 16 base colors with their hex and the semantic names that map to each, `Theme.roles`, written under each tile) over a Look card (`SettingRows` for font, corner radius and animations, and a link to Settings → Look & Feel).

**Layouts editor** (overlay pages and edge menus in one page):
- `views/Layouts.qml` with its pieces in `views/layouts/`. It's not in config: `OverlayPages` adds it (`pinnedPages`) as a persistent page after the Repeater, so it's always last, can't be removed, and survives the page rebuild that every `Overlay.views` change causes (pages are keyed by the views' JSON, so other config edits don't rebuild them; `_onPinned` keeps the user on it across that rebuild).
- What it edits is `OverlayManager.editTarget`: `"page"` (`OverlayManager.selectedViewIndex`, its draft of `Overlay.views`), `"menu"` (`EdgeMenuManager.selectedMenuIndex`, its draft of `EdgeMenus`) `"lockscreen"` (`LockManager.editor`, its draft of `Lockscreen.layout`) or `"greeter"` (`GreeterManager.editor`, of `Greeter.layout`); `editPage(i)`/`editMenu(i)`/`editLockscreen()`/`editGreeter()`/`editPages()`/`editMenus()` switch it. The lock screen's row shows only while `Lockscreen.mode` is `quickshell` (`lockscreenEditable`) and the login screen's only while `Greeter.enabled` (`greeterEditable`); `editTarget` falls back to `"page"` when its row hides (the launcher's `/layouts` and `/menus`, `ipc call edgeMenu edit`). Each is an `EditTarget` (`PageTarget`, `MenuTarget`, and `LockscreenTarget`/`GreeterTarget` on `ScreenLayoutTarget` in `views/layouts/`: the editor, modules, title, icon, screen box, fit line, …) that `Layouts.qml` binds the canvas and inspector to. Save/Reset on the canvas save or reset all four drafts, and `EditsManager` lists the page as unsaved when any is dirty.
- Layout: `LayoutsPanel` on the left (`PagesSection`: your pages, with show/hide, duplicate and remove actions and New page under them, then the tool pages as a dimmed group with only show/hide (every tool page is always in config; ConfigMigration v33 put back any that were removed, hidden), each group dragged to reorder within itself, then the Lock screen and Login screen rows (not pages, not dragged); `MenusSection`: the edge menus, dragged to reorder, duplicate/remove, New menu; then a page's name and icon, a tool page's Show in the navigator, and for any page buttons adding a bar Button or keybind that opens it (`OverlayManager.addBarButton`/`addKeybind`, the `overlayPage` action on its `OverlayConfig.pageKey`: a Custom page's name, else its type; only for a saved page, so an unnamed Custom page has none), a menu's field groups, or a screen layout's (`LayoutsPanel.screenTarget`) Show on screen and field groups (`LockscreenConfig.fieldGroups`, ScreenLayout's), and "Can't save yet"), and on the right `GridCanvas` above `EditorInspector`, placed by `LayoutsEditorLayout`, a `GridDragLayer` covering it all.
- `GridCanvas` draws the selected page or menu at a scale it computes itself (not `Item.scale`): a lattice of unit squares (one `Canvas`) with room around the grid (`GridPlacement.canvasExtent`: a unit above/left, three below/right, or one past the screen), scaled to the area (`canvasFit`), `CanvasModule` tiles (drag to move: onto a module of the same size to swap, onto others to push them aside; drag any edge or corner to resize from that side (`GridPlacement.resizeFrom`), snapping to units, with a size readout; other tiles slide to where the drop or resize would put them, from the drag layer's `previewPlaces`, and the landing outline is red only where it can't be made), a menu's whole screen around it, where the menu really sits on it (`screenBox`: `EdgeMenuManager.screenBoxOf`, `GridPlacement.screenBox` from `placementOf`, below): a dashed outline with the units outside it tinted (they'd scroll), the screen edge as a faint accent bar with the menu's part solid, and a shaded band along it (`reservedDepth`, `GridPlacement.menuReservedDepth`, with a line where the windows start): the strip an integrated menu reserves, or the bars and border a floating one sits past. With "Show other menus" (`EdgeMenuManager.showingOthers`) the other enabled menus on that screen are drawn dimmed where they sit (`ghosts`: `EdgeMenuManager.othersOn`, in screen px through `pxScale`, since their module size can differ; not drop targets). Lattice squares and modules share `cellRadius`, and a header with undo/redo at its left, the module count, a menu's arrows moving it along its edge (Edge menus, Editing) and how it fits (per monitor for a page, along the edge for a menu). The inspector shows the selected module's options (`OptionsGroup`) and its Size (steppers in units, shown as cards: `GridPlacement.cards`), or else the `ModuleLibrary` (`ModuleChip`s to drag, or click to add at `firstFree`). With the canvas focused (a click, a selection): Ctrl+Z, Ctrl+Shift+Z / Ctrl+Y, and on the selected module arrows (`GridEditor.nudge`), Shift+arrows (`grow`, from the bottom right), Delete, Escape (deselect; with nothing selected it passes on and closes the overlay). A group selected shows its count and Remove in the inspector instead of the library.
- `GridDragLayer` payloads: `module-add { type, w, h }` (from the library, at the module's default size), `module-move { index, group }`, and the lists' `page-move`/`tool-move`/`menu-move`. Targets: the canvas (`targetKind: "grid"`, `placeAt(point, drag, grab)` snapped to units, a moved module keeping the unit it was grabbed by under the pointer, a new one held by its middle; `hoverPlan` is the editor's plan for a drop there (memoized per place), applied as is on the drop, and with a tile's `resizePlan` gives `previewPlaces`/`landingPlace`/`landingValid`) and `EntryListTarget`s (`"list"`: `takes(drag)`, `indexAt`, `dropRequested`, which reorder their own rows, each an `EntryListRow` carrying its list's `moveKind`).
- The canvas pieces name no service: they edit through `dragLayer.editor`, a `services/GridEditor` (non-singleton: one grid of modules, its `selected` index, `addModule`/`moveModule`/`resizeModule`/`duplicateModule`/`removeModule`/`updateModuleProperty`, the `canAdd`/`canMove`/`canResize` checks and `problemsFor(modules, name)`. Drops, moves and resizes are first a plan (`planAdd`/`planMove`/`planResize` → `{ kind, index, type, place, places, valid, noop }`, made by `applyPlan`): a new module dropped on a free cell takes the most of its default size that fits there, down to its `minSize` (`GridPlacement.fitPlace`), else (and a move or resize onto modules) it pushes what it lands on along `pushDir` (`GridPlacement.push`, cascading; down on a page, along an edge menu's edge: down a side menu, right along a top or bottom one), refused when that leaves a bounded grid; a move exactly onto a same-size module swaps them. A `TrashTarget` at the bottom of the canvas shows while a module is carried; dropped there it goes, with its group (required ones stay). Several modules selected together (`group`: a box dragged on the canvas background, Shift adding, or Shift/Ctrl+click; `selectGroup`/`toggleSelected`/`isSelected`/`selection()`) move as one (`planMoveGroup`, `GridPlacement.pushGroup`; the drag's `module-move` payload carries the `group`), nudge with the arrows and go with `removeSelection`. Every edit snapshots the modules first (plus the owner's `snapshotExtra`: an edge menu's offset) for `undo`/`redo` (50 deep; typing in one field is one step; cleared when the scope changes and by the owners' load/reset, `clearHistory`); each edit keeps the selection on its module (or group) and normalizes the grid, so a place left of or above it makes room there (on a `hold` axis a gap before the modules stays and only negative places are shifted back: a whole-edge menu's, along its edge, since it starts at the edge's start whatever its modules reach) (`shifted(shift, boundsBefore)` tells the owner, which EdgeMenuManager uses to keep a menu's modules on their cells); with an `area` `{ cols, rows }` the grid is bounded instead: places stay absolute and inside it, new modules go to `GridPlacement.firstFreeIn`, and `problemsFor` flags one outside it; required modules (`canRemove`) are never removed or duplicated, and a grid missing one is a problem). `OverlayManager.layout`, `EdgeMenuManager.layout` and each `ScreenLayoutEditor`'s `layout` (`LockManager.editor`, `GreeterManager.editor`, bounded by the layout's `columns` × `rows`) each own one, pointing `modulesOf` at the selected page's or menu's modules, or the lock screen's.
- Module and view pickers read `OverlayConfig.availableModuleTypes` / `availableViewTypes` (`modulesFor(host)` for the `x-hosts` filter). These come from the schema's `oneOf`s, including `x-defaultSize`, `x-icon` and `x-tool`, so new types show up there automatically. `reusable/TypePickerPopup` is the shared "pick a type" popup used by the bar editor and the page list.

## Edge menus (`EdgeMenus` section, `EdgeMenusConfig`, `EdgeMenuManager`)

Menus that pop out of a screen edge, holding overlay modules. `EdgeMenus` is an array like `Bars` (`x-settings: false`, blocked from `/config`: the layouts editor owns it). Each entry has `id`, `name`, `monitor`, `edge`, `mode`, `offset`/`gridOffset` (below), `length` (`content`: as long as its modules; `edge`: fitted to the whole edge, its rows (columns on a top/bottom edge) growing or shrinking evenly to take exactly the room (`GridPlacement.trackSizes` with `fit`, down to half a unit, scrolling only past that; `menuOnScreen` draws it the same in the editor), modules going compact below their minimum), `moduleScale` (% of its screen's overlay card size), style (`padding`, `moduleBorders`, `pinButton`, `backgroundColor`/`borderColor` read through `EdgeMenusConfig.colorsOf`, floating `detached`/`gap` (Popouts: held off an edge), integrated `frame`), opening (`openOnHover`, `openDelay`, `triggerSize`, `triggerLength`: 0 is the menu's length, `EdgeMenusConfig.lengthOf` from config until it's loaded), closing (`closeOnLeave`, `closeDelay`, `closeOnOutsideClick`) and `modules` (placed as on a Custom page). Escape closes a focused menu (`EdgeMenuBody`), and the `edgeMenu` bind action toggles one by id.
- **State.** `EdgeMenuManager` holds which menus are open and pinned (a `PersistentProperties`, so a reload doesn't reflow windows) and the `edgeMenu` IPC target. The menus follow it and report back when they close by themselves. They work over the overlay: their windows and hover strips are its grab partners (`EdgeMenuSync`'s `window` and `triggerWindow`), a floating one draws over it and, while it's open on its screen, takes no focus grab of its own (`grabEnabled`), which would clear the overlay's and close it. An open floating menu claims its edge (ShellManager's edge claims), putting away an OSD or dock there. A bar `Button` with `action: "edgeMenu"` and `menu: <id>` toggles one, passing itself as the anchor, so a floating menu stays open while the button is hovered.
- **Hosts** (`surfaces/edgemenu/`). `shell/EdgeMenus` builds one `EdgeMenu` per enabled entry (keyed by id), which `LazyLoader`s the host for its mode. Both put `EdgeMenuBody` inside: a `ModuleGrid` on an `OverlayGrid` with `fixedUnit` the card size of its screen's overlay (`EdgeMenuManager.cardUnitOf`: `OverlayManager.areas`, else `OverlayConfig.cardUnitFor` the screen, so Overlay size scales menus too; times the menu's `moduleScale`%), stretched along the edge to `maxLength` when `length` is `edge` (`fillsEdge`), else scrolling along it past that; with `pinButton` it draws a pin in the corner away from the edge (`EdgeMenuManager.togglePinned`). Along the edge the modules sit on a lattice fixed to the screen (`GridPlacement.menuAlong`, at the host's `unit`): as many whole cells as fit between the host's `startPad`/`endPad`, centred there and moved `gridOffset` px; the modules start `offset` cells from centred on it (negative: towards the start), kept on it (so an offset past it is flush with that end's cell). A menu longer than its lattice starts at `startPad` and scrolls. Neither is a form field (`x-settings: false`, which `SchemaLayout.objectGroups` leaves out): the layouts editor sets them (Editing, below). Each host reports where its modules can sit (`EdgeMenuSync.frame` → `EdgeMenuManager.setFrame(id, { screen, startPad, endPad, across, before, after, reserves })`, cleared on destruction or an id change) for the editor, which also draws the other menus from it (`screenRectsOf`); `frameOf(menu)` falls back to the menu's padding for one without a host (disabled). `EdgeMenu` keeps the last live entry, so the hosts read its (schema-defaulted) fields directly. What both hosts share is `EdgeMenuSync`: following `EdgeMenuManager` (and telling it when the menu closes by itself), held/revealing state, `autoDismiss`, the trigger length, grab-partner registration and the reveal's cursor warp (`warpRequested`, each host warping into its own box).
  - `floating`: `FloatingEdgeMenu`, an `EdgePopout` (`contentPadding`, `edgeOffset`, `fillColor`/`strokeColor`, defaulting to what the OSD uses). It's `detached` (a plain box) when held (`menu.detached`: `gap` from the frame lines on its edge and at both ends, Popouts: held off an edge, through `EdgePopout.held`/`gap`) or its edge has a transparent bar, else attached to the border or solid bar, or meeting a pill or floating bar as a bar popout does (`EdgePopout.followsBar`, Popouts below). Its window sits inside what's reserved on each screen edge (`EdgeMenuManager.reservedOn(screen, location)`: `BarManager.reservedOn` (the border's `screenMargin`, a bar's `Bar.reservedZone`, less the `-borderWidth` margin Hyprland counts in for a bar inside the border) plus integrated menus' zones; not docks, which it reaches past), so its edge coordinates start at `alongOrigin` (what the perpendicular edge at its start reserves) and its ends keep `startPad`/`endPad` from the screen's. It places its box with `position: 0` and a `positionOffset` from the modules' start (from the box's natural length: the end joins depend on its position), and across its edge past `reservedOn(edge)`. Both hosts centre their hover strip on the modules from config (`EdgeTrigger.centre`, through `EdgePopout.triggerCentre` for this one), since the body only loads while open.
  - `integrated`: `IntegratedEdgeMenu`, a `PopoutWrapperBase` with a Top-layer `axiom-edge-menu` window along the whole edge. Its layer rule's `order = 7` (above the bars' 5) arranges it first, so it sits outermost and the border, bars and every Normal-exclusion surface move inwards. The zone is set once while it's mapped (windows retile in one step) and the strip slides in. With `frame`, a rounded stroked box runs the strip's whole length, its stroke's inner edge `screenMargin` in from the strip's edges (as the border's is, so the two line up), holding the modules `padding` in from its stroke. It reports its zone (`EdgeMenuManager.setZone`), which `BarPopouts.borderInset` takes off the perpendicular bars' length.
- **Editing** happens on the Layouts page (above). The draft (`ConfigDraft { path: ["EdgeMenus"] }`, `layout`: the selected menu's `GridEditor` with host `edgeMenu`) lives in `EdgeMenuManager`, and shows live on the running menus through `previews.EdgeMenus` while dirty, as the bar editor's does. The menu's fields come in `x-group`s (General, Opening, Placement, Style, Closing, Advanced: the read-only `id`); the Opening group leads with `MenuOpening`: "Show on screen" (sets `previewing` to the selected menu, following the selection and id renames, and opens it; `isHeld(id)`, pinned or previewing, makes a menu ignore `closeOnLeave` and outside clicks; the page's `onDestruction` stops it), what else opens the menu (`EdgeMenuManager.references(id)`: bar Buttons in the bar editor's draft or saved bars, binds in the keybind editor's draft or `HyprlandConfig.binds`), and buttons that add a bar Button (`addBarButton` → `BarManager.addWidgetTo`, into the bar editor's draft, then the bar editor on that bar) or a keybind (`addKeybind` → `KeybindManager.addAndRecord`, then the Keybinds page's editor recording its key), drawn by `OpenerButtons` (shared with the page's Opening group). A new menu (`addMenu`) opens on hover and starts previewing. Beside "Show on screen", "Show other menus" draws the others on the grid. The canvas's lattice is the menu's (its cells past the lattice along the edge tinted, `latticeSpan`), so it never moves when modules do, and edits never move modules on the screen: `GridEditor.shifted` hands `_keepPlace` the shift `normalize` took off and the bounds before the edit, and the menu's `offset` follows so its modules keep their cells (a module dropped left of the others lands where it was dropped). The arrows under the canvas title (`EditTarget`'s nudge fields, from `MenuTarget`: left/right on a top or bottom edge, up/down on a side) step `offset` a cell at a time within `GridPlacement.offsetRange` (`nudgeSelected(step)`; `centreSelected()` recentres), saying where it is (Centred, n cells from the centre, at an end), and the Grid stepper beside them moves the lattice up to half a cell either way (`setGridOffset`, `gridOffsetLimit`). One taking its whole edge has no place along it, and no arrows.
- **Pin.** `pinButton` puts a pin on the menu, and QuickActions has a `pin` action; both toggle `EdgeMenuManager.pinned[id]`. While pinned, a menu ignores `closeOnLeave` and outside clicks. Modules learn where they're shown from `host` (`{ kind: "overlay" }` or `{ kind: "edgeMenu", id, bare }`, on `Card`/`Panel`, passed down `ModuleGrid` → `OverlaySlot`). `x-hosts` on a module definition limits where it may go: `OverlayConfig.modulesFor(host)` feeds the library, and `GridEditor.problemsFor` flags a misplaced module.

## Editors (settings, bar, layouts, keybinds, monitors)

They share one shape; a new editor follows it:
- **Draft.** The manager owns a `ConfigDraft` of its config path: mutate `draft.local` in place, then `changed()` (re-clones next tick so bindings see it; `isDirty` by JSON compare). Structural editors show unsaved edits live through `ConfigManager.setPreview`. Save merges onto the latest config (`commit`, which may refuse: the draft stays dirty); Reset reloads. `ensureLoaded()` on page open reloads only a clean draft.
- **Selection** lives in the manager (`selectedBarIndex`, `selectedViewIndex`, `selectedMenuIndex`, `selectedProfile`, …) and changes through `select*()`, which clears or fixes what hangs off it. Add/remove/move functions keep it on the right entry.
- **Page.** A `BaseView` (sizes: `pageHeight`, `cardPageWidth`, `sideWidth`, and `editorWidth` for the main area beside it) with a `TitledCard` on the left: a list of `ListEntryRow`s (icon, name, badges, unsaved dot from `…Changed(index)`, `RowAction`s) and an `AddEntryButton`, then the selected entry's fields (`FieldGroup`s of `SchemaPropertiesForm`, grouped by `x-group`), then "Can't save yet" (`IssueList`) when `problems` block Save. Save/Reset are page-wide, so they sit top-right like Settings: on the right-hand top card (`SectionsBoard`'s header, `GridCanvas`'s through `LayoutsEditorLayout`), with the left panel's `showActions: false`.
- **Unsaved reminders** (`EditsManager`): drafts survive leaving a page or closing the overlay (bar and edge menu edits stay live through previews), so nothing blocks closing. `EditsManager.unsaved` lists the pages (view types) with dirty drafts; the navigator dots their tabs, and while another page has some it shows Save all / Discard all after its arrows (`saveAll()`/`discardAll()`, skipping `separate` pages: Monitors, which applies with a keep/revert step). A new editor adds its manager to both lists.
- **Text fields** bound to draft values follow the push pattern (CLAUDE.md pitfalls): set the text on selection change, and on draft change unless focused; write per keystroke while focused (`LayoutsPanel`, `Monitors`).
- **Drag.** A `reusable/DragLayer` subclass covers the page and draws the ghost: `BarDragLayer` (targets: the `SectionLane`s, and a `TrashTarget` away from the bar's edge that takes a `move` and removes the widget; payloads `{ kind: "move" | "add", zone, index, type, compact }`) and `GridDragLayer` (see Layouts editor). Draggables are `DragArea`s (`dragLayer`, `payload`) or `DragChip`s.
- **Inspector.** `InspectorHeader` + a `KeyedLoader` keyed on the selection building an `OptionsGroup` (widget/module `properties`), or a library of `DragChip`s in a `TileFlow` when nothing is selected.

**Bar editor** (`views/BarEditor.qml`, pieces in `views/barEditor/`): `BarsPanel` on the left (the bars, with duplicate/remove, then the selected bar's field groups; the Style group's header copies the bar's look, `BarManager.styleKeys` (its Size and Style settings), and pastes it onto one bar or all, the copied style following its bar by index). On the right, `BarDragLayer` holds `SectionsBoard` along the side of the page the selected bar is on (a strip across the top or bottom for a horizontal bar, a column at the left or right for a vertical one) and `WidgetInspector` beside it. The board's five `SectionLane`s are laid out the way the bar lays out its sections (`BarLayout.layoutSections` over each lane's `naturalLength`/`minLength`), each a row or column of `WidgetChip`s that scrolls when it can't show them all (a scroll bar, and the wheel through the lane's `WheelHandler`, sideways on a horizontal lane: the Flickable itself isn't interactive, so chips keep their drags); chips are dragged within and between lanes or dropped in from the library. The inspector shows the widget's options (and, for a Button opening an edge menu or page, `OverlayManager.openedBy`/`editOpenedBy` taking it to the layouts editor), plus its Sizing: the `LayoutOverrideField`s from `Bar.widgetLayoutSchema`, explained from, and starting at, what the bar uses now. With nothing selected it shows the widget library, whose click adds to `BarManager.lastZone` (the section last selected or added to). Edits show live on the running bars.
- **Live reports.** While a BarEditor page is visible (`BarManager.watch(page)`/`unwatch`, a `ConsumerRegistry`: `editing`), the running bars outline the selected widget (`BarManager.isSelectedWidget(source, zone, index)` → `BarWidgetHost.highlighted`), and each `BarContainer` reports `editorReport` to `BarManager.live` (`setLive(id, report)`, `clearLive(id, screen)` on destruction): its `source` (config id), `screen`, `hidden` (per section, the config indices `WidgetGroup.crowdedOut` hides for want of room) and `selected` (the highlighted host's `measure`: `policy`, `size`, `preferred`, `minimum`, `priority`). `BarManager.liveReports()` gives the selected bar's, one per screen: the board's fit line ("Fits DP-1", or what has no room where), the chips' crowded badge, and the inspector's sizing text. `BarContainer.widgetModel` keeps each widget's `configIndex`, since widgets hidden in config aren't on the bar.

## Popouts (bar + screen edge)

Shared pieces live in `components/hosts/popout/`: `PopoutWrapperBase` (open/close/queue state, `isOpen`/`show(data)`/`hide()`, hover-loss dismiss timer; a wrapper may switch an open popout to another payload in place instead of closing it first, through its `canSwitchTo(anchor, data)` and `prepareSwitch(done)` hooks), `FloatingPopout` (a box floating in the free area at a fraction across and down inside per-side margins, `xAlign`/`yAlign` saying which part of the box sits there, fading in; the detached launcher and window switcher), `SlideAnimation`, and `AttachedSurface` (the content box + connector + `CornerPiece` fillets that make a popout look like it grows out of a bar or the screen border; `edge` is a `Bar.Location`. Attached, the box starts on the attach edge with the fillets curving outside its walls (`boxStart`, pushed back only as far as a box too shallow for its fillet and far corner needs); detached, half a connector gap past its lead; a bar's pills keep that half gap, as their depth is sized by it). Bar popouts (`BarPopouts.qml`) share one wrapper per bar. **Switching in place.** A bar popout opened from a widget under the open box, or within a connector gap of it along the bar (`BarPopouts.canSwitchTo`), doesn't close first: the old content is grabbed as a still (`hosts/popout/SwitchStill`, `grabToImage`, held where it was along the bar), the new payload loads under it (every payload reloads, `onCurrentDataChanged`, so the same type for another widget is rebuilt), and while the new content isn't ready the window stays up and the box holds its size and place (`SwitchStill.holding`/`held`, from its `snapshot` hook). Once it is, the box glides and resizes to it (the shown-box Behaviors stay on: given the host's `occupied`, `SwitchStill` also keeps `showing`, open with something to show, and `settled`, a tick after it first shows, which gates them, and ends itself as the host closes), the still fading out as the content fades in (`contentOpacity`, animFast). Tray submenus do the same (`TraySubmenuWrapper`): another submenu of the same menu, a sibling item's or one drilled into, glides level with its item and resizes, in a popup spanning everywhere a submenu of that menu can sit (and the largest since it opened), masked to the surface. Along the parent's side a submenu is placed as a bar popout is along a pill (`EdgeAttach.place`, pill mode, the parent's box at rest, `BarPopouts.attachBox`, as the pill): its first item stays level with the hovered one, moved only to stay within reach or nudged. A side with no room for its fillet runs flush to a free end of the parent's side (`sideFreeTop`/`sideFreeBottom`: its far edge's ends, and on a detached box its bar side too), the parent squaring its corner there (a detached box's near corner too, `AttachedSurface.startNearRadius`/`endNearRadius`). At the bar side of a solid bar's, a pill's, an island's or a merged box it joins the stroke the parent grows from instead (`sideJoinTop`/`sideJoinBottom` at `sideJoinLine`; `AttachedSurface.joinStart`/`joinEnd`, straight on a bare screen edge), as a popout joins the perpendicular border, its window keeping no shadow room past that line. A submenu longer than the side stretches the parent's box past its far end. The submenu hands all this back as `TraySubmenuWrapper.parentStretch` (`{ top, bottom, squareTop, squareBottom, joinReach }`), which the tray content exposes as `sideStretch` and `BarPopouts` draws (`shownStretchTop`/`Bottom`, the corner flags, the window keeping room for it as for its box); as a bar popout meets a pill: a joined submenu keeps its outer fillet only where what it joins already reaches past it and the corner beyond (`BarPopouts.sideJoinFrom`/`sideJoinTo`: the pill or island as the box stretches it, else the bar's ends, `TraySubmenuWrapper.joinFillets`); otherwise its wall runs straight up (`straightJoins`) into the pill or island, which `BarPopouts.pillStretch` stretches to that wall (`joinReach`, within the ends it may reach) and squares there. While one is joined, the parent's own wall on that side, if it ran flush into the pill's end, stops at the attach edge rather than running on through the backfill (`AttachedSurface.flushStartThrough`/`flushEndThrough`), since the stroke it continued now carries on under the submenu. On a pill or island the submenu also covers the parent's backfill row beside it (`AttachedSurface.joinBackfill`, `BarPopouts.sideJoinBackfill`: plain fill past its joined end, outside its shadowed outline, its window keeping that row), where the parent's glow showed as a dash. A submenu that closes with the pointer off the tray menu and its icon (it left, or an entry was picked) closes the menu at once (`content/SystemTray`), a cascade rather than the menu's own dismiss delay after it. `PopoutWrapperBase`'s parked-cursor check (a popup mapping over its anchor steals hover from a still pointer) arms only when the anchor loses hover, so no other hover loss (the content's, a submenu closing, `keepAlive`) holds a popout open under a pointer that's merely still. Asked again meanwhile, the latest payload wins; a switch also calls off a close under way. Farther away, the popout closes and reopens as before. Screen-edge popouts (`EdgePopout.qml`, used by `OSD.qml`, floating edge menus and the attached launcher) are one independent instance per screen (`Variants` over `Quickshell.screens`). Each is an Overlay-layer `PanelWindow` with Normal exclusion and a `-borderWidth` margin, so it lands on the inner stroke of whatever reserves that edge: the border (`surfaces/border/`) or a bar.

**One placement for everything that pops out of an edge.** `components/methods/EdgeAttach` (pure, `tests/tst_EdgeAttach.qml`) decides where a box goes along its edge and how it meets what's there, for bar popouts, every `EdgePopout` (OSDs, floating edge menus, the attached launcher) and docks alike: `joins` (an end joins a joinable perpendicular stroke when the box would be pushed back from it or come within a connector gap of it), `place` (the mode: `plain`, out of a `pill` or an `island` (the same rules: a pill bar's pills are met as islands are, see Floating bars), or `merged` (grown from the outer edge of a pill bar showing no pills); the box's `start`/`end`, the content's `contentStart`/`contentOffset`, joined/flush ends, fillet margins, the surface's span and the pill/island `stretch`). **The content always sits where it wants to** (its anchor, its `position`), moved only to stay on the screen or island: the box grows around it to reach a joined stroke, an island's end, or a pill stroke it would just miss, instead of the content moving to make the box fit. Out of a pill or island, a side ending just short of the pill's end (too close for a fillet, so the box would run flush to it with empty space) keeps its fillet instead: with `pillGrows` (bar popouts and `EdgePlacement`: edge popouts and docks) the pill or island grows past its end far enough to carry it (`stretch`), and the box stays its content's size. Only where it can't grow (a pill joining the perpendicular edge, which the box then joins too; past where islands may reach, `islandFrom`/`islandTo`) does the side run flush as before. Tray submenus, whose "pill" is the parent's box, use `nudge` instead: the content moves the shorter way that grows nothing, up to that end or back far enough for the fillet; either is less than a fillet's room. Hosts place their content at `contentOffset` rather than centring or stretching it. A surface standing on a pill or island hands its `stretch` to the bar through `hosts/popout/PillStretch` (owner-keyed: `BarContainer.setStretch(owner, stretch)`, any number at once, combined per pill by `BarLayout.stretchOf`); the bar animates how far each pill reaches past its own ends (`BarContainer` `reaches`, `_shownStretches`), so pills and islands grow out and draw back while their position follows the layout at once. **The pill grows first.** A surface slides out only once its pill reaches as far as its stretch asks (`PillStretch.ready`, from `BarContainer.carries(stretch)` as drawn; the host sets `open`, and it's judged a turn of the event loop later, since a host's stretch comes in with its content), mirroring a close, where the box slides away before the stretch is taken off and the pill draws back. Once ready it holds while the surface stays open, so a switch in place or a resize never pulls the box back. Bar popouts (`surface.active`), edge popouts (`EdgePlacement.stretchReady`) and docks (`shown`) all wait on it; with no stretch there's no wait. An `EdgePopout` and a dock both reach it through `hosts/popout/EdgePlacement` (what's on the edge, `place`, `detached`, `straight`, `barAttach`, `joinable(name)`, and its `PillStretch`): it follows a non-solid bar on its edge unless held (`followsBar`), pills and islands as a bar popout meets them, a transparent bar with a detached box past it (`Bar.detachedPush`). Content is mapped only once its payload is in (`BarPopouts._payloadApplied`: a Loader reports Ready before `onLoaded`) and its positioners laid out (`_layOut`: Row/Column/Grid lay out on polish, which an unmapped window never runs), so it never maps small and grows a frame later (on a bottom or right bar the popup would also have to move, which the compositor didn't always follow).

**Shadow and glow.** Every surface with an exposed border casts the shell's shadow or glow (the `BarStyle` section's `shadow`/`shadowColor`/`shadowSize`, as the bars and border do) through `hosts/popout/SurfaceShadow` (a `MultiEffect`, kept only outside the surface's shape (`cut`, of pixels it covers fully: under its anti-aliased edge the shadow stays, or a pixel's gap shows) so none shows through a translucent fill; while the blur window backs a surface it casts the shadow instead, see Translucency and blur; drawn under its target by `hosts/popout/OutsideShadow`, which captures the target with room for the shadow and leaves out `holes`: where surfaces joined to it sit, the bar's open popouts (its stretches) and, for the border's own shadow window, `ShellManager.borderOpenings`; never as a `layer.effect` on, or a `MultiEffect` given directly, a visible surface's own layer, whose padding would redraw that surface in the padded rect: a free-standing (`detached`) surface's shadow falls away from the edge it grows out of; one joined to the border or a bar casts it evenly, as the border does (`falls` false), since a shadow shifted along a stroke it joins covers that stroke; a glow always spreads evenly): `AttachedSurface.castShadow` (bar popouts, tray submenus, edge popouts: OSDs, floating edge menus, the attached launcher; docks), the dock's detached box, and a copy of `FloatingPopout`'s box behind it (the floating launcher, the window switcher). A bar's own pills don't: their bar's layer casts it. Only the outline casts it, not the content. `SlideAnimation.overflow` lets it draw past the surface on every side but the one it slides from (that side's clip still hides the surface until it's out, and keeps the glow off the bar it grows from), and each window keeps `BarStyle.shadowReach` of room for it (`BarPopouts.spareAcross`, `EdgePopout`'s depth, the dock's depth, the tray submenu's `shadowRoom`).

**Bars and the screen border share an edge by layer-shell ordering.** `Appearance.screenBorder` turns the border (`shell/ScreenBorder`: `surfaces/border/RoundedBorders`, four `BorderPanel` strips and four `CornerPiece` corners, layer namespace `axiom-border`) off.
- **Solid bar** (`Bar.background: "solid"`): Top layer, at the screen edge. The border's strip on that edge is arranged after it and overlaps its inner part, so the strip's stroke is the bar's inner edge. Hyprland reads a layer rule's `order` only as a surface maps, so the bars, border, docks and edge menus are built once `HyprlandManager.layerRulesReady` (the rules evaluated at startup, kept across QML reloads): in the detached mode, where hyprland.lua doesn't hold the rules, a border mapped first would land outside the bar, its corners on the bar's outer side. For the same reason `shell/Bar` keys each bar's window on whether it sits inside the border as well as its id: switching to or from solid changes its namespace, so the window is remade and maps under the new rule.
- **Bar inside the border** (`barConfig.insideBorder`: any but solid, with the border on): Top layer like the border, in the `axiom-bar-floating` namespace, whose layer rule (`order = -1`, below the border's 0) has Hyprland arrange it after the border and draw it over it. It sits just inside the border with a `-borderWidth` margin, so its outer edge lies on the border's stroke. A fullscreen window covers it, as it does everything on the Top layer, so it never hides. Hyprland counts that margin into the reserved space, so it reserves `extent`. `RoundedBorders.cornerMargin` pulls the corner pieces back out to the border's corners on such a bar's edge.
- **Pills** (`BarContainer.pillRects`): one per section, merged when they're at most `pillMerge` apart. Each is an `AttachedSurface` growing out of the bar's outer edge, covering the border stroke (`barConfig.overlap`); widgets sit `overlap + pillPad` in from that edge. A pill at an end of the bar joins the perpendicular edge (`joinStart`/`joinEnd`: flush on its stroke, whose far corner meets it with a fillet). The bar window is `borderRadius` thicker than `extent` in pill mode for that fillet, masked to the bar itself. Floating bars take `-borderWidth` margins on both ends too, so bar-window 0 along the bar is the perpendicular stroke's outer edge.
- **Floating bars** (`background: "floating" | "floatingPills"`, `barConfig.island`/`islandPills`): laid out like tiled windows: islands held their float gap in from the border's stroke (or the bare screen edge), across the bar and from both ends (`islandStart`; `floatGap` Automatic (-1) is Hyprland's gaps_out on the bar's edge, as windows keep, so the islands' ends line up with the windows'), each a rounded box with a stroke all round holding the widgets and their `padding`. `BarContainer.pillRects` holds them shaped like pills (`BarLayout.islandRects`: one from limit to limit, or one per group merged within `pillMerge`), so the popout code reads them as pills, and draws them from `pillShapes` (`BarLayout.stretchIslands`). Nothing joins a floating bar (`joinable` is a solid bar's alone). A popout, edge popout or dock on an island (the one under its centre, else the nearest) grows out of its inner stroke (`attachAt`), never merging (`EdgeAttach.place`, island mode): a side whose fillet lands on the island (or on a neighbour the island stretches to within `pillMerge` of, the two then drawing as one while it's open) keeps it; any other reaches to the island's end and runs flush into it, the island stretched to the box where the box goes past it. A stretch changing while a surface is open is drawn by the bar but wasn't shown until the bar committed again, so `BarContainer` paints a few frames of its own after one changes (`_repaint`). A flush side runs into the island in one straight line (`AttachedSurface.flushStart`/`flushEnd`: a wall continuing the island's end, its backfill kept off that stroke), the island squaring that inner corner (`squareStart`/`squareEnd`, animated). Floating bars reserve up to their islands, so windows keep gaps_out from them as from a screen edge (gaps_in is only between windows; `Bar.reserveTrim` is 0 for them), whatever their float gap.
- **Bar popouts** join an end the same way as edge popouts (`EdgeAttach.joins`). On a pill bar, every surface (edge popouts and docks alike) grows out of a pill's far stroke exactly as out of an island: the pill under it (else the nearest) stretches, animated, to carry it, joining neighbours within `pillMerge`, and squares its far corner where the box runs flush into its end (`AttachedSurface.startCornerRadius`/`endCornerRadius`, animated); at a pill joining the perpendicular edge the box joins that edge too. `BarContainer.pillShapes` is the pills (or islands) as drawn, stretched and merged. Only a pill bar showing no pills leaves a box to grow from its outer edge (`BarPopouts.mergeWithPill`, `EdgePlacement.merged`), as deep as the pills would be. A flush wall runs on through the surface's backfill, covering the end of the stroke it continues (the backfill leaves that open, and the glow showed through it as a seam). On a transparent bar popouts are `detached`: plain rounded boxes on the bar's own edge, which never join an end (they're clamped clear of it). They're a layer surface of their own (`underWindow`, not a popup, which would always draw over its bar) in the `axiom-popout-under` namespace, whose layer rule (`order = 6`) stacks it under the bars and border; it starts at the bar's outer edge and the box (`AttachedSurface.detachedOffset`) slides out from beneath the bar. That rule also stacks it under the overlay, so while the overlay is open on its screen (`ShellManager.surfaceOpenOn("overlay", screen)`) the box shows from the bar's popup instead, which draws over it, without the slide. Detached floating edge menus do the same (`FloatingEdgeMenu._overOverlay`, followed only while the menu is closed, since it changes the window's namespace) (`EdgePopout.slideDistance`/`underLayer`).
- **Held off an edge** (floating edge menus, docks and OSDs with `detached`): an island, `gap` in from the frame line (`BarManager.frameLine`, plus integrated menus' zones in `EdgeMenuManager.frameLineOn`: the inner side of the border's stroke, a solid bar's inner stroke, a floating bar's islands, a pill bar's far side, a transparent bar's inner edge) on its own edge and on both perpendicular edges. `BarManager.detachedGaps(screen, location, gap)` gives the three gaps: `gap` on each, or Auto (-1): a floating bar's `floatGap` on all three when one shares the edge (lining up with its islands across and at both ends), else, per side, how far past the frame line windows start (`BarManager.reservedOn` + gaps_out), so it lines up with them. Each surface places itself from where its window starts (`EdgeMenuManager.reservedOn`). An `EdgePopout` does it itself given `held` and `gap` (the OSD's and floating edge menus'): `gaps`, `startInset`/`endInset` (the room a box keeps at an unjoined end: held, its gaps; else its fillet's), `heldAttach` (where its window's attach edge goes, `attachAt` by default, from `attachBase`), `detached`, `edgeOffset`, and `slideDistance` (from under a non-solid bar's outer edge, `barPanel`/`barOuter`, or the border; none while the overlay is open on its screen, `_overOverlay`, so it draws over it). `maxBoxLength` and the clamp in `boxStart` use the insets. The dock, not an `EdgePopout`, does the same from `BarManager.detachedGaps` itself; held and reserving its space, its exclusive zone ends at its box, so windows keep the gaps_out Hyprland adds past any zone, as from a screen edge. A new surface held off an edge uses these rather than its own distances.
- **Transparent bars** reserve `Hyprland gaps_out` less (`HyprlandManager.gapsOut`), so windows start at the bar's invisible inner edge and the widgets' gap to them matches their gap to the screen edge. Bar popouts use `adjustment: PopupAdjustment.None`: their placement is computed, and Hyprland otherwise nudges one flush on the screen edge a few pixels inwards.
- **Border off**: a solid bar draws its own inner stroke (`barConfig.innerStroke`, on its innermost `borderWidth` pixels, where its popouts attach). Surfaces on a bare screen edge (`BarManager.screenEdgeOpen(screen, location)`: no border, no bar there) run straight off it, with no fillets and no `-borderWidth` margin: `AttachedSurface.straight` (attach edge) / `straightJoins` (joined ends) for pills, merged popouts and EdgePopout, and the overlay panel pushes its corners and stroke past the window on those sides.

## Translucency and blur (`Appearance.surface`)

- **One setting.** Look & Feel → Translucency: `opacity` (60–100%; 100 is solid and blurs nothing), `blur`, `throughWindows`, `blurBackdrops`, `pauseFullscreen` (`x-scope: machine`). The strength isn't axiom's: Hyprland has one blur, for windows and layers alike, set by the window look's blur part (Hyprland → Window look) or the user's own config; the card's intro (`TranslucencyStatus`) shows the one in effect, and with Hyprland's blur off (nothing blurs then) offers to set it. Readers: `Appearance.surfaceAlpha`, `translucent`, `blur`, `blurThroughWindows`, `blurBackdrops`, `blurThreshold` (0.5), `shadowAlphaMax`.
- **Fills.** Every surface fill goes through `Appearance.fill(color)` at the shared pieces' draw sites (`AttachedSurface`, `FloatingPopout`, `CornerPiece`, `BorderPanel`, the bar's background and islands, the overlay's box and navigator, edge menus, docks, power menu, overview, polkit and monitor prompts, `StyledContainer`, `Card`/`Panel`, buttons, inputs, `ActionTile`, `DropdownSurface`), outer and nested alike, so nested fills stack (a card on a 60% panel reads about 84%). Accent colors and hover tints are left alone.
- **Hyprland.** `HyprLua.blurLua` (HyprlandConfigManager's `_blurLua`, `M.blur()` in the module): named layer rules always written, `enabled` or not, since a rule is taken back by redefining it (no reload): `axiom-blur` on the namespaces that blur themselves (`HyprLua.blurSurfaces`: the blur window, the overlay, floating launcher and switcher, notifications, …) with `blur_popups` and `ignore_alpha` at the threshold (the big transparent windows need it; shadows are capped under it while blurring, `Bar.shadowColor`), `xray` unless `throughWindows`; `axiom-blur-popups` on the chrome's own namespaces (`HyprLua.blurChrome`), for their popups alone (tooltips, the dock's menu: Hyprland blurs a layer's popups whether or not the layer blurs, never xray, and with its `ignore_alpha`, so a bar popout, a popup drawn transparent over the blur window, blurs only under its content); `axiom-blur-backdrops` (`axiom-backdrop`, and polkit, whose window holds its dim) at any alpha; `axiom-blur-no-anim` (`no_anim` on `HyprLua.blurBacked`, the windows the blur window draws for, while it does): they slide themselves, and Hyprland fading or popping one in (its `layers`/`fade` animations, read as it maps) would leave its stroke and content behind the fill, blur and shadow drawn for it, which it doesn't animate. That's all it writes: the strength is Hyprland's own blur (see the window look). The module file holds the setting as saved (`_surfacesBlur(true)`); at runtime it's `BlurManager.active`, evaluated over the file after every reload.
- **The blur window.** A surface blurring on its own blurs what's drawn under it, other surfaces' fills included, up to blur size × 2^passes past its edge, so joined surfaces never matched. Instead the chrome (the border's frame, bars, bar popouts and tray submenus, edge popouts: OSDs, floating edge menus, the attached launcher; integrated edge menus' strips, docks) registers its shapes (`hosts/popout/BlurShape`: an `AttachedSurface`, a `Rectangle` or the border's `frame`, with its top-left on screen and its fill color) with `BlurManager`, and `shell/BlurBacking` (one click-through `axiom-blur-backing` window per screen, layer order 9: under the chrome, over the backdrop) draws a copy of each (`AttachedSurfaceCopy`, an `AttachedSurface` `mirror`, its geometry bound to the source's, sliding with it; a strip that slides reads `SlideAnimation.slideX`/`slideY`), all opaque and then at the surface opacity at once, so overlaps never stack. Backed surfaces' shadows are cast there too, from the same copies: each `BlurShape` names its `shadow` (a look: BarStyle's, or its bar's; an `AttachedSurface`'s follows `castShadow`, `edge` and `detached`), the copies are grouped by look and the way it falls (`BlurBacking.shadowKey`), and each group casts one `SurfaceShadow` cut by every shape on the screen, so a shadow runs unbroken round joined surfaces and none falls on a surface joined to the one casting it (no holes needed). Kept under the blur threshold, they aren't blurred. Meanwhile the surfaces' own shadows (`OutsideShadow`, inactive while `backed`) and the border's shadow window stand down. Unbacked (paused, solid, or a window not yet placed) each surface casts its own again, from a black copy of its shape kept off screen (`OutsideShadow.hideTarget`): `AttachedSurface`'s, the bar's (each pill, island and solid fill puts its copy in `shadowShape`, pills an `AttachedSurfaceCopy`; its holes are the bar's `openings`, where surfaces cover its far stroke, stretched or not), the dock's detached box. The copies are a keyed `ListModel` (`KeyedModel`, by `BlurShape.uid` through `BlurManager.shapeOf`), so a shape coming or going adds or removes only its own, and any copy moving, resizing or sliding nudges the window (`FrameNudge`). It's the only one of them Hyprland blurs, in one pass; the overlay, floating launcher and switcher, notifications and the other free-standing surfaces still blur themselves. The chrome draws its outer fill transparent (`AttachedSurface.backed`, `BarContainer.backed`, `RoundedBorders.backed`). Where a surface's fill used to hide a stroke it's joined over, the stroke is left open: a pill's or island's far stroke under a popout (`PillStretch.opening` → `BarContainer.setOpening`), a popout's side under a tray submenu (`BarPopouts.submenuHole`, `AttachedSurface.strokeHoles`), drawn through `reusable/HoledItem`; a dock joined to the border opens it as edge popouts do. An opening spans only what's drawn over it (`AttachedSurface.coverStart`/`coverLength`): the box while it slides, its fillets too once it's out, since until then they're behind the edge it slides from and the opened stroke showed as a dark gap at each corner. A tray submenu's popup takes no compositor adjustment (its window reaches past the parent's, and a nudge left its blur and the parent's opening behind). Layer windows don't know where they are, so `hosts/popout/LayerOrigin` asks `BlurManager.layerOrigin`, read from `hyprctl layers` (only while surfaces are translucent) on layer events and whenever the window or what's reserved around it changes, and remembered for windows mapped only while open. Every window asking spans its edge: it's matched by namespace, its length along the edge and the side of the screen it's on, and a window grown or shrunk across its edge (an edge popout's content) is placed from the side it's anchored to until Hyprland reports it again. Until it's known a surface fills itself. A bar popout's and submenu's place follows from their bar's.
- **Paused over fullscreen** (`pauseFullscreen`, on by default): while any screen shows a fullscreen window, `BlurManager.active` is false: the blur window goes, the chrome fills itself (still translucent), and the rules are taken back at runtime, as is Hyprland's blur where the window look kept it on for the surfaces alone (the module file keeps the saved setting).
- **Stacking.** The chrome's fills all live in the one blur window (Top, order 9), under every chrome window. A chrome surface that stood over another one in a higher layer (the attached launcher, an Overlay-layer edge popout, over a dock) no longer hides it with its fill: what's in between shows through. Such a surface claims its edge instead (`ShellManager.setEdgeClaim`, the attached launcher's rank `launcher`), and what's under it gives way. Ranks, lowest first: `dock`, `osd`, `popout` (a bar's popouts, on its edge), `launcher`, `menu` (a floating edge menu). A bar popout outranked on its edge closes and won't open (`PopoutWrapperBase.blocked`); surfaces giving way do it a turn later (`Qt.callLater`), since giving way drops their own claim, which their `outranked` reads.
- **Lock screen and greeter.** No compositor blur reaches a session-lock surface, so `ScreenLayoutView` frosts its own background under the modules while the shell blurs (`frosted`: the backdrop blurred at about Hyprland's strength, `hyprBlur`, which the lock surface reads from `HyprlandManager.blur` and the greeter leaves at Hyprland's defaults, masked by the modules at the blur threshold), unless the wallpaper is blurred already.
- **No reload per step.** The window look and the blur are HyprlandConfigManager's `_liveInputs`: in every mode a change is only evaluated at runtime (`_applyLook`, which also runs after every reload); the file catches up on its next write. Turning a look part off rewrites it (an eval can't take a setting back).
- **Joins.** A surface joined to the border's stroke (`EdgePopout`) publishes the stretch it covers (`ShellManager.setBorderOpening`, screen px along the edge: its edge coordinates start at `reservedOn(startSide)`), and `BorderPanel` leaves its stroke and the fill of the stroke's row open there (`Utils.subtractSpans`; a strip's own offset along its edge, `screenOffset`, is read through `LayerOrigin`, until then taken as half what the edges across it reserve). The same goes for strokes a surface is joined over: an opening is cut whenever surfaces are translucent, blurred or not., so a translucent fill doesn't show a line through it.

## Launcher (`surfaces/launcher/`, `LauncherManager`)

`LauncherManager` turns the search text into rows, and the UI only draws them. `LauncherPanel` holds the field, list and hint, with no box of its own. `Launcher.qml` places it as a dock or OSD is placed (`edge`, `position` along it, `detached`), with one difference: detached, it isn't held a gap in px off the edge but a `distance` (0-50%) across the free screen. Detached, it's a `FloatingPopout` whose fraction and align across are both that distance (from the far side on the bottom or right edge), so 0% sits against its margin and 50% is centred; its margins are where a detached dock or OSD with an automatic gap sits (`BarManager.detachedGaps`, per side; `Launcher._marginOn`). `maxContentHeight` keeps it from moving and `growUp` keeps a reversed field in place. As matches come and go, the list's frame (`LauncherPanel.listFrame`) glides to its rows' height (animFast) while the list keeps its target height, clipped meanwhile, and both hosts follow the panel as drawn (`FloatingPopout.animateHeight` off, so its box doesn't chase it). Rows are reused across keystrokes; one whose result changes (`kind` + `title`) dips its content and brings it back (animFast) rather than cross-fading its text, so nothing is created per keystroke. Attached, it's an `EdgePopout` at `position` on its edge; on a side edge its height runs along the edge, so the panel holds its tallest (`LauncherPanel.holdHeight`, the blocks against the field) instead of the window keeping room across (`maxContentDepth`). The settings card's top is `LauncherPlace` (the section's `x-intro`): a `ScreenSpotPicker` with presets (Top, Upper, Center, Bottom, Left, Right) over the place fields. Both have the same API (`show`/`hide`/`isOpen`/`contentItem`/`window`), and only the host in use is created, through `LazyLoader`s. `open(text)` searches first (so instances on other monitors show the same text); the panel created on opening then doesn't search again. `reverse` puts the field at the bottom and lays the list out bottom to top. Every provider returns the same row shape: `{ kind, image, glyph, title, usage, subtitle, hint, complete, run(shift) }`. `run` returns true to close, false to stay open (then the rows are rebuilt, keeping the selection), or a string to search for instead. Tab puts `complete` into the field.
- **Routing.** The first character picks the provider: `/` commands, `=` calculator, `>` run, `?` web, `@` chat, `:` clipboard history (ClipboardManager), `;` emoji (EmojiManager). Anything else searches apps (scored, plus frecency from `usage` `{id: {count, last}}` in `state/launcher.json`) and windows (`HyprlandManager.windowList`). A calculator row is added when the text is plain math, and a web row goes last. Each provider has a `Launcher` config toggle (`LauncherConfig`).
- **The calculator** runs `qalc` through one debounced Process, and the rows are rebuilt when it answers.
- **Commands** live in `services/LauncherCommands.qml`, a plain list of `{ name, aliases, glyph, description(), usage, needsArg, confirm, available(), status(), options(arg), run(arg, value) }`. A new shell feature gets a command by adding an entry that calls its service. `options` supplies argument completions. `confirm` (destructive session actions) asks for a second Enter.
- **`/config`** sets any setting by dotted path (`/config Appearance.font.size 14`), saving it at once through `SettingsManager.commitValue`, and holds `save` / `restore` for snapshots and `example` for the example setups (as on the settings page, `save` suggests only `SavedConfigsManager.active`, saying whether it's `modified`; another is replaced only by typing its name; `restore` lists the active one first; no delete, since a row runs without a confirm). It works inside the options contract: each option's title is the whole argument, so matching and Tab work unchanged. It offers `SettingsManager.settingPaths` only: the settings page's fields, minus `x-applyOnSave` ones and anything under `_blockedPrefixes` (`Bars`, `Overlay.views`), so it can never edit bars or overlays. Values are parsed and checked by `SettingsManager.parseValue`, and choices come from `SettingsManager.optionsFor` (shared with `SchemaField`).
- **IPC** is `appLauncher`: `open` / `close` / `toggle` / `search <text>`.
- **Opening a page.** `ShellManager.openOverlayPage(type)` opens the target overlay on a page, taking a view type or a view's name.

## Lockscreen (`Lockscreen.mode`)

`LockManager.lock()` is the one way to lock; lock buttons call it through `ShellManager.sessionAction("lock")`, and idle daemons through the `lockscreen` IPC target:
- **`quickshell`** (default): the built-in locker, `shell/Lockscreen.qml`. A `WlSessionLock` (Wayland `ext-session-lock-v1`, the protocol hyprlock uses) with one `WlSessionLockSurface` per screen showing `surfaces/lockscreen/LockSurface.qml`. While locked the compositor shows only the lock surfaces and sends them all input; if qs dies the session stays locked (Hyprland's fallback; `misc:allow_session_lock_restore` lets a restarted qs take it back). The locked state lives in a `PersistentProperties`, so a QML reload comes back locked. **Only `AuthManager.authenticationSucceeded` (PAM, `login` stack) unlocks**: there is no IPC unlock, and nothing on the surface may run commands.
- **`hyprlock`**: `ThemeManager.generateHyprlockConfig()` writes `$XDG_STATE_HOME/axiom/hyprlock.conf` from `scripts/templates/hyprlock_template.conf` (theme colors, font, wallpaper, blur, translated greeting) on theme/wallpaper/font/language changes and on switching to this mode; lock runs `hyprlock -c` with it. The user's own `hyprlock.conf` is never touched.
- **`none`**: axiom provides no locker and no IPC target (so an idle daemon pointed at axiom can't loop through `loginctl lock-session`); lock buttons run `Lockscreen.lockCommand`.
- **hypridle**: `Idle.enabled` has axiom run it with its own config (see HypridleManager). A user's own hypridle for the first two modes: `lock_cmd = qs -c axiom ipc call lockscreen lock`, `before_sleep_cmd = loginctl lock-session`; for `none`, no axiom references.

**The built-in lock screen's layout** (`Lockscreen.layout`, `x-settings: false`, edited on the Layouts page's Lock screen row; `LockscreenConfig.layout` is the saved one, which is all a real lock ever shows):
- **Grid.** Overlay modules on a bounded grid of `columns` × `rows` units (16 × 9 by default), absolute places from the top left (a `ScreenLayout`, shared with the greeter). `fineGrid` ("Double grid") splits each unit in two each way (`GridPlacement.screenGrid(layout)` is the grid in the units places use): turning it on or off rescales every place (`GridPlacement.scalePlace`, in `ScreenLayoutEditor.updateLayoutField`; merging rounds each edge, so modules that met still meet), and the `GridEditor`'s `sizeScale` doubles new modules' default sizes. `LockSurface` (on `surfaces/screenlayout/ScreenLayoutView`, the background, dim and fitted grid it shares with `GreeterSurface`) fits it to each screen inside a `cardSpacing` margin: an `OverlayGrid` whose `fixedUnit` is `GridPlacement.latticeUnit` (the axis with less room decides), and a `ModuleGrid` with `extent` the lattice (or what the modules reach, if more) and `stretch` the screen, so the units stretch to fill a screen of another shape and placements keep their relative spot. The editor draws the lattice inside a screen outline (`LockscreenTarget.screenBox`).
- **Hosts.** Modules get `host: { kind: "lockscreen", target, preview, key, bare, passwordBorder, greetingBorder }` (`bare` is `!moduleBorders`: no card box, but unlike a bare edge menu module it keeps its padding, `SlotContext.pad`, since nothing else pads it). `Password` and `Greeting` ignore `bare` there: their boxes follow the layout's own `passwordBorder` / `greetingBorder` (off by default). Only module types whose `x-hosts` list `lockscreen` may go there: display-only ones plus NowPlaying (media transport), VolumeDials and Power (suspend, restart, shut down through `ShellManager.sessionAction`; restart and shut down ask twice), nothing that launches, dispatches, kills, writes files or shows private content. A new module stays off the lock screen unless it's added there deliberately.
- **Password.** The `Password` module (`x-hosts: ["lockscreen"]`, `x-required`) draws `content/parts/PasswordField`, which talks to `AuthManager` and keeps the keyboard focus only when `active`: on the `target` screen of a real lock (`host.target && !host.preview`); anywhere else it's inert. It reports itself to `ShellManager.reportRequiredField(host.key, true)` (each surface's key comes from `ShellManager.newSurfaceKey(kind)`, never reused: keyed by screen name, a monitor that dropped out and came back while turning off had its old surface's teardown clear the new one's report, flickering the fallback in), and a surface whose key has no report shows a `PasswordField` of its own (a tick after loading, near the bottom, over the modules), so a hand-edited or broken layout can never lock anyone out. The field never moves or grows with its messages (`reusable/PasswordEntry`: the message line's room is kept, `reserveMessage`, and the busy bar runs over the field's bottom edge); a slot too short for the line (one row on a doubled grid) drops the card padding, shrinks the field to fit and shows the message as the empty field's placeholder (`inlineMessage`), as the greeter's `Login` does. Focus comes back through `content/parts/FocusKeeper` (also `LoginField`'s), which waits while a clicked control is pressed: a button losing focus mid-press drops its click (the calendar arrows did). `AuthManager` answers PAM's prompts without showing them.
- **Other screens** (`otherScreens`): `layout` shows the modules without `Password`, `background` only the background.
- **Background**: `background` `wallpaper` (`Appearance.wallpaperFor(screen)`, blurred by a `MultiEffect` when `Lockscreen.blurWallpaper`, which hyprlock's config also follows) or `color` (`backgroundColor`), under a black layer at `dim`%.
- **Greeting** (`content/Greeting`, any host): a line of text fitted to its slot (`Text.Fit`), with `{name}`, `{user}` and `{greeting}` (a `SystemClock` at hour precision, only while the text uses it); empty is the translated "Hey {0}". On the real greeter the names are `GreetdManager.selectedUser`'s (none yet: "Welcome").
- **Editing and preview.** `LockManager.editor` is a `services/ScreenLayoutEditor` (non-singleton, shared with the greeter): the draft (`ConfigDraft` of `["Lockscreen", "layout"]`, so it never fights the settings page's draft over `mode`), its `GridEditor` (`layout`), `problems`, `updateLayoutField`, `ensureLoaded`/`saveChanges`/`resetChanges` and the preview. "Show on screen" (`startPreview()`) closes the overlay and shows `surfaces/lockscreen/LockPreviewWindow` on the target screen (fixed when it starts, `previewScreen`): an Overlay-layer window with exclusive keyboard focus holding `LockSurface { preview: true }` on the draft. Nothing is locked and the field is inert (it lets Escape through); Escape or a click on the background (`stopPreview()`) reopens the overlay on Layouts. `lock()` ends a preview first.
- `showMedia` became modules in ConfigMigration v34 (Greeting, NowPlaying unless it was off, Password, where the old column had them).

## Greeter (`Greeter` section, `GreeterConfig`, `GreeterManager`, `GreetdManager`)

Axiom as greetd's login screen, laid out like the lock screen. Off by default; set up from Settings → Screen & Power → Login screen (`views/settings/GreeterStatusCard`) or the onboarder's Integrations page, both through `forms/GreeterSetup`. The greeter runs as greetd's user, who can't read the user's home, so it runs from a copy and reads an export:
- **Install** (`GreeterManager.install`/`update`/`uninstall`, one polkit prompt each: `pkexec /usr/bin/bash scripts/greeter/greeter_install.sh <action> <repo> <user> [<staged bundle>]` until it's installed, then `pkexec /usr/share/axiom-greeter/scripts/greeter/greeter_install.sh …`, root's copy, which the installed polkit action `org.axiom.greeter.manage` (`scripts/greeter/org.axiom.greeter.policy`) names by `exec.path`, so its prompt says what it's for and the user's own file never runs as root again (`check` reports `helper`). An update is run by the copy it replaces, so the script's arguments stay compatible. `check`/`hash` run without root; under pkexec, `<user>` must be `$PKEXEC_UID`'s). It copies the code (less tests, docs and `*.md`) from `Greeter.source` (`GreeterConfig.source`; the script's `<source> <channel>` arguments, the channel being `SelfUpdate.channel`) to `/usr/share/axiom-greeter` (root's; `.greeter-source` says where from, `"git <channel> <url>"` or `"local"`, and `.greeter-hash` names the version): **git** (default) fetches, as root, into its own bare mirror `/var/lib/axiom-greeter/upstream.git` the channel's newest `v*` tag (peeled, `sort -V`) or `main`/`master`, found with `git ls-remote` on the url recorded at the first git install (the clone's branch remote, else `origin`, made https so root needs no keys): the clone and its remote can't redirect it later, and its hash is the commit; **local** archives the clone's tracked files as they are in the working tree (whatever branch, uncommitted changes included; `git ls-files` + `tar`, as the user through `runuser`, so the clone's config and filters never run as root), its hash the files' content (docs edits are no update). A copy without `greeter.qml`, the session script or the policy (a release from before the login screen) is refused. `ext::` transports are off and git never prompts. Then it makes `/var/lib/axiom-greeter` (`config/` the user's, the bundle; `state/` greetd's user's: the last user and their sessions, `GreetdManager`'s `greeter` state), snapshots the bundle as the copy's `fallback/` (from `<staged bundle>`, `$XDG_RUNTIME_DIR/axiom/greeter-bundle`, which axiom writes just before install and update since a first install has no bundle yet; copied with `-P`: the folder is the user's, and root never follows a link there), and points greetd's `default_session` `command` at `scripts/greeter/greeter-session.sh` after backing `/etc/greetd/config.toml` up (`.axiom-original` once, `.axiom-bak-<date>` per change; line-wise, keeping its `user`). Uninstall puts the original back and deletes `.axiom-original`, so a later install backs up the config as it is then. A copy that can't be swapped in leaves the old one in place. It refuses without `agreety` (`greetd-agreety`), the fallback login. While pkexec waits, the overlay and onboarder step aside unless axiom's own polkit agent is running (ShellManager). `finishCommands` are what the user runs to make greetd the display manager (`readlink display-manager.service`); the card shows them as `CodeLine`s. Every path is under `$AXIOM_GREETER_ROOT` for tests (`tests/scripts/test_scripts.py` `GreeterInstall`); never run it against the real `/`.
- **Status** (`check` at startup, on the card and after each action): `checking` | `checkFailed` (the first check failed: `lastError` says why, Check again retries) | `noGreetd` (greetd or agreety missing) | `off` | `notInstalled` (`Greeter.enabled` with no copy) | `outdated` (the copy's hash isn't its source's current one, `installedSource` isn't `GreeterManager.wantedSource` (the setting changed), or greetd's command changed; a git remote that can't be reached, `currentHash` "", isn't behind) | `installed`. `Greeter.enabled` (`x-settings: false`) is set by Install and cleared by Remove; it shows the Layouts page's Login screen row. A new `outdated` hash is notified once (`config/state/greeterUpdates.json` `notifiedHash`; `desktopEntry` `axiom-greeter-update`, whose handler opens Settings → Login screen). IPC `greeter`: `open`, `preview`.
- **The bundle** (`GreeterBundle.exportConfig`, pure): the `Greeter`, `Appearance`, `General`, `Weather` and `Lockscreen` sections, `Hyprland.mode` and `monitors.profiles`, and in managed mode the `Hyprland.managed` options marked `x-greeter` (keyboard, mouse, touchpad, cursor); `theme.json` (`ThemeManager.currentTheme`); each wallpaper copied to `wallpapers/<md5 of its url>.<ext>` (cp + mv, stale ones removed), the bundle's `Appearance` naming the copies. Written by one `sh` (`GreeterManager._writeBundle`: each JSON through a temp file and a rename, then `chmod -R go+rX` so greetd's user can read it whatever the umask) while installed and writable, a second after any of it changes (a failed write is retried on the next change); right after an install or update succeeds, so the greeter never starts before its bundle; and, JSON only, to the staging folder before one. Changing the login screen therefore needs no root; only code changes need Update.
- **Running it.** `greeter-session.sh` (greetd's command) starts `start-hyprland` on `scripts/greeter/hyprland.lua` (logo off, numlock, no animations), whose start hook runs `greeter-session.sh shell`: `AXIOM_GREETER=1 qs -p <copy>/greeter.qml`, once more with `AXIOM_GREETER_SAFE=1` if it fails (qs exits non-zero on a broken load), then `hyprctl dispatch 'hl.dsp.exit()'`. Twice failed (a marker in `$XDG_RUNTIME_DIR`, else the greeter's `state/`; never `/tmp`) or no Hyprland: `agreety --cmd '${SHELL:-/bin/sh}'`, quoted so the session's own `sh` expands it to the login shell of whoever logs in, so a login is always possible.
- **Greeter mode** (`AXIOM_GREETER=1`; `Paths.greeter`, read from the environment again in `ConfigManager.greeter` since it reads no reader). `greeter.qml` builds only `shell/Greeter` (a `GreeterWindow` per screen; one `FloatingWindow` with `AXIOM_GREETER_WINDOWED=1`, for looking at it from a session; `AXIOM_GREETER_DIR` points it at a scratch folder). `ConfigManager` loads `GreeterBundle.pick([bundle, fallback/])`: the first that parses and passes migrate/prune/defaults/validate (a bundle from a newer axiom is still tried, its unknown keys pruned), else schema defaults, logging why each was skipped; it never writes, watches or polls. `ThemeManager` reads the `theme.json` beside the config `ConfigManager.greeterSource` names (the bundle's, else `fallback/`'s, so safe mode never loads a bundle theme) and generates, links and runs nothing; `Paths.statePath`/`userStatePath` are the greeter's `state/`. Singletons are lazy, so nothing else of the session's starts.
- **GreetdManager** (`Quickshell.Services.Greetd`): `users` (`methods/GreeterUsers`: `/etc/passwd` within `/etc/login.defs`' UID range, login shells only), `sessions` (`methods/GreeterSessions`: `/usr/share/wayland-sessions/*.desktop`, Exec split by the desktop entry spec, field codes dropped), `selectUser(name)` (a typed name not in the list is still tried), the user's last session, `submit(response)` (creates the session with the password pending for greetd's first question; later questions, an OTP, become `prompt`/`promptEcho`), `cancel()`, `failed`, launching with `XDG_SESSION_TYPE`/`XDG_CURRENT_DESKTOP`/`XDG_SESSION_DESKTOP`, remembering the user (with `rememberUser`) and their session, `power(action)` (`systemctl`), the keyboard layouts (`hyprctl devices`, `switchxkblayout`) and `avatarOf(name)` (AccountsService's icons). At start it evals `HyprLua.greeterLua` (the profiles' `monitorsLua`, in every mode, plus one `hl.config` of the `x-greeter` options in managed mode) and `hyprctl setcursor`; not when windowed.
- **Surfaces and modules.** `surfaces/greeter/GreeterSurface` (a `ScreenLayoutView`): host `{ kind: "greeter", target, preview, key, bare, passwordBorder, greetingBorder }`, the target being `Greeter.monitor`'s screen; other screens follow `otherScreens`; with no Login module reported (`ShellManager.requiredFields`) it draws a `content/parts/LoginField` of its own. Greeter-only modules: `Login` (`x-required`; a `LoginField`: `StyledComboEntry` of users, typed over, and `PasswordEntry`, plus the picture; the two side by side in a slot too short to stack them, shrunk to fit one shorter than a field), `Session` (the field alone, no card, in a slot shorter than it), `Power` (restart and shut down ask twice; also on the lock screen) and `KeyboardLayout`; display modules list `greeter` in `x-hosts` (ClockCalendar, Greeting, Weather, Battery, Network, Palette, ColorSwatch). Every one is inert unless `host.kind === "greeter" && !host.preview && Paths.greeter`, so the user's session never talks to greetd. `ScreenLayoutView` draws only modules whose `x-hosts` list the host's `kind` (validation takes any module in a `ScreenLayout`, and the bundle's folder is writable by any of the user's programs), so a hand-made bundle can't put a launcher on the login screen. "Show on screen" (`GreeterManager.editor`, a `ScreenLayoutEditor`) shows `GreeterPreviewWindow` from `shell/GreeterPreview`.
